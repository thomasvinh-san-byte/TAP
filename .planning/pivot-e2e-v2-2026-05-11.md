# Pivot E2E v2 — Brief stratégique + Playbook Claude Code Web

**Date** : 2026-05-11
**Auteur** : Guillaume (révision v2 après constat UX preview)
**Statut** : Remplace `pivot-e2e-2026-05-11.md` (v1)

---

## 0. Pourquoi un v2

Le brief v1 traitait l'UX comme une contrainte transversale, citée dans une section « Principes invariants » qu'on peut raisonnablement ignorer pendant l'exécution. Conséquence concrète, observée sur la preview au 2026-05-11 : la page `/patients` ressemble à une liste HTML basique, le bouton « + Nouvelle course » déborde du header, aucun menu utilisateur connecté n'est visible, aucune hiérarchie visuelle ne distingue ce SaaS d'un CRUD générique. Le CLAUDE.md §1 promet le niveau Linear/Stripe ; la livraison concrète n'y est pas.

Le v2 corrige cela en deux points.

Premier point : chaque passe a maintenant **deux goals parallèles** — un goal fonctionnel (ce que l'utilisateur peut faire) et un goal UX (à quoi ça ressemble et comment ça se sent). Aucun goal ne peut être validé sans l'autre. Une passe livrée techniquement mais visuellement médiocre est une passe non-livrée.

Deuxième point : le brief est structuré en **playbook prompt-ready pour Claude Code web**. Les sections de la Passe 1 sont découpées en 6 prompts numérotés 03-A à 03-F, prêts à copier-coller un par un. Entre chaque prompt, Guillaume valide la livraison avant de coller le suivant. Pas de monologue Claude Code, pas de dérive de scope.

## 1. Constat sur l'existant (preview 2026-05-11)

**Ce qui marche.** Login fonctionnel (après fix GoTrue NULL). Liste patients avec recherche fuzzy. Saisie express course par modal global (Cmd/Ctrl+Shift+K). Auto-save brouillons en DB. Audit triggers Postgres opérationnels. RLS multi-tenant et chiffrement NIR en place.

**Ce qui ne marche pas visuellement.**

1. Header de l'app : bouton « + Nouvelle course » déborde du conteneur, pas d'alignement propre, pas de menu utilisateur (déconnexion, profil).
2. Liste `/patients` : pas d'avatar ou d'initiale, pas de date de dernière course, pas de prochain rendez-vous, pas de statut visible. Le badge `canal_contact_prefere` est isolé, sans contexte.
3. Absence totale de l'identité visuelle annoncée dans CLAUDE.md §1 : pas d'accent terracotta visible, pas de chiffres tabulaires perceptibles sur les téléphones, pas de hiérarchie typographique forte.
4. Pas de feedback de connexion : on ne sait pas qu'on est connecté en `regulateur@demo.tap`.

**Ce que ça implique.** Avant de produire la Passe 1, on consacre **un prompt entier (03-C) à la refonte du shell de l'application** — layout, header, navigation, design tokens visibles, mode nuit. Sans ça, chaque écran ajouté hérite du shell cassé actuel.

## 2. Principes UX intégrés (non négociables sur toutes les passes)

Ces principes sont à reprendre tels quels dans tous les prompts Claude Code, en bloc « contraintes UX ». Ils ne sont pas redécouverts à chaque passe.

**Identité.** Bleu primaire profond (variable `--primary` déjà en place) + accent terracotta `--accent` à utiliser réellement, pas juste défini. Inter avec `font-feature-settings: 'tnum'` pour les chiffres tabulaires partout où il y a des numéros (téléphones, montants, dates, IDs). Lucide ligne fine pour toutes les icônes, jamais mélangé.

**Spacing strict.** Échelle 4/8/12/16/24/32/48/64. Aucune valeur intermédiaire. Si un écran a l'air vide ou serré, c'est probablement le mauvais cran de l'échelle, pas une valeur intermédiaire à inventer.

**Hiérarchie visuelle.** Chaque écran a une H1, des H2/H3 si nécessaire, un texte secondaire `text-muted-foreground` pour les méta. Les actions principales en `--primary`, les destructives en `--destructive`, jamais l'inverse. Pas plus d'une action primaire par écran.

**États.** Repos, survol, pressé, actif, désactivé — 5 états distincts sur tout élément interactif. Transitions 150ms ease-out. Focus clavier visible avec anneau coloré et offset, jamais retiré.

**Feedback.** Skeleton screens pour les chargements > 500 ms, jamais de spinners. Optimistic UI sur les mutations courantes. Toast Sonner pour confirmation, jamais d'alert ni de popup natif. Erreurs reformulées en français lisible, jamais de message brut.

**Mode nuit.** Traité à parité du mode jour. Pas une inversion mécanique, des choix de palette dédiés. Le toggle est dans le menu utilisateur du header.

**Mobile.** Boutons d'action principale chauffeur ≥ 56 px de hauteur, texte ≥ 18 px. Une action principale unique par écran chauffeur, en bas, accessible au pouce. Tests minimum iPhone SE 375 px et desktop 1280 px avant push.

**Densité.** Côté régulateur, dense mais lisible (référence : Linear, Posthog). Côté chauffeur, aéré et grand (référence : Things 3, Cron mobile).

## 4. Passe 1 (Phase 3) — Détail complet

### 4.1 Goal fonctionnel

Un régulateur et un chauffeur peuvent ensemble compléter le parcours d'une course du premier appel patient à la trace finale en moins de 10 minutes, en jouant les 6 maillons. Le régulateur crée la course, choisit un chauffeur dans une liste, le chauffeur voit sa journée sur son téléphone, démarre, clôture en saisissant tarif + paiement, le régulateur voit l'encaissement, l'audit log liste les 7 transitions.

### 4.2 Goal UX

Le shell de l'application est refondu pour avoir le niveau de finition d'un Linear (côté régulateur) ou d'un Things 3 (côté chauffeur). Concrètement :

- Header propre avec logo, navigation, menu utilisateur (avatar/initiales, nom, rôle, déconnexion, toggle mode nuit)
- Nav latérale ou top selon le rôle, distincte par couleur de rôle (dirigeant, régulateur, chauffeur)
- Liste `/patients` enrichie : initiales colorées, nom + prénom, téléphone tabulaire, date de dernière course, prochaine course si programmée, badge canal contact en contexte
- Page de détail patient en drawer slide-in, pas redirection page
- Écran chauffeur `/conduite` : cartes empilées avec une seule action primaire par carte, fond aéré, typographie 18 px, gros boutons 56 px
- Toast Sonner sur chaque mutation, skeleton sur chaque chargement
- Mode nuit fonctionnel partout

### 4.3 Périmètre — dans / hors

**Dans la Passe 1** : référentiel chauffeurs (CRUD simple dirigeant), référentiel véhicules (CRUD simple dirigeant), assignation course → chauffeur via liste déroulante, vue chauffeur `/conduite` sur navigateur mobile responsive (pas de PWA), bouton Démarrer + Clôturer côté chauffeur, saisie manuelle tarif numeric à la clôture, marquage encaissement + méthode, liste du jour côté régulateur enrichie, audit triggers étendus.

**Hors Passe 1** : PWA installable, hors-ligne, calcul CGSS automatique, drag & drop assignation, tournée comme objet métier persistant, récurrences, SMS, optimisation OR-Tools, mode dégradé, B2B portail, 2FA.

### 4.4 Écrans-cibles + références visuelles

**Shell (header + nav + menu user)** — référence : Linear (header ultra-compact, dense, menu user en haut à droite avec avatar coloré). Bouton primaire bien aligné en flex justify-end, gap-16, menu user à droite avec dropdown Radix.

**Liste `/patients`** — référence : Linear issues list (densité, alignement, hover ligne). Pour chaque patient : initiale colorée 32px, nom prénom semibold, téléphone tabular-nums muted-foreground, dernière course en date relative FR (« il y a 3 jours »), prochaine course si applicable, badge canal en bout de ligne. Hover : background muted, transition 150 ms.

**Drawer patient** — référence : Linear issue side panel ou Stripe customer drawer. Slide depuis la droite, largeur 480 px, sections empilées : Identité, Coordonnées, Préférences, Notes opérationnelles, Historique courses (5 dernières). Header sticky avec actions (Modifier, Archiver, Historique complet).

**Liste `/courses`** — référence : Linear sprint board ou Stripe payments list. Colonnes : heure, patient (avec initiale), trajet (pickup → dropoff), mode, urgence, chauffeur assigné (ou bouton Assigner si vide), statut, paiement (badge). Hover ligne pour preview, click pour drawer détail.

**Modal assignation** — référence : Linear assignee picker. Combobox recherche chauffeur par nom, liste filtrée par chauffeurs actifs, option « Assigner aussi un véhicule » (combobox secondaire), validation Cmd+Entrée.

**Écran chauffeur `/conduite`** — référence : Things 3 today view + Cron mobile event card. Liste verticale de cartes empilées, une carte par course du jour. Carte = en-tête patient + heure, corps adresse pickup et dropoff (icônes Lucide MapPin pour pickup, Navigation pour dropoff), pied de carte = bouton primaire contextuel large (Démarrer pour le prochain, Clôturer pour celui en cours, terminé en grisé). Fond `--background`, cartes en `--card` avec ombre douce.

**Modal de clôture** — référence : Stripe checkout-style mini. Modal mobile bottom-sheet, 3 champs : tarif en chiffres tabulaires gros (input numeric step 0.50), payment_method (4 boutons radio cash/CB/chèque/cgss_différé en grille 2×2), payment_status (toggle encaissé/à encaisser), bouton primaire « Clôturer la course » 56 px.

**Menu utilisateur** — référence : Linear user menu top-right. Avatar 32 px avec initiales colorées par rôle (dirigeant bleu profond, régulateur terracotta, chauffeur vert). Dropdown contenant : nom complet, rôle traduit en FR (Dirigeante, Régulatrice, Chauffeur), email muted, séparateur, Toggle mode jour/nuit avec icône Sun/Moon, Paramètres (placeholder désactivé), séparateur, Déconnexion (destructive).

### 4.5 Critère de fin de Passe 1

Guillaume seul joue le parcours suivant en moins de 15 minutes, sans aide externe, sans regarder le code :

1. Connexion en `regulateur@demo.tap`
2. Création d'un patient via `+ Nouveau patient` (drawer)
3. Saisie d'une course Cmd+Shift+K pour ce patient, créneau libre, deux adresses
4. Assignation à `chauffeur@demo.tap` via liste déroulante depuis `/courses`
5. Déconnexion régulateur, connexion chauffeur sur même navigateur en mode mobile (375 px)
6. Ouverture `/conduite`, course visible dans la liste du jour
7. Démarrage de la course (bouton primaire carte)
8. Clôture avec tarif 28.50 + payment_method cash + payment_status encaissé
9. Déconnexion chauffeur, reconnexion régulateur
10. Vérification dans `/courses` que la course est `terminee` + `payment_status = encaisse`
11. Ouverture du drawer course → onglet historique → 7 entrées audit_logs visibles

Critères de succès :
- Durée totale ≤ 15 min mesurée à la montre
- Aucun bug bloquant (404, 500, modal qui ne s'ouvre pas, formulaire qui rejette une saisie valide)
- Aucune friction visuelle évidente (texte coupé, bouton qui déborde, alignement cassé, contraste illisible)
- Mode nuit testé sur 3 écrans au moins, lisible
- Test desktop 1280 px + iPhone SE 375 px sur les écrans clés

Si un de ces critères n'est pas rempli, la passe est en « livrée tech / non validée UX » et un retour Claude Code corrige.

## 7. Validation Guillaume seul — protocole

Sans design partner externe, le risque de s'auto-rassurer est réel. Trois contre-mesures actives sur toutes les passes.

**Règle de la nuit.** Entre la livraison d'un prompt (PR validée techniquement) et la validation UX, laisser au moins une nuit. Le matin, on revient à l'écran avec un œil plus frais et on détecte les frictions invisibles la veille.

**Règle de la grand-mère.** Pendant le walkthrough, jouer le parcours en s'imaginant l'expliquer à voix haute à quelqu'un qui ne connaît ni le code ni le métier TAP. Chaque endroit où l'explication dépasse une phrase pour clarifier ce que fait l'écran = friction. À noter dans `docs/observations/AAAA-MM-JJ-guillaume-autotest.md`.

**Règle des 5 captures.** À la fin de chaque passe, prendre 5 captures « pourrait être un screenshot produit » et 5 captures « pas encore prêt ». Le ratio donne le verdict honnête de la maturité visuelle. Si le ratio est en dessous de 1:1 sur la Passe 1, on ne lance pas la Passe 2.
