# Plan 06.13-01 — Foundations design system

## Goal

Livrer 3 documents + 1 fichier `tokens.json` en suivant la structure
définie 2026-06-03. Pas de code applicatif. Pas de dépendance npm.

## Livrables

### Livrable 1 — `docs/design-system/01-foundations.md`

Document de doctrine et conventions visuelles. Structure imposée :

1. **Préface** : raison d'être du design system TAP, doctrine
   accessibilité (DEC-088), étoile polaire (DEC-089), portée
   (`apps/web` uniquement V1).
2. **Couleurs sémantiques** : grille avec noms sémantiques
   (`color.surface.*`, `color.text.*`, `color.action.*`,
   `color.feedback.*` : success/warning/danger/info, `color.border.*`).
   Mapping vers les variables CSS HSL et les classes Tailwind actuellement
   utilisées dans le repo. **Ne pas inventer de nouvelles couleurs** —
   documenter ce qui existe.
3. **Échelle d'espacement** : confirmer le 4/8/12/16/24/32/48/64 utilisé
   actuellement. Documenter les classes Tailwind correspondantes.
4. **Typographie** : font-family (Inter), scale modulaire
   (xs/sm/base/lg/xl/2xl/3xl), line-height, font-weight conventions.
5. **Rayons (radii)** : `radius.sm/md/lg/full` mapping CSS var `--radius`.
6. **Élévation (shadows)** : 3-4 niveaux maximum (Atlassian doctrine),
   `shadow.subtle/raised/overlay`. Mode sombre traité à parité (cf.
   `globals.css`).
7. **Motion** : durations (`fast=150ms`, `medium=200ms`, `slow=400ms`)
   + easings standard (`ease-out` pour entrées, `ease-in` pour sorties).
   Aligné sur Tailwind config `transitionDuration.DEFAULT=150ms` et
   `transitionTimingFunction.DEFAULT=cubic-bezier(0,0,0.2,1)`.
8. **Doctrine accessibilité datée** : check-list WCAG 2.1 AA appliquée
   à TAP — contraste 4.5:1 min, focus visible, navigation clavier,
   doublement couleur+texte, ARIA landmarks, skip links. Mention
   RGAA 4.1.2 et Access42 comme référence d'audit possible future.
9. **NE PAS** documenter ce qui n'est pas en place — pas de doctrine
   théorique sur des conventions non appliquées. Tout doit être traçable
   dans le code existant.

### Livrable 2 — `apps/web/src/styles/tokens.json`

Fichier source de vérité au format W3C Design Tokens Format Module
2025.10 (`$value` / `$type` / `$description`).

Les valeurs HSL/dimensions doivent être alignées sur :

- `apps/web/src/app/globals.css` (CSS vars HSL light + dark).
- `apps/web/tailwind.config.ts` (spacing 4/8/12/16/24/32/48/64,
  durations, easings, radius).

**Avant de figer les valeurs**, exécuter :

```bash
cat apps/web/tailwind.config.ts
cat apps/web/src/app/globals.css
```

Le but est de **documenter l'existant**, pas d'introduire de nouvelles
couleurs.

### Livrable 3 — `docs/design-system/02-patterns-emergents.md`

Catalogue des 5 patterns réutilisables identifiés en Phase 06.11. Pour
chaque pattern, structure imposée :

1. **Nom + emplacement** dans le repo.
2. **Phase d'origine** + lien vers PR.
3. **Description courte** : à quoi sert ce pattern, dans quel contexte
   l'utiliser.
4. **Props / Variants** : interface TypeScript reproduite, brièvement
   commentée.
5. **Code exemple** : usage typique (10-15 lignes max).
6. **Do / Don't** : 2-3 do, 2-3 don't.
7. **Accessibilité** : ce qui est en place (`tabIndex`, `aria-label`,
   contraste…).
8. **Évolutions futures** : ce qu'on pourrait améliorer V2.

5 patterns à documenter :

| Pattern                           | Emplacement                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------- |
| `KpiCard` (4 variantes)           | `apps/web/src/app/(app)/tableau-de-bord/_components/kpi-card.tsx`            |
| `EmptyState` (action discriminée) | `apps/web/src/components/ui/empty-state.tsx`                                 |
| `RideBadge` (3 types)             | `apps/web/src/app/(app)/cockpit/optimisation/_components/ride-badge.tsx`     |
| `SlaBadgesCard` (règles SLA)      | `apps/web/src/app/(app)/tableau-de-bord/_components/sla-badges-card.tsx`    |
| `HautsBadge` (modèle référence)   | `apps/web/src/app/(app)/cockpit/optimisation/_components/hauts-badge.tsx`    |

**Avant de rédiger, lire chaque fichier** pour reproduire l'interface
exacte. Ne pas inventer.

### Livrable 4 — `docs/design-system/03-benchmark-foss.md` (optionnel)

Capitalisation des recherches FOSS méthodiques. Structure :

1. **Normes & standards applicables** : WCAG 2.1 AA, RGAA 4.1.2, W3C
   Design Tokens 2025.10, ARIA Authoring Practices.
2. **Design systems FOSS top 10** par pertinence pour TAP (Carbon,
   Atlassian, NHS, Polaris, Primer, Fluent 2, Material 3, Spectrum,
   Salesforce Lightning, DSFR-référence-seulement).
3. **Meilleures UI sectorielles** : santé (Doctolib, NHS Apps, Bahmni
   référence sémantique), logistique (Onfleet, Routific, Solvice, HVI,
   RoadWarrior, Traccar), SaaS (Stripe, Linear, Notion, Cal.com,
   Posthog, Supabase Studio, Vercel, Refine, Plane).
4. **Doctrine d'application** : emprunter / adapter / rejeter (verbatim
   doctrine 06.6 LOCKED pour conformité RGPD).
5. **Plan d'attaque phases futures** : pour chaque écran TAP, identifier
   1-2 références FOSS à étudier en priorité avant refonte (table de
   correspondance).

Si le livrable 4 demande > 3 h pour livrer une version complète,
**privilégier les Livrables 1-2-3** et signaler en `Concerns:` :
