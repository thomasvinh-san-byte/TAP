# Recherche — Phase 06.14 : migration tokens.json → Tailwind config

But du document : capitaliser les bonnes pratiques 2025-2026 pour brancher le
`tokens.json` (livré Phase 06.13, format W3C DTCG 2025.10) sur le code, sans
créer de divergence entre sources de vérité. Sert d'amont au
`/gsd-discuss-phase 06.14`. Toutes les recommandations portent leur source.

## 0. État réel du repo (vérifié 2026-06-04, pas supposé)

- **Tailwind v3.4.10**, Next.js 14.2.35, PostCSS + autoprefixer classiques.
- Chaîne de couleur actuelle : `globals.css` définit des CSS vars HSL
  (`--primary: 217 92% 32%`) → `tailwind.config.ts` les référence en
  `hsl(var(--primary))`.
- `tokens.json` (Phase 06.13) est une **troisième** représentation des mêmes
  valeurs, au format DTCG, avec `$description` documentant les variantes sombres.
- **Style Dictionary absent** du repo (aucune dépendance, aucun script tokens).
- Seulement **2 fichiers `.tsx`** contiennent des couleurs en dur (hex/rgb) —
  le code est déjà très propre, la « migration des consommateurs » est donc
  un chantier modeste.
- `globals.css` **n'a pas de bloc `.dark`** alors que `tokens.json` documente
  des valeurs sombres partout. Divergence à acter en discuss (cf. §5, risque R3).

## 1. Le consensus de fond : le token est la source, la CSS var est un output

La spec DTCG a atteint sa première version stable (2025.10) en octobre 2025,
établissant un format vendor-neutre pour partager les décisions de design entre
outils. Les design tokens sont la source de vérité unique pour les couleurs, la typographie, l'espacement et les autres décisions de design, longtemps fragmentées entre formats propriétaires.

Le point doctrinal qui tranche notre situation à trois sources : une CSS var
vit dans le CSS, tandis qu'un token vit dans un format qui peut compiler vers
CSS, Swift, Kotlin ou une config Tailwind. Le token est la source de vérité ; la variable CSS est l'un des outputs de cette source.

**Implication directe pour 06.14** : il ne faut pas trois fichiers maintenus à
la main (`tokens.json` + `globals.css` + `tailwind.config.ts`). La cible saine
est : `tokens.json` source → génération automatique des CSS vars (et idéalement
des valeurs Tailwind). Sinon on retombe dans la dérive que la Phase 06.13 disait
vouloir éviter. Tout design system commence par un mensonge : « on gardera les couleurs synchronisées à la main » — puis la réalité rattrape.

## 2. L'outil standard : Style Dictionary

Le transformateur attendu par l'écosystème DTCG est Style Dictionary (aussi
Theo, Supernova). Les tokens sont définis dans un fichier JSON et traités par un transformateur comme Style Dictionary, qui les exporte en plusieurs formats : pour le web, ils deviennent des valeurs de config Tailwind ou des variables CSS.

Bonne pratique de nommage relevée : garder les tokens agnostiques de la plateforme — ne pas employer de nommage spécifique à Tailwind dans les fichiers de tokens bruts. Le `tokens.json` actuel respecte déjà ça (nommage sémantique `color.action.primary`, pas `colors.primary` façon Tailwind).

Architecture en couches recommandée : définir les tokens au format DTCG avec une architecture en couches (base et alias). Une 3e couche « component tokens » est optionnelle et ne se justifie qu'à l'échelle ; inutile ici.

## 3. Le piège technique central : HSL + `<alpha-value>`

**C'est le défaut le plus important à corriger en 06.14.** La config actuelle
écrit `hsl(var(--primary))` — sans le placeholder d'alpha. Conséquence : les
utilitaires d'opacité Tailwind (`bg-primary/50`, `text-foreground/70`) ne
fonctionnent pas correctement.

Le pattern correct documenté par Tailwind v3 : déclarer la couleur comme
`'hsl(var(--primary) / <alpha-value>)'`, en stockant la CSS var en composantes
HSL séparées par des espaces, **sans `hsl()` autour** (`--primary: 217 92% 32%`,
ce que le repo fait déjà). Lors de la définition des couleurs ainsi, le format des variables CSS doit correspondre à la fonction de couleur utilisée : espaces pour la syntaxe moderne, virgules pour les fonctions legacy comme rgba.

Tailwind expose un slot d'alpha aux couleurs définies en fonction, et un check
gère le cas où l'alpha n'est pas fourni. On reçoit la valeur d'opacité de Tailwind utilisable comme canal alpha avec la couleur au format approprié ; si elle est indéfinie, on retourne la couleur sans alpha. Avec le placeholder `<alpha-value>`, ce câblage est automatique côté Tailwind v3 — pas besoin de fonction custom.

→ **Action 06.14** : passer tous les `hsl(var(--x))` en `hsl(var(--x) / <alpha-value>)`. Gain immédiat : toute la grammaire d'opacité Tailwind redevient disponible sur les couleurs du design system.

## 4. Décision de fond à trancher en discuss : rester v3 ou migrer v4 ?

Tailwind v4 est stable et production-ready depuis 2025, avec une config
**CSS-first** (`@theme` dans le CSS) qui remplace `tailwind.config.js`, un moteur
Oxide (Rust) 3-10× plus rapide, et des CSS vars natives pour tous les tokens.
Pour de nouveaux projets ciblant des navigateurs modernes, v4 est le choix évident ; pour les projets existants, il faut peser les bénéfices contre le coût de migration et les exigences navigateur.

Le point bloquant potentiel — les cibles navigateur : Tailwind v4.0 vise Safari 16.4+, Chrome 111+, Firefox 128+ ; pour supporter des navigateurs plus anciens, rester en v3.4 jusqu'à ce que les exigences changent. v4 dépend de features CSS modernes (`@property`, `color-mix()`, `@layer`).

Nuance importante sur les classes composant : les classes composant semblent devenues des citoyens de seconde zone en v4 par rapport aux utilitaires ; l'ajout d'utilitaires custom passe désormais par la directive @utility (cascade layers natives) plutôt que par @layer utilities.

**Lecture pour TAP** : il y a une convergence forte entre v4 (CSS-first,
`@theme`, CSS vars natives) et notre cible « tokens → CSS vars ». MAIS :
- migrer v4 est une **autre phase** (06.9 modernise déjà Next 15 ; coupler v4 à
  ce moment-là est plus cohérent qu'en 06.14) ;
- v4 a un coût et des exigences navigateur à valider contre la cible PWA
  chauffeur (iOS Safari ancien possible sur le terrain — à vérifier) ;
- v3.4 reste un excellent framework et recevra les mises à jour de sécurité ; rester en v3 est un choix parfaitement raisonnable.

→ **Recommandation pour le discuss** : faire 06.14 **en v3** (corriger l'alpha,
poser le pont tokens → CSS vars via Style Dictionary), et inscrire la bascule v4
comme décision séparée à coupler éventuellement avec 06.9. Ne pas mélanger les
deux dans une seule PR. La décision t'appartient (dirigeant).

## 5. Risques identifiés (à verser en CONTEXT)

- **R1 — triple source de vérité.** Si 06.14 se contente de recopier les tokens
  dans la config sans générer, on aggrave la dérive. Mitigation : Style
  Dictionary génère `globals.css` (et/ou un fragment de thème) depuis
  `tokens.json`. `tokens.json` devient seul éditable à la main.
- **R2 — alpha cassé silencieusement.** Le `hsl(var(--x))` sans `<alpha-value>`
  marche pour l'opacité 100 % et casse en silence sur `/50`. À corriger pour
  tout le set en une passe (cf. §3).
- **R3 — dark mode documenté mais absent. TRANCHÉ (décision dirigeant
  2026-06-04) : 06.14 GÉNÈRE le bloc `.dark` depuis les tokens.** Motif :
  lutter contre la dérive — si `tokens.json` est la source de vérité, le dark
  en est un output, pas un fichier écrit à la main à côté. Cela résout R1 et R3
  d'un même geste.
  **Pré-requis bloquant découvert (vérifié 2026-06-04)** : aujourd'hui le dark
  n'existe QUE en prose dans les `$description` (« Sombre : hsl(...) »), jamais
  comme valeur exploitable. Style Dictionary ne peut rien générer en l'état. Il
  faut donc D'ABORD **restructurer `tokens.json`** pour porter une vraie valeur
  light + dark par couleur concernée.
  **Périmètre chiffré (vérifié)** : 57 tokens feuilles au total ; seulement
  **12 couleurs** ont une variante sombre (toutes parsables proprement depuis
  le texte actuel) ; les **45 autres** sont non-chromatiques (spacing, typo,
  radius, shadow, motion, touch targets) — invariants light/dark, à NE PAS
  dupliquer. Les 3 couleurs sans dark documenté (`text.onAction`,
  `action.focusRing`, `border.input`) : décider en discuss si elles héritent
  du light ou reçoivent une valeur dark explicite.
  **Architecture DTCG du dark : à trancher en discuss** (décision dirigeant :
  laisser Claude Code arbitrer après relecture de la spec 2025.10). Deux options
  cadrées :
  - (a) **Token Sets** : un fichier tokens de base + un fichier d'override
    dark qui ne redéclare que les 12 couleurs. Approche standard DTCG,
    multi-thème-friendly, recommandée par l'écosystème Style Dictionary.
  - (b) **`$value` structuré** light/dark par token : plus compact, un seul
    fichier, mais s'écarte du modèle « un set = un thème » de la spec.
    Claude Code tranche en relisant la spec DTCG 2025.10 (designtokens.org) et
    la doc Style Dictionary sur le theming, puis inscrit le choix en DEC + ADR
    si structurant.
- **R4 — couleurs en dur résiduelles.** 2 fichiers `.tsx` portent des couleurs
  en dur. Petit, mais à inclure dans le périmètre « migration consommateurs »
  pour clore proprement.
- **R5 — hook guard-commit.** Toute modif touche `pnpm typecheck` +
  `format:check`. Un script de génération de tokens doit produire un output
  déjà formaté (ou lancer prettier en post-build) pour ne pas bloquer le commit.

## 6. Proposition de périmètre V1 (à valider/amender en discuss)

1. **Restructurer `tokens.json`** pour porter le dark comme valeur exploitable
   (12 couleurs concernées), selon l'architecture DTCG tranchée en discuss
   (Token Sets ou `$value` structuré). Migrer les valeurs sombres actuellement
   en prose dans les `$description` vers de vraies valeurs. Retirer les mentions
   « Sombre : … » devenues redondantes des descriptions.
2. Ajouter Style Dictionary (devDependency) + script `tokens:build`.
3. Générer `globals.css` — CSS vars light **+ bloc `.dark`** (décision dirigeant
   2026-06-04) — depuis `tokens.json`. `tokens.json` = seule source éditable.
4. Corriger le pattern couleur en `hsl(var(--x) / <alpha-value>)` dans
   `tailwind.config.ts`.
5. Migrer les 2 fichiers à couleurs en dur vers les classes sémantiques.
6. Documenter dans `docs/design-system/` le workflow « éditer un token →
   `pnpm tokens:build` → commit » + le mécanisme de bascule de thème.
7. Rester en Tailwind v3 ; inscrire v4 comme décision séparée (couplage 06.9).

Estimation indicative inchangée (5-8 h), à raffiner en plan.
