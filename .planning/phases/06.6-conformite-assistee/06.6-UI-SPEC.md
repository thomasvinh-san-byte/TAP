## 1. Portée de cet UI-SPEC

Pipeline GSD étape 2/5. Input : `06.6-CONTEXT.md` (PR #157, décisions D-01..D-13).

Phase 06.6 a une **vraie surface UI**. La pièce maîtresse est l'**écran de revue** du pré-remplissage du registre des traitements. Tout le reste gravite autour : un déclencheur sur l'état vide, le même pattern décliné pour le DPA et la DPIA, et de simples textes d'aide pour les pages vides par nature.

La décision **D-01** structure tout cet UI-SPEC — les 6 pages legal ne reçoivent pas le même traitement :

| Page | Nature | Surface UI 06.6 |
|---|---|---|
| **registre** | TAP connaît ses traitements | Déclencheur état vide (S1) + **écran de revue** (S2) + contenu des 6 entrées (S3) |
| **dpa** | TAP connaît ses sous-traitants techniques | Déclencheur + écran de revue des fiches (S4) |
| **dpia** | Structure connue, verdict de risque inconnu | Déclencheur + trame squelette (S5) |
| **breaches** | Vide = aucune fuite = normal | Aide contextuelle — texte d'état vide (S6) |
| **requests** | Vide = aucune demande = normal | Aide contextuelle — texte d'état vide (S6) |
| **dpo** | Le dirigeant désigne la personne | `DpoForm` déjà existant — au plus, état vide explicite (S6) |

**Règle de spec absolue :** breaches / requests / dpo n'ont **pas** d'écran de revue ni de pré-remplissage de données. Ne pas leur en inventer.

## 2. Référence industrie

Les outils de conformité 2026 fournissent des **registres des traitements (RoPA) pré-remplis** : modèles d'activités de traitement courantes du secteur, à relire et personnaliser. Le principe constant : le modèle est un **point de départ**, présenté comme tel, jamais comme une conformité finie. L'utilisateur valide entrée par entrée avant que quoi que ce soit n'entre dans son registre officiel.

→ **Application TAP** : l'écran de revue présente les entrées-types d'un transport sanitaire, le dirigeant les relit/ajuste/écarte, et seules les entrées validées sont insérées (D-02b). Le disclaimer de non-certification (D-07) matérialise « point de départ, pas produit fini ».

## 3. Surface 1 — Déclencheur sur l'état vide du registre

Page `/admin/legal/registre`. L'état vide actuel (`registre-list.client.tsx`, `entries.length === 0`) affiche une boîte pointillée « Aucune entrée au registre » + bouton « Créer la première entrée ». Cet état vide est **enrichi** d'un bloc d'amorçage du pré-remplissage.

### Wireframe ASCII

```
┌──────────────────────────────────────────────────────────────┐
│ Registre des traitements                  [Exporter PDF]  [+] │
│ Recensez quelles données patients vous utilisez et pourquoi.  │
│                                                                │
│ ┌────────────────────────────────────────────────────────┐   │
│ │                  (icône Lucide FileText)                │   │
│ │   Votre registre est vide.                              │   │
│ │   Un transport sanitaire a des traitements de données   │   │
│ │   très prévisibles. TAP peut vous proposer un brouillon │   │
│ │   des entrées types — à relire et adapter.              │   │
│ │                                                          │   │
│ │      [ Pré-remplir avec les traitements types ]  ◀ primaire │
│ │      [ Créer une entrée manuellement ]           ◀ secondaire│
│ └────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

- **Visible uniquement si 0 entrée** (D-09). Dès qu'une entrée existe, l'état vide — donc tout ce bloc — disparaît, remplacé par la table. Idempotence par conception : aucune logique anti-doublon nécessaire.
- Bouton primaire « Pré-remplir avec les traitements types » → ouvre l'écran de revue (S2).
- Bouton secondaire « Créer une entrée manuellement » → conserve le `RegistreDrawer` existant inchangé.
- Le bouton « Nouvelle entrée » du header de page (`page.tsx`) reste pour la création unitaire ; il n'est pas un déclencheur de pré-remplissage.

## 4. Surface 2 — Écran de revue du registre (LE CŒUR)

Déclenché par le bouton « Pré-remplir ». Présente les 6 entrées-types (S3) dans des **cartes-formulaires éditables**, chacune incluable ou écartable. Seules les entrées cochées et valides sont insérées (D-02b). Aucune ligne n'est écrite tant que le dirigeant n'a pas confirmé.

**Forme retenue : page dédiée** `/admin/legal/registre/pre-remplir` (pas un `Sheet` 400 px — six formulaires complets y seraient à l'étroit). Cohérent avec le pattern admin pleine page (`/admin/tarifs`).

### Wireframe ASCII

```
┌──────────────────────────────────────────────────────────────┐
│ ← Retour au registre                                          │
│ Pré-remplir le registre des traitements                       │
│                                                                │
│ ┌─ ⚠ À lire avant d'insérer ──────────────────────────────┐  │
│ │ Ces entrées sont des suggestions adaptées au transport   │  │
│ │ sanitaire. Vérifiez et personnalisez chacune selon votre │  │
│ │ activité réelle. Vous restez responsable de leur         │  │
│ │ exactitude et de leur mise à jour. Ceci ne constitue pas │  │
│ │ un conseil juridique.                                     │  │
│ └───────────────────────────────────────────────────────────┘ │
│                                                                │
│ 6 entrées proposées — décochez celles à ne pas insérer.       │
│                                                                │
│ ┌─ ☑  1 · Planification et exécution des courses ─────────┐  │
│ │ Finalité       [ Planifier et exécuter les courses de…] │  │
│ │ Base légale    [ Contrat                            ▾ ] │  │
│ │ Catégories     [ identité, coordonnées, adresses      ] │  │
│ │ Personnes      [ patients                             ] │  │

│ │ Mesures sécu.  [ RLS multi-tenant, accès par rôle, …  ] │  │
│ │ ☐ Transfert international hors UE                        │  │
│ └───────────────────────────────────────────────────────────┘ │
│ ┌─ ☑  2 · Facturation CGSS (tiers payant) ────────────────┐  │
│ │ … mêmes champs, pré-remplis (voir §5) …                  │  │
│ └───────────────────────────────────────────────────────────┘ │
│ ┌─ ☑  3 · Gestion des chauffeurs et affectations ─────────┐  │
│ ┌─ ☑  4 · Données de santé patients (TPMR, dialyse) ──────┐  │
│ ┌─ ☑  5 · Géolocalisation et adresses ────────────────────┐  │
│ ┌─ ☑  6 · Consentement cookies (site public) ─────────────┐  │
│                                                                │
│            [ Annuler ]      [ Insérer les 6 entrées cochées ] │
└──────────────────────────────────────────────────────────────┘
```

### Comportement

- **Disclaimer D-07** : bandeau en tête, **avant** les cartes, lu avant toute action. C'est le moment du transfert de responsabilité. Ton sobre (icône `AlertTriangle`, `text-muted-foreground`, fond `muted`) — un avertissement, pas une alarme rouge.
- **Cartes** : une par entrée-type. En-tête de carte = case à cocher « inclure » + numéro + intitulé court. Cochée par défaut. Décocher griser/réduire la carte (champs non soumis).
- **Champs** : exactement ceux du registre — `purpose`, `legal_basis` (select des 6 valeurs enum), `data_categories`, `data_subjects`, `recipients`, `retention_period_days` (number), `security_measures` (textarea), `international_transfer` (checkbox). Tous **pré-remplis** avec le contenu-type (S3) et **tous éditables**. Réutiliser le jeu de champs de `registre-drawer.client.tsx` — voir §8 (extraction en fragment partagé `RegistreFields`).
- **Bouton de confirmation** : libellé dynamique « Insérer les N entrées cochées » (N = nombre de cartes cochées ; désactivé si N = 0).
- **Insertion** : seules les entrées cochées et valides sont écrites dans `data_processing_register` (boucle ou variante batch sur `createDataProcessingRegisterAction` — à cadrer au plan). Les entrées décochées ne sont **jamais** écrites (D-02b — le registre est append-only, une ligne insérée par erreur ne se supprime pas).
- **Succès** : redirection vers `/admin/legal/registre` désormais peuplé. Le déclencheur S1 a disparu (D-09).
- **Pas de flag « suggéré »** (D-08) : les entrées insérées sont des lignes de registre normales, indistinguables d'une saisie manuelle — le dirigeant les a validées.

## 5. Surface 3 — Contenu des 6 entrées-types du registre

Contenu rédactionnel **cadré ici**. Les durées de conservation exactes et la condition précise de l'art. 9-2 RGPD seront affinées au plan/execute sur références publiques **CNIL / CNAM** (D-13). TAP ne certifie pas — ce sont des suggestions à valider.

| # | Finalité (`purpose`) | Base légale (`legal_basis`) | Catégories de données | Personnes concernées | Destinataires | Conservation (ébauche) | Mesures de sécurité |
|---|---|---|---|---|---|---|---|
| 1 | Planifier et exécuter les courses de transport des patients | `contrat` | identité, coordonnées, adresses de prise en charge et destination, informations de mobilité | patients | régulateur, chauffeur affecté | ~3 ans après la dernière course | RLS multi-tenant, accès authentifié par rôle, journalisation `audit_logs` |
| 2 | Facturer les courses en tiers payant CGSS et tenir la comptabilité | `obligation_legale` | identité, NIR, montants, prescriptions de transport | patients | CGSS, expert-comptable | ~10 ans (obligation comptable) | NIR chiffré AES-256-GCM (clé hors base), RLS, `audit_logs` |
| 3 | Gérer les chauffeurs et leurs affectations aux courses | `contrat` | identité, coordonnées, permis de conduire, carte professionnelle, affectations | chauffeurs (salariés) | dirigeant, régulateur | durée du contrat + ~5 ans | RLS, accès dirigeant/régulateur, `audit_logs` |
| 4 | Adapter le transport aux besoins de santé du patient (TPMR, dialyse, mobilité réduite) | `mission_interet_public` | données de santé liées à la mobilité, notes opérationnelles médicales | patients | régulateur, chauffeur affecté (besoin d'en connaître) | ~3 ans après la dernière course | notes médicales chiffrées applicatif, RLS, accès restreint, `audit_logs` |
| 5 | Géolocaliser le véhicule pendant le service et gérer les adresses | `contrat` | adresses, position géographique du véhicule pendant le service | patients, chauffeurs | régulateur | 90 jours en base chaude puis purge | capture uniquement pendant le service, purge automatique 90 j, RLS |
| 6 | Recueillir et tracer le consentement aux cookies du site public | `consentement` | choix de consentement, hash de session, hash user-agent | visiteurs du site public | aucun (usage interne) | ~6 à 13 mois (preuve du consentement) | hash (pas d'identifiant direct), accès `service_role` uniquement |

**Notes de spec :**
- Entrée 4 — la base légale est `mission_interet_public` ; la **condition de l'art. 9-2** (catégorie particulière de données de santé) sera précisée au plan. Le champ `legal_basis` ne porte que la base art. 6 — la condition art. 9 relève du texte de `purpose` / `security_measures` ou d'une note. À cadrer au plan, sans verdict définitif de TAP.
- Entrées 1, 3, 5 — `international_transfer = false` ; entrées 2, 4, 6 — `false` également (sous-traitants techniques en UE ; le statut HDS est traité Phase 06.5). Le champ reste éditable.
- Le champ `international_transfer_safeguards` (présent au schéma, absent du `registre-drawer` actuel) reste hors périmètre tant qu'aucune entrée n'a `international_transfer = true`.
- Aucune de ces entrées ne contient de nom propre de personne (NFR-001 respecté — ce sont des descriptions de traitements).

```
│ ← Retour aux DPA                                              │
│ Pré-remplir les fiches sous-traitants                         │
│                                                                │

│                                                                │
│ ┌─ ☑  Supabase ────────────────────────────────────────────┐ │
│ │ Sous-traitant   [ Supabase                            ]  │ │
│ │ Rôle            [ Hébergement base de données, Auth,  ]  │ │
│ │                 [ Storage                             ]  │ │
│ │ Version DPA     [ à compléter                         ]  │ │
│ │ Date signature  [ ___/___/____ ]  ◀ OBLIGATOIRE — à vous │ │
│ │ Notes           [ Sous-traitant technique. Joindre le ]  │ │
│ │                 [ DPA signé.                          ]  │ │
│ └───────────────────────────────────────────────────────────┘ │
│ ┌─ ☑  Vercel ──────────────────────────────────────────────┐ │
│ │ … Hébergement de l'application front …                    │ │
│ └───────────────────────────────────────────────────────────┘ │
│                                                                │
│            [ Annuler ]      [ Insérer les fiches cochées ]    │
└──────────────────────────────────────────────────────────────┘
```

- Champs pré-saisis : `subprocessor_name`, `subprocessor_role`, `notes`. `dpa_version` laissé à compléter.
- **`signed_at` est `NOT NULL`** au schéma — le champ « Date de signature » est **vide, obligatoire, mis en évidence** : le dirigeant le saisit lui-même. TAP **décrit** la fiche, ne **valide pas** le contrat (D-04 / verrou V6). L'insertion d'une fiche cochée échoue si sa date est vide — message sous le champ.
- `dpa_document_url` (upload du DPA signé) : optionnel, hors périmètre de pré-remplissage — saisi plus tard via le formulaire DPA normal.
- Le fournisseur **SMS n'est pas listé** (différé — ADR-004).
- Insertion via la Server Action DPA existante (boucle/batch — plan).

## 8. Surface 6 — Aide contextuelle breaches / requests / dpo (léger)

**Aucun pré-remplissage de données, aucun écran de revue.** Vides par nature = situation normale et souhaitable (D-06 / verrou V8). Seul l'état vide reçoit un court texte guide, dans le ton pédagogique du hub `/admin/legal`.

- **breaches** (état vide) : « Cette page restera vide tant qu'aucune donnée patient n'aura fuité, été perdue ou volée — c'est une bonne nouvelle. En cas d'incident, déclarez-le ici : vous avez 72 h pour notifier la CNIL, et un compte à rebours vous accompagne. »
- **requests** (état vide) : « Vous suivrez ici les demandes RGPD de vos patients (accès, rectification, effacement…). Une page vide signifie qu'aucune demande n'est en cours. Vous disposez de 30 jours pour répondre à chaque demande. »
- **dpo** : la page est **déjà** un formulaire guidé (`DpoForm`, champs `organizations.dpo_*`). Ne pas le refaire (verrou V8). Au plus, un état vide légèrement plus explicite si les champs ne sont pas renseignés (« Désignez la personne à contacter pour les questions de données — ses coordonnées s'afficheront sur votre site public. »). Optionnel ; aucune nouvelle Server Action.

|---|---|---|

## 11. Design tokens

Cohérent avec `/admin/legal/*`, `/admin/tarifs`, UI-PATTERNS.md (DEC-034).

- **Spacing NFR-003** : `space-y-24` entre zones, `space-y-16` entre cartes, `p-16` carte, `space-y-4` label/champ, `gap-8` cases à cocher. Échelle 4/8/12/16/24/32/48/64 uniquement.
- **Typographie** : titre page `text-2xl font-semibold tracking-tight` ; intitulé de carte `text-sm font-semibold` ; texte d'aide / disclaimer `text-sm text-muted-foreground`.
- **Couleurs sémantiques** : disclaimer = `AlertTriangle` + `text-muted-foreground` sur fond `muted` (avertissement sobre, pas de rouge — ce n'est pas une erreur) ; champ obligatoire manquant = `text-destructive` ; carte décochée = opacité réduite.
- **Icônes Lucide** (famille unique) : `FileText` (registre / état vide), `Sparkles` ou `ListPlus` (action pré-remplir), `AlertTriangle` (disclaimer), `FileSignature` (DPA), `ClipboardCheck` (DPIA). Style ligne fine, jamais mixé.
- **Champs** : réutiliser `Input`, `Label`, `select`, `textarea`, `Button` shadcn déjà employés par `registre-drawer` — aucune nouvelle primitive.
- **Animations NFR-004** : aucune ; états `pending` natifs via `useTransition`. Pas de framer-motion.

## 12. Anti-patterns (interdits)

- ❌ INSERT direct des suggestions sans écran de revue — le registre est append-only, une ligne erronée ne se supprime pas (D-02b / verrou V2).
- ❌ Réinventer les champs du formulaire registre — réutiliser `registre-drawer` via `RegistreFields` (verrou V4).
- ❌ Omettre le disclaimer de non-certification, ou le placer après les cartes — il doit être en tête, avant toute action (D-07 / verrou V3).
- ❌ Pré-remplir `dpa_record.signed_at` à la place du dirigeant — TAP décrit, ne valide pas le contrat (D-04 / verrou V6).
- ❌ Faire émettre un verdict de risque par la trame DPIA — `risks_identified` / `mitigations` restent vides (D-05 / verrou V7).
- ❌ Pré-remplir breaches ou requests avec des incidents / demandes fictifs (D-06 / verrou V8).
- ❌ Refaire le `DpoForm` — il existe déjà (verrou V8).
- ❌ Persister un flag « suggéré » sur les entrées insérées (D-08 / verrou V9).
- ❌ Afficher le bouton « Pré-remplir » quand le registre n'est pas vide (D-09 / verrou V5).
- ❌ Présenter le pré-remplissage comme une conformité certifiée / garantie (verrou V3).
- ❌ framer-motion ou toute nouvelle lib UI (NFR-004 / verrou V10).
