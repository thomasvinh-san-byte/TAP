## Pourquoi (couplage 06.12)

`solveLocal` (Phase 06.12) est opérationnel mais affamé : `packages/optimizer-client/src/transform.ts` (l.107-116) exclut toute course où `pickup_lat/lng` OU `dropoff_lat/lng` est `null` (`reason: 'no_coordinates'`).

**Les courses récurrentes (dialyse = transport le plus mutualisable) arrivent SANS coords → exclues → on rate l'optimisation là où le gain est maximal.** 06.19 nourrit 06.12 ; elle ne touche PAS l'optimisation elle-même.

- **Pas de migration nécessaire** : la table `ride_recurrences` (migration `20260519000001_ride_recurrences.sql`) a DÉJÀ les 6 colonnes `pickup_lat/lng/citycode` + `dropoff_*` (numeric(10,7), nullables, lignes 13-19). Le trou est purement applicatif.
- **Trou applicatif identifié** : `patients/actions/recurrences.ts` schéma Zod (l.44-46) + INSERT (l.80) ont `pickup_address` / `dropoff_address` mais ignorent les colonnes coords existantes.
- **Création express déjà géocodée OK** (référence : `rideExpressInputSchema` + `AddressOrPOIPicker`).
- **`AddressOrPOIPicker`** : `onSelect(selection: AddressOrPOIPickerSelection)` remonte `lat/lng/citycode` (l.109-127). `lib/geocoding/ban.ts` exporte `geocodeBanSearch`.

### D-02 — Filet de géocodage serveur

Helper partagé `geocodeIfMissing` dans `apps/web/src/lib/geocoding/geocode-safety-net.ts`. Consommé par :
- `createRideAction` (`courses/actions/create.ts`).
- `createRecurrenceAction` + `updateRecurrenceAction` (`patients/actions/recurrences.ts`).

Si `pickup_lat` NULL mais `pickup_address` présent → appel serveur `geocodeBanSearch(pickup_address, { limit: 1 })`, persister `lat/lng/citycode`. Idem dropoff.

**Idempotent** : court-circuit si coords déjà fournies par le picker.
**Non bloquant** : si BAN indisponible ou 0 résultat → coords restent NULL, la course est créée quand même (exclue de l'optim mais jamais perdue).
