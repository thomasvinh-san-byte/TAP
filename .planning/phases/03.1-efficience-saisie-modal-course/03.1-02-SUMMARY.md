# Phase 03.1 Plan 02 : chips date rapides DateFreeformField (A3) — Summary

Extension du composant `DateFreeformField` avec 4 chips inline de
sélection rapide (« demain 8h », « demain 14h », « lundi 9h »,
« dans 30 minutes »). Pattern Linear chips plates, pas de Button shadcn.
Le click chip remplit l'input et déclenche le parse chrono.fr exactement
comme une saisie manuelle.

## Tasks exécutées

### Task 1 — Extension `DateFreeformField` (commit `f6a4388`)

Modifications dans
`apps/web/src/app/(app)/courses/_components/ride-express-form-fields.client.tsx` :

- Ajout constante module-level `DATE_CHIPS` (4 valeurs verbatim D-A3-2,
  ordre figé, `as const`).
- Ajout de la prop `disabled?: boolean` (passe-plat HTML + condition de
  masquage chips, D-A3-5).
- Ajout de la prop `rideId?: string` (condition de masquage chips en
  mode édition, D-A3-5).
- Ajout du handler `handleChipClick(label: string): void` qui :
  1. appelle `onChange(label)` (propagation au state parent du modal),
  2. appelle `parseFreeformDate(label)` (chrono.fr `forwardDate: true`),
  3. en cas de succès, `onError(null)` puis `onParsed(parsed.iso)`,
  4. en cas d'échec, `onError(parsed.reason)`.
- Rendu conditionnel via `showChips = !disabled && !rideId` : si vrai,
  un `<div className="flex flex-wrap gap-8 mt-8">` contient un
  `<button type="button">` par chip avec classes D-A3-3 collées
  verbatim. Sinon, JSX `null` (chips non-rendues, pas `aria-hidden`).
- Le `<Input>` reçoit aussi `disabled={disabled}` pour cohérence
  comportementale (un parent qui passe `disabled` désactive l'input
  ET masque les chips).

Pas d'icône Lucide. Pas de Tooltip. Pas de toast. Pas d'animation
autre que `transition-colors` héritée. `type="button"` sur chaque chip
pour neutraliser tout submit du form parent.

### Anomalie Wave 0 signalée (sans fix Plan 02, scope hors `files_modified`)

**Découverte** : Le prompt de spawn et le PLAN.md affirmaient que Wave 0
avait déjà câblé `rideId={props.rideId}` à `<DateFreeformField />`
dans `ride-express-modal.client.tsx`. Le SUMMARY Wave 0 confirme
que la prop `rideId?: string` a bien été ajoutée à la **signature**
du composant `DateFreeformField` (Task 3 Wave 0), mais sur l'état du
worktree avant Plan 02, ce câblage n'a pas été appliqué :

- `ride-express-modal.client.tsx` ligne 315-321 : appel à
  `<DateFreeformField>` SANS prop `rideId`.
- `ride-express-form-fields.client.tsx` (avant Plan 02) : signature
  `DateFreeformField` sans `rideId?` (worktree state = pré-Wave 0
  propagation prop).

**Action Plan 02** (per `<task type="auto">` step 5 du plan) : ajout
local de la prop `rideId?: string` (et `disabled?: boolean` au passage
pour cohérence des conditions de masquage D-A3-5) à la signature.
**Sans modification du modal**, conformément au scope `files_modified`
imposé (checker B3 Option A).

**Conséquence fonctionnelle** : en mode édition course (un clic sur une
course existante du tableau), le modal s'ouvre avec un `rideId` interne
non propagé à `DateFreeformField` — les chips restent donc visibles.
Le critère D-A3-5 « chips masquées en mode édition » n'est PAS satisfait
sur la preview tant que le modal n'aura pas été patché en aval.

**Recommandation** : Plan 03 (banner doublon B3) modifie de toutes
façons le modal. Ajouter une-ligne dans le commit de Plan 03 :
```diff
  <DateFreeformField

    error={dateError ?? fieldErrors.scheduled_at ?? null}
```
