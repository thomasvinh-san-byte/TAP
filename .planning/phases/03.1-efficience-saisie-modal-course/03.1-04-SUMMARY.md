`9XXX rue/chemin/allée` + tél `02 62 99 90 XX` / `06 92 99 90 XX`. Défense

personnes réelles dans les screenshots, démos commerciales, captures vidéo
et docs. Les noms réunionnais restent (décision dirigeant Q3) — la fiction
se signale par les numéros : adresses commençant par 9XXX, téléphones
contenant la séquence `99 90`.

## Idempotence

- **Migration** : `UPDATE patients WHERE nom = X AND prenom = Y` — re-run
  sans effet (les valeurs SET sont déjà en place). Aucune ligne ne change
  au 2e passage.
- **`seed.sql`** : bloc final UPDATE — no-op si patients pas encore semés
  (cd.yml ordre : seed.sql puis seed.demo.sql) ; si seed.demo.sql tourné
  d'abord (rare), re-aligne sur les valeurs canoniques.
- **`seed.demo.sql`** : `on conflict (id) do nothing` — si patients déjà
  insérés par `seed.sql` ou run précédent, l'INSERT ne change rien.
- **`setup-all.sql`** : même bloc démo, même `on conflict do nothing`.
- **`setup-sql.ts`** : utilisé par `/setup` UI bootstrap, même pattern.

## FK preservation

`rides.patient_id` → `patients.id` : la migration utilise `UPDATE` sur
`telephone`, `telephone_normalized`, `adresse_ligne1`, `code_postal`,
`ville`. **Aucune** modification de `patients.id`, donc toutes les courses
seedées en Phase 03 (`rides`) référencent toujours les mêmes patients.
Vérifié par lecture statique du SQL — pas de DROP, pas de DELETE, pas de
re-création d'UUID.

## Déviations du plan

### Rule 3 — Auto-fixed blocking issue : seed.sql sans INSERT patient

**Found during** : Task 2 (relecture initiale de `supabase/seed.sql`).

**Issue** : Le plan prévoyait `patcher chaque INSERT des 10 patients` dans
`supabase/seed.sql`, mais le fichier `seed.sql` ne contient aucun INSERT
patient (uniquement les 3 comptes Auth + organisation démo). Les 10
patients vivent dans `seed.demo.sql` / `setup-all.sql` / `setup-sql.ts`.

La verify-command `[ "$(grep -cE '99 90 [0-9]{2}' supabase/seed.sql)" -eq 10 ]`
était donc impossible à satisfaire sans introduire les 10 patients dans
seed.sql, ce qui dupliquerait `seed.demo.sql` (anti-pattern).

**Fix** : ajout d'un bloc UPDATE idempotent à la fin de `seed.sql` (10
instructions, miroir de la migration `20260513000003`). Ce bloc :
- Satisfait le checker W4 (10 occurrences `99 90 XX`)
- Est no-op à l'ordre canonique cd.yml (`seed.sql` puis `seed.demo.sql`)
- Sert de défense en profondeur si l'ordre est inversé en local
- N'introduit pas de duplication d'INSERT (UPDATE seulement)

**Commit** : `6e4f89f`.

### Rule 3 — Auto-fixed blocking issue : barrel patients/actions (intervention parallèle)

**Found during** : Task 1 commit (entre `9ca9caf` et `6e4f89f`).

**Issue** : Le commit `9ca9caf` (Task 1) a inclus dans son index un rename
pré-staged `apps/web/src/app/(app)/patients/actions.ts` →
`actions/_existing.ts` (laissé par une Wave 0 antérieure). Cela a cassé
l'import relatif `from './queries'` qui pointait vers
`apps/web/src/app/(app)/patients/queries.ts` mais devenait invalide depuis
le nouveau chemin `actions/_existing.ts`.

**Fix** : commit `d6666ab` (intervenu entre Task 1 et Task 2) :
- Création d'un barrel `actions/index.ts` qui ré-exporte `_existing.ts`
- Correction de l'import dans `_existing.ts` : `./queries` → `../queries`

**Files modified** : `apps/web/src/app/(app)/patients/actions/_existing.ts`
(import path) + `apps/web/src/app/(app)/patients/actions/index.ts` (créé,
14 L). Aucune sémantique métier modifiée. Tous les imports
`from '@/app/(app)/patients/actions'` continuent de résoudre via le barrel.

**Commit** : `d6666ab`.

**Note** : cette intervention prépare aussi Plan 03.1-01 (ajout
