<domain>
## Phase Boundary

**Goal fonctionnel** : Réduire les frictions de saisie de course via 3 patterns
issus de Doctolib (quick booking), Uber Health (NEMT dashboard) et Onfleet
(task validation). Ajouter une couche d'anonymisation défensive sur les
patients seedés démo (NFR-001 défense en profondeur).

**Goal UX** : Sensation Linear/Stripe — chips date élégantes (pas variant
Button épais), banner doublon amber non-destructif (pattern Linear warning),
zéro toast intrusif sur les smart defaults (silent prefill).

**Effort total estimé** : 6h30 - 7h30 (4 plans atomiques).

**Critère de fin** :
- A2 : sélectionner un patient avec course existante → mode/urgence
  pré-remplis silencieusement (si encore aux défauts V1).
- A3 : cliquer une chip date → champ rempli ET parse OK (chrono.fr-compatible).
- B3 : créer un doublon ±30 min même patient → banner amber + bouton « Créer
  quand même » qui bypass la vérification.
- SEED : tous les patients démo affichent tél `02 62 99 90 XX` ou
  `06 92 99 90 XX` + adresse `9XXX rue/chemin/allée`.
</domain>

<decisions>
## Implementation Decisions

### Smart defaults mode + urgence depuis dernière course (A2)

- **D-A2-1** : Pré-remplissage **silencieux**. Aucun toast, aucune animation
  focus. La régulatrice voit juste les valeurs déjà choisies — comportement
  attendu pour un pattern « smart defaults » (cf. Doctolib quick booking).
- **D-A2-2** : Nouvelle query `getPatientRideDefaults` dans
  `apps/web/src/app/(app)/patients/queries.ts` (+20L, fichier reste ≤ 300L).
  Filtre statut ∈ `{validee, assignee, en_cours, terminee}` (exclut annulee_*).
  `order by scheduled_at desc limit 1`. Retourne `{ transport_mode, urgency }`
  ou `null` si aucune course passée.
- **D-A2-3** : Exposée via `getPatientRideDefaultsAction` dans
  `apps/web/src/app/(app)/patients/actions.ts` (+5L, export action).
  Appelée depuis le callback de sélection patient dans
  `apps/web/src/app/(app)/courses/_components/ride-express-modal.client.tsx`,
  **après** l'`updateField('patient_id', id)`.
- **D-A2-4** : Écrase `transport_mode` et `urgency` UNIQUEMENT si encore aux
  défauts V1 (`mode === 'taxi_conventionne'` ET `urgency === 'programmee'`).
  Ne touche pas si la régulatrice a déjà changé les valeurs manuellement.
- **D-A2-5** : Désactivé en mode édition (`props.rideId` présent) — l'édition
  charge déjà les valeurs réelles via `useRidePrefill`.

### Chips date rapides (A3)

- **D-A3-1** : Chips **inline** dans `DateFreeformField`
  (`ride-express-form-fields.client.tsx`), pas un sous-composant séparé.
  Le fichier reste ≤ 80L pour la section `DateFreeformField`.
- **D-A3-2** : 4 valeurs (toutes testées chrono.fr-compatibles avec
  `forwardDate: true`) :
  - `'demain 8h'`
  - `'demain 14h'`
  - `'lundi 9h'`
  - `'dans 30 minutes'`
- **D-A3-3** : Style bouton chip :
  ```
  px-12 py-8 rounded-full text-xs border border-input bg-background
  hover:bg-muted text-muted-foreground transition-colors
  ```
  PAS variant Button shadcn (trop épais visuellement à 40px h pour ce
  contexte secondaire — référence : chips Linear sous datepicker).
- **D-A3-4** : Click chip → `onChange(label)` + `onParsed(iso)` synchrones
  (déclenche le parse comme une saisie manuelle). Pas de side-effect masqué.
- **D-A3-5** : Masqués si `props.disabled === true` OU `props.rideId` présent
  (mode édition course). Évite confusion : l'utilisateur ne doit pas avoir
  de raccourcis « rapides » qui rebooteraient le state.

### Détection doublon non-bloquante (B3)

- **D-B3-1** : Server Action `checkDuplicateRideAction` dans nouveau fichier
  `apps/web/src/app/(app)/courses/actions/check-duplicate.ts` (~60L).
  Export dans `apps/web/src/app/(app)/courses/actions/index.ts` (+1L).
- **D-B3-2** : Critères de détection (V1, taxonomie viendra via observation) :
  - Même `patient_id`
  - `scheduled_at` dans fenêtre ±30 min
  - `archive = false`
  - `status` ∈ `{validee, assignee, en_cours, terminee}` (exclut annulee_*)
  - Exclut la course elle-même si on est en mode édition (filter sur
    `id != currentRideId` quand applicable)
- **D-B3-3** : Banner **non-bloquant** :
  - State local `duplicateConfirmed: boolean` séparé du state `fieldErrors`
  - Au submit : si check renvoie ≥ 1 doublon ET `!duplicateConfirmed` →
    afficher banner + return early (pas de création)
  - Bouton « Créer quand même » → `setDuplicateConfirmed(true)` puis
    re-call `handleSubmit()`
- **D-B3-4** : Style banner amber (référence Linear warning, non-destructif) :
  ```
  rounded-md border border-amber-500/50 bg-amber-50
  dark:bg-amber-950/30 px-16 py-12 space-y-8
  ```
  Contenu : titre « Course en doublon détectée », 1-3 lignes décrivant les
  doublons trouvés (heure prévue + statut), 2 boutons (« Annuler » outline,
  « Créer quand même » destructive variant).
- **D-B3-5** : Reset `duplicateConfirmed = false` après création réussie
  (côté handleSubmit success branch — avant `props.onClose()`).
