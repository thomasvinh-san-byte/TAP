# Phase 03.1 Plan 03 : détection doublon non-bloquante avec banner amber (B3) — Summary

Server Action `checkDuplicateRideAction` (lecture seule ±30 min même
patient) câblée dans le modal saisie express via le hook
`useDuplicateCheck`. Le composant `DuplicateBanner` scaffold Wave 0 est
désormais instancié juste avant `<DialogFooter>` ; flux non-bloquant avec
bouton « Créer quand même » qui bypasse la vérification une fois (D-B3-1
à D-B3-5).

## Tasks exécutées

### Task 1 — Server Action `checkDuplicateRideAction` (commit `bd64fc7`)

Nouveau fichier `apps/web/src/app/(app)/courses/actions/check-duplicate.ts`
(80 L, ≤ 100 L cible) :

- `'use server'` + import `getAuthContext` + whitelist
  `REGULATEUR_OR_DIRIGEANT` (defense in depth, doublé du RLS Postgres).
- Schéma zod : `patientId: uuid()`, `scheduledAt: datetime()`,
  `excludeRideId: uuid().optional()`.
- Calcul fenêtre `[scheduledAt − 30 min, scheduledAt + 30 min]` via
  `new Date(...).getTime() ± 30 * 60 * 1000` puis `.toISOString()`.
- Query Supabase filtre : `eq(patient_id) + eq(archive,false) +
  in(status, ['validee','assignee','en_cours','terminee']) +
  gte(scheduled_at,fromIso) + lte(scheduled_at,toIso)` ; ajout
  conditionnel `.neq('id', excludeRideId)` en mode édition.
- Retour `{ data: DuplicateRide[] }` ou `{ error: '...' }`. Aucune
  branche d'erreur ne fuit de message Postgres — toutes les erreurs
  sont reformulées FR (« Paramètres invalides. », « Session expirée. »,
  « Accès non autorisé. », « Vérification doublon indisponible. »).
- Pas de `revalidatePath` (lecture seule).

Re-export ajouté dans `actions/index.ts` (+1 L).

### Task 2 — Hook `useDuplicateCheck` + instanciation `<DuplicateBanner>` (commit `3e0e5b0`)

**Mitigation Risk Hint « budget modal »** : le plan prévoyait ~25-35 L
d'ajouts dans le modal. Première itération à 324 L > 300 L plafond
CLAUDE.md § 11. Extraction d'un hook `useDuplicateCheck` (72 L) qui
encapsule state + parse + call action, ramenant le modal à **297 L**
(marge 3 L sous le plafond). Anti-pattern « refacto opportuniste »
respecté : aucune autre modification structurelle.

Nouveau fichier
`apps/web/src/app/(app)/courses/_components/use-duplicate-check.client.ts`
expose `{ duplicates, duplicateConfirmed, runCheck, confirm, cancel, reset }` :

- `runCheck(form, excludeRideId)` parse `dateInput` via
  `parseFreeformDate` si `form.scheduled_at` absent, return early si
  `patient_id` ou ISO manquants, appelle `checkDuplicateRideAction`,
  set `duplicates` si ≥ 1, return `true` (caller doit return early).
- `confirm()` set `duplicateConfirmed = true`.
- `cancel()` clear `duplicates` (modal reste ouverte, formulaire intact).
- `reset()` clear les deux states (appelé par `onSuccess`, D-B3-5).

Modifications dans le modal
(`apps/web/src/app/(app)/courses/_components/ride-express-modal.client.tsx`) :

- Imports nettoyés : retrait des `@ts-eslint-disable` Wave 0 sur
  `DuplicateBanner` (désormais instancié) et `STATUS_LABELS_FR` (utilisé
  uniquement par le composant `DuplicateBanner` lui-même, donc import
  retiré du modal — DRY).
- Ajout `const dup = useDuplicateCheck();` à côté des autres `useState`.
- `useRideSubmit({ onSuccess })` enveloppé : `dup.reset()` puis
  `props.onClose()` (D-B3-5 reset AVANT onClose).
- Nouvelle callback `runSubmit(bypass: boolean)` :
  `if (!bypass && await dup.runCheck(form, props.rideId)) return; submit.submit(form);`
- `handleSubmit(e?)` rendu optionnel sur `e` pour permettre re-call
  programmatique ; lit `dup.duplicateConfirmed` du closure courant.
- Instanciation `<DuplicateBanner duplicates={dup.duplicates}
  isPending={submit.isPending} onCancel={dup.cancel} onConfirm={...} />`
  insérée **juste avant `<DialogFooter>`** (UI-SPEC Element 2).
- `onConfirm` : `dup.confirm()` puis `void runSubmit(true)` — bypass
  explicite car le state ne se propage qu'au render suivant (closure
  resolution React, contournement documenté par commentaire inline).

## Walkthrough script (à exécuter sur preview Vercel)

1. Se connecter avec `regulateur@demo.tap` / `demo1234!`.
2. Saisie express (Cmd+Shift+K) → choisir un patient → date « demain 10h »
   → adresses → Créer la course.
3. Re-saisir le même patient → date « demain 10h15 » (fenêtre ±30 min) → Créer.
4. Vérifier l'apparition du banner amber « Course en doublon détectée »
   avec 1 ligne `10:00 — validée` (formatHourFR + STATUS_LABELS_FR).
5. Cliquer « Annuler » → banner disparaît, modal reste ouverte, formulaire intact.
6. Re-cliquer Créer → banner réapparaît (état `duplicateConfirmed` reset après cancel ? non —
   `cancel()` ne reset PAS `duplicateConfirmed`. Si la régulatrice avait
   déjà cliqué « Créer quand même » puis re-ouvert un autre formulaire,
   `reset()` aurait été appelé via `onSuccess`. Ici, après cancel sans
   submit réussi, `duplicateConfirmed` reste à `false` — donc re-Créer
   relance bien le check).
7. Cliquer « Créer quand même » → modal ferme, course créée, toast OK.
   Pendant la transition : les 2 boutons banner sont `disabled` (checker W2).
8. Re-ouvrir Saisie express avec le même patient + 10h30 → banner réapparaît
   (`duplicateConfirmed` reset à la fermeture précédente via `reset()`).
9. Patient SANS course ±30 min → aucun banner, création directe.
10. Mode édition : ouvrir une course existante → submit sans changement →
    aucun banner (la course elle-même exclue via `excludeRideId`).
11. Mode sombre : contraste amber-100 sur amber-950/30 reste lisible.
12. Lecteur d'écran : annonce automatique du titre du banner
    (`role="alert" + aria-live="polite"`, délégué au composant Wave 0).
