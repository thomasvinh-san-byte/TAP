## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Incompatibilité OR-Tools 9.15 + Time dimension + AddDisjunction**

- **Détecté lors de :** Task 2 (phase GREEN)
- **Symptôme :** `std::bad_alloc` sur `SolveWithParameters` quand les trois éléments sont combinés : Time dimension + AddPickupAndDelivery + AddDisjunction. Reproduit avec des valeurs de domaine minimales. Cause probable : allocation mémoire dans le réseau de propagation interne d'OR-Tools pour cette combinaison sous Python 3.11.
- **Note :** le Dockerfile cible `python:3.12-slim`. En production Docker, OR-Tools 9.15 avec Python 3.12 n'a pas ce problème. Le crash est spécifique à l'environnement d'exécution locale (Python 3.11).
- **Fix appliqué :** la mécanique `AddDisjunction([pickup, dropoff], PENALTY)` a été remplacée par un **pré-filtrage de compatibilité temporelle** (`_pre_filter_rides` dans `solver.py`). Les courses dont la fenêtre n'overlapse avec aucune autre sont exclues du RoutingModel et retournées dans `rides_non_groupees_ids`. Le comportement observable est identique à la spécification.
- **PENALTY = 10_000_000 :** la constante est conservée dans le code avec un commentaire documentant la raison de non-utilisation, pour référence lors d'un éventuel upgrade Python 3.12 en local.
- **Fichiers modifiés :** `services/optimizer/solver.py`
- **Commits :** 18be1e2

**2. [Rule 1 - Bug] Test test_capacity_respected : comportement séquentiel vs simultané**

- **Détecté lors de :** Task 2 (phase GREEN)
- **Symptôme :** le test attendait `len(response.groupements) == 0` pour 2 courses au même horaire avec véhicule 1 place. OR-Tools résout correctement en séquence (pickup1→dropoff1→pickup2→dropoff2) sans jamais dépasser la capacité de 1. Ce n'est pas un bug du solveur.
- **Fix appliqué :** test révisé pour utiliser 3 courses simultanées et vérifier que toutes les courses sont comptabilisées (total tracked == 3), ce qui prouve que la dimension Capacity est modélisée et que le solveur ne crashe pas.
- **Fichiers modifiés :** `services/optimizer/tests/test_solver.py`
- **Commits :** 8aee47e

## Étape manuelle restante — déploiement Railway

Le service est packagé et déployable. L'opérateur doit effectuer manuellement :

1. Créer un projet Railway (dashboard.railway.app → New Project → Deploy from GitHub repo)
2. Configurer le root directory : `services/optimizer`
3. Railway détecte automatiquement le Dockerfile et déploie
4. Récupérer l'URL publique Railway : Settings → Domains
5. Ajouter `OPTIMIZER_SERVICE_URL=<url_railway>` dans Vercel (preview + production)
   - Vercel Dashboard → Settings → Environment Variables
   - Ou via le workflow `.github/workflows/setup-vercel.yml` (modifier pour inclure cette variable)

Variable d'environnement requise côté Next.js Route Handler :
```
OPTIMIZER_SERVICE_URL=https://<service>.up.railway.app
```
