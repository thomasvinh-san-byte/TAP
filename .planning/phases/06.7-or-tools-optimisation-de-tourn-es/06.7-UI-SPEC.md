# Phase 06.7 — UI Design Contract : OR-Tools optimisation de tournées

> Contrat visuel et d'interaction pour la phase 06.7 — écran d'optimisation de tournées (propose/dispose).
> Généré par gsd-ui-researcher. Vérifié par gsd-ui-checker avant exécution.
>
> Ce contrat *applique* les décisions D-01..D-21 de `06.7-CONTEXT.md` — il ne les rouvre pas.

## 1. Portée de cet UI-SPEC

Pipeline GSD étape 2/5. Input : `06.7-CONTEXT.md` (décisions D-01..D-21).

Phase 06.7 livre la **vue d'optimisation de tournées** (CDC v2 § 5.11) : un écran régulateur qui présente des propositions de mutualisation et d'ordonnancement de courses, que la régulatrice accepte ou rejette au grain fin. Cet UI-SPEC traduit les décisions du discuss en interface, en appliquant les règles UI/UX du projet (CLAUDE.md §1, §2, §5 + NFR-001..006) comme des contraintes.

### Décisions du CONTEXT qui cadrent l'UI

| # | Décision | Impact UI |
|---|---|---|
| D-01 | Mutualisation + ordonnancement | Chaque proposition = un groupe ordonné de courses compatibles |
| D-02 | Granularité journée entière | Sélecteur de date obligatoire — une seule journée par calcul |
| D-05 | Appel synchrone borné 2-5 s | État de chargement obligatoire (skeleton + message, jamais page blanche) |
| D-10 | Zones Hauts signalées via citycode INSEE | Badge « à vérifier » sur les groupements dont un trajet traverse les Hauts |
| D-14 | Propose / dispose — aucune écriture avant validation | Aucun libellé, aucune surface ne doit laisser croire à une affectation automatique |
| D-15 | Acceptation grain fin + comparatif actuel vs proposé | Vue comparative côte à côte (ou overlay) ; 3 actions par groupement |
| D-16 | Écriture finale via Server Actions existantes | L'UI déclenche seulement ; l'audit est automatique |
| D-17 | Courses exclues explicitement signalées | Surface dédiée « Courses exclues », jamais cachée |
| D-18 | Proposition éphémère | Pas d'état persistant à représenter ; fermeture = discard silencieux |
| D-19 | Exactement 2 indicateurs « estimés » | Taux de mutualisation + km à vide estimés — aucun 3e indicateur |
| D-20 | Aucun indicateur présenté comme terrain | Les 2 indicateurs portent explicitement le mot « estimé » |

**Hors périmètre V1 (rappel) :** affectation automatique chauffeur, ré-optimisation dynamique, OSRM, historique des propositions, OTP terrain, deadhead réel (D-03, D-18, deferred).

## 4. Typographie

Inter uniquement. `tabular-nums` (`font-feature-settings: 'tnum'`) sur tous les chiffres (horaires, distances, pourcentages).

| Rôle | Taille | Graisse | Line-height | Usage |
|---|---|---|---|---|
| Titre de page (h1) | 24 px (`text-2xl`) | 600 (`font-semibold`) | 1.2 | « Optimisation du {date} » |
| Titre de section (h2) | 16 px (`text-base`) | 600 (`font-semibold`) | 1.3 | « Plan actuel », « Plan proposé », « Courses exclues » |
| Titre de groupement (h3) | 14 px (`text-sm`) | 600 (`font-semibold`) | 1.4 | « Groupement N — {N} courses » |
| Corps / étiquette | 14 px (`text-sm`) | 400 (`font-normal`) | 1.5 | Détails de course, justification du groupement |
| Métadonnée / libellé secondaire | 12 px (`text-xs`) | 400 (`font-normal`) | 1.4 | « estimé », source Haversine, note d'exclusion |
| Chiffre indicateur | 24 px (`text-2xl`) | 600 (`font-semibold`) | 1.2 | Taux de mutualisation, km à vide |

Nombre de tailles déclarées : 4 (24, 16, 14, 12 px) + variante chiffre réutilise 24 px — dans la limite de 3-4 tailles prescrites.

Nombre de graisses déclarées : **2** — 400 (`font-normal`) pour le corps et les métadonnées, 600 (`font-semibold`) pour tous les titres et les valeurs d'indicateur. La hiérarchie h2/h3 repose sur la taille (16 px vs 14 px) ; la hiérarchie h3/corps repose sur la graisse (600 vs 400). Aucune graisse intermédiaire (`font-medium` 500) n'est utilisée.

## 7. Surface 1 — Point d'entrée dans le cockpit

La régulatrice lance l'optimisation depuis le cockpit (`/cockpit`), son écran d'accueil par défaut.

### Emplacement du CTA

Bouton « Optimiser la journée » placé dans l'en-tête du cockpit, à droite du titre de date, aux côtés des contrôles existants (filtre, date du jour). Icône Lucide `Sparkles` (ligne fine) + label textuel obligatoire.

```
┌──────────────────────────────────────────────────────────────────┐
│ Cockpit — vendredi 22 mai 2026            [Optimiser la journée] │
│                                                                    │
│ [Aujourd'hui] [filtre statut ▾]                                    │
└──────────────────────────────────────────────────────────────────┘
```

- Bouton : variante `default` (fond `--primary`, texte `--primary-foreground`), hauteur ≥ 44 px, `rounded-md`.
- Le bouton agit sur la journée courante affichée dans le cockpit — pas de sélecteur de date séparé en V1 (D-02 : granularité journée entière ; le cockpit a déjà un sélecteur de date).
- Si la journée n'a aucune course planifiée, le bouton est visible mais déclenche l'état vide (Surface 7b) au lieu d'afficher une proposition.

### État de chargement (2-5 s)

Le clic sur « Optimiser la journée » ouvre une **page dédiée** `/cockpit/optimisation?date={YYYY-MM-DD}` (ou un panneau plein-écran monté par-dessus le cockpit via un `Sheet` côté latéral pleine largeur). Pendant le calcul :

- La page du cockpit reste accessible (navigation non bloquée — D-14).
- L'écran d'optimisation affiche un skeleton avec un message texte « Calcul en cours… cela peut prendre quelques secondes. » (pas de spinner animé — NFR-005).
- Le skeleton reproduit la forme de la vue comparative : deux colonnes avec des blocs gris de hauteur variable.

```
┌─────────────────────────────────────────────────────────────────┐
│ Optimisation du 22/05/2026                                       │
```

### Règles de mise en page

- Deux colonnes de largeur égale (`grid grid-cols-2 gap-24`), séparées par un trait vertical subtil (`border-l border-border`).
- Sur écran < 1024 px : empilement vertical (`grid-cols-1`) — panneau proposé en premier (D-14 : la proposition est l'information principale). Sur cet empilement, la colonne « Plan proposé » réordonnée porte un `aria-label="Plan proposé — affiché en premier"` pour orienter la navigation au lecteur d'écran (ordre DOM ≠ ordre logique).
- Le panneau « Plan actuel » est une liste plate (`<ol>`) des courses de la journée dans leur ordre chronologique, sans interactions — lecture seule.
- Le panneau « Plan proposé » contient les cartes de groupement (Surface 3) + les courses non groupées (libellées « non groupée », fond `bg-background`, sans actions).
- Les courses mises en évidence dans le plan proposé correspondent visuellement aux courses du plan actuel (même code — « Course A », « Course B » — pour le test du flou).
- La bande d'indicateurs (Surface 4) est toujours visible en haut, au-dessus des deux colonnes.
- La section « Courses exclues » (Surface 5) est toujours visible en bas, sous les deux colonnes.
- Le bouton de validation finale est en bas de page, pleine largeur, variante `default` (accent `--primary`).
- Le bouton « Fermer × » (en-tête de la vue comparative) utilise la variante `ghost`, sans accent — l'accent `--primary` reste strictement réservé aux deux seuls CTA déclarés au §5.

## 9. Surface 3 — Anatomie d'un groupement proposé

Composant réutilisable `ProposedGroupCard`. Une carte = un conteneur `rounded-lg border bg-muted/40 p-16` avec effet de survol léger (`hover:shadow-md` transition 150 ms ease-out — NFR-005).

### Wireframe ASCII

```
┌────────────────────────────────────────────────────────┐
│ Groupement 1  [badge optionnel : À vérifier]            │  ← h3 + badge ambre
│                                                          │
│ Course A — 08:00  →  Centre de dialyse, Saint-Denis     │  ← liste ordonnée
│ Course B — 08:30  →  Hôpital Général, Saint-Denis       │
│                                                          │
│ Véhicule 3 — Berline 5 places                           │  ← véhicule suggéré
│                                                          │
│ Motif : compatibilité horaire + trajet commun           │  ← justification courte
│ Gain estimé : ~12 km à vide économisés                  │  ← gain estimé
│                                                          │
│  [Accepter]       [Rejeter]       [Ajuster]             │  ← 3 actions
└────────────────────────────────────────────────────────┘
```

### Détail des éléments

**En-tête (h3)**
- Libellé : « Groupement {N} » + nombre de courses entre parenthèses si > 2 : « Groupement 1 (3 courses) ».
- Badge « À vérifier » si la zone Hauts est détectée (D-10) : `Badge` variant `outline` + couleur `text-amber-700 border-amber-300 bg-amber-50`, icône Lucide `AlertTriangle` (12 px, `aria-hidden`) à gauche du texte. Toujours doublé du texte « À vérifier » (la couleur seule ne suffit pas — WCAG).

**Liste des courses ordonnées**
- `<ol>` numérotée (ordre de passage dans le groupe).
- Chaque ligne : heure prévue (tabular-nums) + adresse de prise en charge courte + adresse de dépose courte.
- Hauteur de ligne min 24 px, texte `text-sm`.
- Pas de nom patient (NFR-001 — aucun nom propre dans les mockups ; en production réelle, le nom patient s'affiche car il ne s'agit pas d'un mockup mais d'une donnée opérationnelle — l'exécuteur utilisera le vrai champ `patient.prenom + patient.nom`).

**Véhicule suggéré**
- Icône Lucide `Car` (`aria-hidden`) + libellé : « Véhicule {identifiant neutre} — {type} {capacité} places ».
- En V1, D-03 : affectation automatique chauffeur hors périmètre — on affiche uniquement le véhicule suggéré, pas le chauffeur. Libellé : « Véhicule suggéré : Véhicule {N} — {type} ».

**Justification courte**
- Maximum 2 lignes, `text-sm text-muted-foreground`.
- Format : « Motif : {motive court} ».

**Gain estimé**
- Maximum 1 ligne, `text-sm text-muted-foreground`.
- Toujours préfixé « ~ » (approximatif) + suffixé « estimé » ou unité claire.
- Format : « Gain estimé : ~{N} km à vide ».

**3 actions (grain fin — D-15)**
- Rangée de 3 boutons : « Accepter » | « Rejeter » | « Ajuster ».
- Hauteur minimale 44 px (WCAG 2.2 AA — cibles tactiles).
- « Accepter » : variante `default` (fond `--primary`) + icône `Check` (16 px).
- « Rejeter » : variante `outline` + couleur `text-destructive border-destructive/40` + icône `X` (16 px). La couleur est doublée du libellé textuel — WCAG.
- « Ajuster » : variante `ghost` + icône `SlidersHorizontal` (16 px). Ouvre un `Sheet` latéral (voir Surface 3bis).
- La couleur n'est jamais le seul différenciateur : chaque bouton porte un libellé textuel et une icône distincte.
- Transitions : 150 ms ease-out sur `hover` et `focus` — NFR-005.
- Focus : anneau coloré visible (`focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-offset-2`).

**État après action**
- Après « Accepter » : bordure gauche verte (`border-l-4 border-green-500`) + badge `StatusBadge`-style « Accepté » (vert) + icône `CheckCircle` dans le coin supérieur droit. Les boutons « Accepter » passent en état désactivé, « Rejeter » et « Ajuster » restent actifs.
- Après « Rejeter » : bordure gauche rouge (`border-l-4 border-destructive`) + badge « Rejeté » (rouge/destructive). Les boutons « Rejeter » passent en état désactivé. Le groupement reste visible (pas supprimé — la régulatrice peut changer d'avis).
- Les changements d'état sont ephémères (D-18) : aucune écriture en base.

### Surface 3bis — Sheet « Ajuster »

Le clic sur « Ajuster » ouvre un `Sheet` latéral droit (480 px, style cockpit `ride-drawer`) permettant :
- De retirer une course du groupement (checkbox par course).
- De changer le véhicule suggéré (select parmi les véhicules disponibles de la journée).
- CTA : « Valider l'ajustement » (confirme l'état local ; toujours éphémère jusqu'à validation finale).
- Retour : « Abandonner les modifications ».
- Le Sheet n'écrit pas en base — il met à jour l'état local de la proposition.

## 10. Surface 4 — Bande d'indicateurs estimés (D-19)

Exactement 2 indicateurs. Aucun 3e indicateur ne doit être ajouté (D-19 — arbitrage verrouillé). Chaque indicateur porte le mot « estimé » visible.

### Wireframe ASCII

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Taux de mutualisation estimé          Km à vide estimés                 │
│         47 %                                  32 km                      │
│                                                                           │
│  Valeurs estimées (Haversine). Non contractuelles.                       │
└──────────────────────────────────────────────────────────────────────────┘
```

### Règles

- Fond : `bg-muted/60 rounded-lg border border-border` — section distincte mais discrète.
- Les deux indicateurs sont placés dans une grille `grid grid-cols-2 gap-32 p-16`.
- Libellé : `text-xs font-normal text-muted-foreground` — « Taux de mutualisation estimé » / « Km à vide estimés ».
- Valeur : `text-2xl font-semibold tabular-nums text-foreground` — nombre + unité sur la même ligne.
- Avertissement : `text-xs text-muted-foreground italic` en pied de la bande — « Valeurs estimées sur la base de distances à vol d'oiseau (Haversine). Non contractuelles. »
- Aucune couleur sémantique sur les indicateurs (neutre — D-20 : on ne présente pas de performance terrain).
- Aucune icône décorative, aucun graphique (D-19 : chiffres seuls, pas de lib de graphes).
- Le taux de mutualisation est exprimé en pourcentage entier. Les km à vide sont exprimés en km avec 0 décimale.

## 11. Surface 5 — Courses exclues (D-17)

Section obligatoire, toujours visible, placée sous la vue comparative. Si aucune course n'est exclue, la section n'affiche pas « aucune » — elle n'est simplement pas rendue (la présence de la section signale l'exclusion ; l'absence de section signifie que toutes les courses ont été traitées).

### Wireframe ASCII (état avec exclusions)

```
┌─ Courses non incluses dans le calcul ─────────────────────────────────────────┐
│  Ces courses n'ont pas été prises en compte : adresse sans coordonnées         │
│  géographiques. Elles doivent être affectées manuellement.                    │
│                                                                                 │
│  • Course G — 11:00 → Adresse libre (pas de géocodage)                        │
│  • Course H — 15:30 → Adresse libre (pas de géocodage)                        │
└────────────────────────────────────────────────────────────────────────────────┘
```

### Règles

- Fond : `bg-amber-50 border border-amber-200 rounded-lg p-16` (attention, pas erreur — NFR-004).
- Icône Lucide `Info` (16 px, `text-amber-700`, `aria-hidden`) à gauche du titre.
- Titre : « Courses non incluses dans le calcul » (`text-sm font-semibold text-amber-800`).
- Corps : texte explicatif + liste `<ul>` des courses exclues avec leur heure et adresse tronquée.
- Chaque ligne d'exclusion : heure (tabular-nums) + adresse libre + raison courte (« adresse sans coordonnées »).

- La couleur ambre est doublée du texte explicatif — WCAG.
- Si la liste est longue (> 5 courses), les suivantes sont masquées derrière un bouton « Afficher toutes ({N}) » — `Button variant="ghost"`.

## 15. Checklist WCAG 2.2 AA

- **Contraste** : ≥ 4,5:1 texte courant, ≥ 3:1 grand texte (24 px+ semibold). Vérifier la bande indicateurs (`text-muted-foreground` sur `bg-muted/60`) et le badge ambre.
- **Couleur non seule porteuse** : chaque état couleur est doublé d'un texte ou d'une icône avec `aria-label` :
  - Badge « À vérifier » = ambre + texte + icône `AlertTriangle`.
  - Bouton « Rejeter » = rouge + texte + icône `X`.
  - Groupement accepté = bordure verte + badge textuel « Accepté ».
  - Section exclues = ambre + texte explicatif complet.
- **Navigation clavier** : tous les boutons d'action (Accepter/Rejeter/Ajuster), tous les liens de courses exclues, le bouton « Appliquer » et le bouton « Fermer » sont atteignables et activables au clavier. Ordre de tabulation logique : indicateurs → plan actuel (lecture seule) → plan proposé groupement par groupement (h3 → actions) → courses exclues → bouton Appliquer.
- **Cibles tactiles** : tous les boutons d'action ≥ 44×44 px (`min-h-[44px] min-w-[44px]`). Liens de courses exclues ≥ 44 px de hauteur.
- **Sémantique** : `h1` titre de page, `h2` titres « Plan actuel » / « Plan proposé » / « Courses non incluses », `h3` titre de chaque groupement. `<ol>` pour l'ordre des courses dans un groupement. `<ul>` pour les courses exclues. `aria-label` sur les icônes non-décoratives.
- **`prefers-reduced-motion`** : les animations skeleton (`animate-pulse`), les transitions de carte (hover shadow) et les changements d'état (bordure verte/rouge) respectent `prefers-reduced-motion: reduce` — pas d'animation si la préférence est activée.
- **Test du flou** : à 10 % de résolution, les deux colonnes « Plan actuel » / « Plan proposé » restent identifiables par leur position (gauche/droite) et leur titre `h2`. Les chiffres des indicateurs restent lisibles (24 px semibold).
- **Messages d'erreur** : le message d'erreur service indisponible est en français, sans code technique ni stack trace. Le message vide est factuel et informatif.
- **Focus visible** : anneau coloré `focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-offset-2` sur tous les éléments interactifs.

## 17. Anti-patterns (interdits)

- Ne pas présenter la proposition comme une affectation automatique — aucune surface ne doit comporter les mots « affecté automatiquement », « validé automatiquement » ou équivalents (D-14).
- Ne pas afficher un 3e indicateur ou un graphique (D-19 — arbitrage verrouillé, non rouvrable).
- Ne pas présenter les indicateurs comme des mesures terrain (pas de libellé « réel » ou « mesuré » — D-20).
- Ne pas masquer les courses exclues ou les afficher dans une note de bas de page discrète (D-17 — section obligatoire et visible).
- Ne pas bloquer le cockpit pendant le calcul — la navigation reste accessible (D-14).
- Ne pas utiliser un spinner plein écran (NFR-005 — skeleton uniquement).
- Ne pas afficher une modale de confirmation pour « Rejeter » un groupement — l'action est réversible (§6 : pas de confirmation pour action réversible).
- Ne pas afficher une stack trace ou un code d'erreur HTTP en cas d'erreur du service (NFR-002).
- Ne pas utiliser d'émojis dans l'interface (NFR-002).
- Ne pas mélanger plusieurs familles d'icônes (NFR-004 — Lucide uniquement).
- Ne pas utiliser de valeurs de spacing hors de l'échelle 4/8/12/16/24/32/48/64 (NFR-003).
- Ne pas afficher de nom propre dans les placeholders, mockups ou données de seed (NFR-001 — utiliser « Course A », « Véhicule 3 », « Centre de dialyse »).
- Ne pas introduire framer-motion (NFR-005 — transitions CSS 150 ms suffisent).
- Ne pas créer une nouvelle lib de graphes ou de carte pour cette phase — D-19 spécifie des chiffres purs.
- Ne pas persister la proposition en base (D-18 — éphémère, zéro migration de ce côté).
