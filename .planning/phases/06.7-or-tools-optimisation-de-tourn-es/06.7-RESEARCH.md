## Summary

Phase 06.7 introduit le premier service Python persistant dans un monorepo TypeScript / Next.js / Supabase. Toute la complexité algorithmique vit dans `services/optimizer` (FastAPI + OR-Tools 9.15) ; tout le code TypeScript est dans `packages/optimizer-client` (zod + fetch typé) et dans les composants Next.js déjà spécifiés par l'UI-SPEC.

Le modèle PDPTW d'OR-Tools est la représentation standard du transport de patients : chaque course est modélisée comme une paire (nœud pickup, nœud dropoff) avec contraintes de même véhicule, d'ordre (pickup avant dropoff), de fenêtres horaires et de capacité. Les courses sans coordonnées sont simplement exclues du payload avant envoi au solveur (D-17). Le solveur renvoie des groupes (listes d'IDs ordonnés) que le client transforme en proposition affichée à la régulatrice — rien n'est écrit en base tant que la régulatrice ne valide pas (D-14).

Le chemin critique est : contrats zod partagés → `packages/optimizer-client` → hook `use-optimization` → composants UI (déjà spécifiés dans UI-SPEC). Le service Python est consommé de manière synchrone bornée (D-05), ce qui simplifie la gestion d'état côté client.

**Recommandation principale :** FastAPI + uvicorn, OR-Tools 9.15.6755, hébergement Railway.app (PaaS container, Europe West, démarrage < 3 s, suffisant pour beta). La matrice Haversine est recalculée en Python (~10 lignes) — pas d'extraction de `packages/pricing` en `packages/shared` en V1 : le code Python est indépendant et plus simple à tester en isolation.

### Pattern 1 : Modélisation PDPTW OR-Tools

**Ce que fait ce pattern :** modéliser chaque course comme une paire (nœud pickup, nœud dropoff) avec constraints de même véhicule, d'ordre chronologique, de fenêtre horaire et de capacité. Les `AddDisjunction` rendent les paires optionnelles : si une course ne peut pas être groupée sans violer les contraintes, elle reste seule (non groupée) plutôt que d'être forcée.

**Quand utiliser :** toujours — c'est la structure canonique PDPTW pour NEMT.

```python
# Source: OR-Tools official PDPTW pattern [VERIFIED: github.com/google/or-tools]
# services/optimizer/solver.py

from ortools.constraint_solver import pywrapcp, routing_enums_pb2
from .models import SolveRequest, SolveResponse, Groupement
from .haversine import distance_matrix

def solve(req: SolveRequest) -> SolveResponse:
    rides = req.rides
    vehicles = req.vehicles

    # Nœuds : dépôt fictif (index 0) + 2 nœuds par course (pickup + dropoff)
    # ride i → pickup node : 1 + 2*i ; dropoff node : 2 + 2*i
    n_nodes = 1 + 2 * len(rides)
    manager = pywrapcp.RoutingIndexManager(n_nodes, len(vehicles), 0)
    routing = pywrapcp.RoutingModel(manager)

    # --- Dimension distance/temps -----------------------------------------------
    coords = [req.depot] + [c for r in rides for c in (r.pickup, r.dropoff)]
    dm = distance_matrix(coords, req.correction_factor)  # km corrigé

    # On travaille en secondes : distance_km / vitesse_moy_kmh × 3600
    AVG_SPEED_KMH = req.avg_speed_kmh  # constante paramétrable (D-12)
    def time_cb(from_idx, to_idx):
        f = manager.IndexToNode(from_idx)
        t = manager.IndexToNode(to_idx)
        return int(dm[f][t] / AVG_SPEED_KMH * 3600)

    time_cb_idx = routing.RegisterTransitCallback(time_cb)
    routing.SetArcCostEvaluatorOfAllVehicles(time_cb_idx)

    routing.AddDimension(
        time_cb_idx,
        3600,        # slack_max : temps d'attente max entre deux stops (1h)
        24 * 3600,   # max cumul : horizon journée entière
        False,       # ne pas fixer cumul à 0 au départ
        "Time",
    )
    time_dim = routing.GetDimensionOrDie("Time")

    # --- Fenêtres horaires (D-11) -----------------------------------------------
    for i, ride in enumerate(rides):
        pickup_idx = manager.NodeToIndex(1 + 2 * i)
        dropoff_idx = manager.NodeToIndex(2 + 2 * i)

        # Fenêtre dérivée de urgency (D-11) :
        #   programmee : ±30 min autour de scheduled_at
        #   urgente    : ±60 min
        #   immediate  : ±15 min (quasi-pin)
        # Dialyse détectée par urgency == "programmee" avec horaire imposé
        # → tolérance réduite configurée par constante.
        tw = _time_window(ride.scheduled_at, ride.urgency)  # retourne (earliest, latest) en secondes depuis minuit
        time_dim.CumulVar(pickup_idx).SetRange(tw.earliest, tw.latest)
        # Dropoff : après le pickup + durée estimée (pas de fenêtre explicite)
        # Le modèle garantit pickup avant dropoff via AddPickupAndDelivery.

    # --- Dimension capacité -------------------------------------------------------
    def demand_cb(from_idx):
        node = manager.IndexToNode(from_idx)
        if node == 0:
            return 0
        ride_i = (node - 1) // 2
        is_pickup = (node - 1) % 2 == 0
        return 1 if is_pickup else -1  # charge +1 au pickup, -1 au dropoff

    demand_cb_idx = routing.RegisterUnaryTransitCallback(demand_cb)
    capacities = [v.places_assises for v in vehicles]
    routing.AddDimensionWithVehicleCapacity(
        demand_cb_idx, 0, capacities, True, "Capacity"
    )

    # --- Contraintes PDPTW --------------------------------------------------------
    PENALTY = 10_000_000  # pénalité si course non desservie (permet de laisser seule)
    for i in range(len(rides)):
        pickup_idx = manager.NodeToIndex(1 + 2 * i)
        dropoff_idx = manager.NodeToIndex(2 + 2 * i)

        routing.AddPickupAndDelivery(pickup_idx, dropoff_idx)

        # Même véhicule pour pickup et dropoff
        routing.solver().Add(
            routing.VehicleVar(pickup_idx) == routing.VehicleVar(dropoff_idx)
        )
        # Ordre : pickup avant dropoff
        routing.solver().Add(
            time_dim.CumulVar(pickup_idx) <= time_dim.CumulVar(dropoff_idx)
        )

        # Rendre la paire optionnelle avec pénalité → si elle ne peut pas être
        # groupée sans violer les contraintes, elle reste seule (non assignée à
        # un véhicule) et n'apparaît pas dans un groupement.
        routing.AddDisjunction([pickup_idx, dropoff_idx], PENALTY)

    # --- Stratégie de recherche (D-05) -------------------------------------------
    search_params = pywrapcp.DefaultRoutingSearchParameters()
    search_params.first_solution_strategy = (
        routing_enums_pb2.FirstSolutionStrategy.PATH_CHEAPEST_ARC
    )
    search_params.local_search_metaheuristic = (
        routing_enums_pb2.LocalSearchMetaheuristic.GUIDED_LOCAL_SEARCH
    )
    search_params.time_limit.seconds = req.time_limit_seconds  # 2-5 s (D-05)

    # --- Résolution ---------------------------------------------------------------
    solution = routing.SolveWithParameters(search_params)
    if not solution:
        return SolveResponse(groupements=[], rides_exclues_ids=[], km_a_vide_estimes=0.0)

    return _extract_groupements(routing, manager, solution, rides, vehicles, dm)
```

**Points critiques :**
- `AddDisjunction([pickup_idx, dropoff_idx], PENALTY)` : si la pénalité est suffisamment haute, le solveur préfère toujours servir la paire ; si les contraintes l'empêchent, il l'omet — la course reste « non groupée » (pas perdue).
- `SetRange` sur `CumulVar(pickup_idx)` applique la fenêtre horaire. Les nœuds sans fenêtre explicite héritent du slack de la dimension (1h ici).
- L'affectation automatique de chauffeur est hors V1 (D-03) — on affecte uniquement un véhicule (vehicle_idx dans la solution).

### Pattern 2 : Dérivation des fenêtres horaires depuis `urgency` (D-11)

**Ce que fait ce pattern :** transformer `(scheduled_at: str, urgency: str)` en fenêtre `[earliest, latest]` en secondes depuis minuit, sans aucune migration BDD.

```python
# Source: logique de projet (ASSUMED — règle à valider avec le dirigeant)
# services/optimizer/solver.py

from datetime import datetime, timezone
from dataclasses import dataclass

# Tolérances en secondes (constantes de code — D-11)
TOLERANCE_PROGRAMMEE_S = 30 * 60   # ±30 min courses planifiées
TOLERANCE_URGENTE_S    = 60 * 60   # ±60 min courses urgentes
TOLERANCE_IMMEDIATE_S  = 15 * 60   # ±15 min (quasi-pin)

@dataclass
class TimeWindow:
    earliest: int  # secondes depuis minuit UTC+4
    latest: int

def _time_window(scheduled_at_iso: str, urgency: str) -> TimeWindow:
    """
    Réunion = UTC+4 sans DST. scheduled_at est un timestamptz ISO 8601.
    On travaille en secondes depuis minuit UTC+4 pour l'horizon journée.
    """
    REUNION_OFFSET = 4 * 3600
    dt = datetime.fromisoformat(scheduled_at_iso.replace("Z", "+00:00"))
    secs_since_midnight = (dt.timestamp() + REUNION_OFFSET) % 86400

    tolerance = {
        "programmee": TOLERANCE_PROGRAMMEE_S,
        "urgente":    TOLERANCE_URGENTE_S,
        "immediate":  TOLERANCE_IMMEDIATE_S,
    }.get(urgency, TOLERANCE_PROGRAMMEE_S)

    return TimeWindow(
        earliest=max(0, int(secs_since_midnight) - tolerance),
        latest=min(86400, int(secs_since_midnight) + tolerance),
    )
```

**Note sur la dialyse :** les courses de dialyse ont une heure imposée par le centre — elles arrivent typiquement avec `urgency = 'programmee'` et `scheduled_at` précis. La tolérance ±30 min standard est suffisante pour les contraindre sans les rendre infaisables. Aucun traitement spécifique n'est nécessaire si l'heure est déjà précise en BDD.

### Pattern 3 : Calcul Haversine Python (D-09)

**Décision (Claude's Discretion) :** recalcul en Python, ne pas extraire `haversineKm` de `packages/pricing` vers `packages/shared`. Raisons : (1) `haversineKm` est une fonction privée non exportée dans `compute-cgss-short-trip.ts` — extraction nécessiterait une refacto de `packages/pricing` ; (2) le service Python est physiquement séparé (conteneur), il ne peut pas importer du TypeScript ; (3) ~10 lignes Python pur, trivial à tester.

```python
# Source: formule Haversine standard [ASSUMED — formule mathématique universelle]
# services/optimizer/haversine.py

import math
from typing import Sequence

EARTH_RADIUS_KM = 6371.0

def haversine_km(lat1: float, lng1: float, lat2: float, lng2: float) -> float:
    r = math.radians
    dlat = r(lat2 - lat1)
    dlng = r(lng2 - lng1)
    a = math.sin(dlat/2)**2 + math.cos(r(lat1)) * math.cos(r(lat2)) * math.sin(dlng/2)**2
    return 2 * EARTH_RADIUS_KM * math.atan2(math.sqrt(a), math.sqrt(1-a))

def distance_matrix(
    coords: Sequence[tuple[float, float]],
    correction_factor: float,
) -> list[list[float]]:
    """
    Matrice NxN de distances Haversine × facteur_correction (DEC-056).
    coords[0] = dépôt fictif (peut être (0,0) — jamais utilisé dans le coût final).
    """
    n = len(coords)
    return [
        [haversine_km(coords[i][0], coords[i][1], coords[j][0], coords[j][1]) * correction_factor
         for j in range(n)]
        for i in range(n)
    ]
```

```typescript
import { z } from 'zod';

/** Version du contrat — à incrémenter si le schéma change. */
export const CONTRACT_VERSION = '1';

/** ---- Requête (TS → Python) ------------------------------------------------ */

export const RideNodeSchema = z.object({
  id: z.string().uuid(),           // opaque ride ID (D-08 : pas de nom patient)
  pickup: z.tuple([z.number(), z.number()]),    // [lat, lng]
  dropoff: z.tuple([z.number(), z.number()]),   // [lat, lng]
  scheduled_at: z.string().datetime({ offset: true }),
  urgency: z.enum(['programmee', 'urgente', 'immediate']),
  transport_mode: z.enum(['taxi_conventionne', 'tpmr', 'vsl', 'ambulance']),
});

export const VehicleNodeSchema = z.object({
  id: z.string().uuid(),           // opaque vehicle ID
  type: z.enum(['taxi', 'tpmr', 'vsl', 'ambulance']),
  places_assises: z.number().int().min(1).max(20),
  places_tpmr: z.number().int().min(0).max(4),
});

export const SolveRequestSchema = z.object({
  contract_version: z.literal(CONTRACT_VERSION),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),       // YYYY-MM-DD
  rides: z.array(RideNodeSchema).min(1).max(200),
  vehicles: z.array(VehicleNodeSchema).min(1),
  correction_factor: z.number().min(1.0).max(2.0),       // DEC-056
  avg_speed_kmh: z.number().min(10).max(120),             // D-12
  time_limit_seconds: z.number().int().min(2).max(5),     // D-05
});

/** ---- Réponse (Python → TS) ------------------------------------------------ */

export const GroupementSchema = z.object({
  vehicle_id: z.string().uuid(),
  ride_ids: z.array(z.string().uuid()).min(2),  // toujours ≥ 2 courses
  order: z.array(z.string().uuid()),            // ordre de passage
  motif: z.string().max(120),                  // justification courte
  gain_km_a_vide: z.number().min(0),           // km économisés estimés
});

export const SolveResponseSchema = z.object({
  contract_version: z.literal(CONTRACT_VERSION),
  groupements: z.array(GroupementSchema),
  rides_non_groupees_ids: z.array(z.string().uuid()),
  rides_exclues_ids: z.array(z.string().uuid()),   // sans coords (D-17)
  km_a_vide_estimes: z.number().min(0),            // total km à vide plan proposé
});

export type SolveRequest = z.infer<typeof SolveRequestSchema>;
export type SolveResponse = z.infer<typeof SolveResponseSchema>;
export type Groupement = z.infer<typeof GroupementSchema>;
```

### Pattern 5 : Client HTTP typé avec timeout

```typescript
// packages/optimizer-client/src/client.ts [ASSUMED - design to implement]

import { SolveRequestSchema, SolveResponseSchema, type SolveRequest, type SolveResponse } from './contract';

export class OptimizerError extends Error {
  constructor(
    message: string,
    public readonly code: 'TIMEOUT' | 'UNAVAILABLE' | 'CONTRACT_MISMATCH' | 'VALIDATION',
  ) { super(message); }
}

export async function solve(
  request: SolveRequest,
  options: { baseUrl: string; timeoutMs: number },
): Promise<SolveResponse> {
  // Validation du payload avant envoi (évite les allers-retours inutiles)
  const validated = SolveRequestSchema.parse(request);

  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), options.timeoutMs);

  try {
    const res = await fetch(`${options.baseUrl}/solve`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(validated),
      signal: controller.signal,
    });

    if (!res.ok) {
      throw new OptimizerError(`Solveur indisponible (${res.status})`, 'UNAVAILABLE');
    }

    const raw = await res.json();
    const parsed = SolveResponseSchema.safeParse(raw);
    if (!parsed.success) {
      throw new OptimizerError('Réponse solveur inattendue — version de contrat incorrecte ?', 'CONTRACT_MISMATCH');
    }
    return parsed.data;
  } catch (err) {
    if (err instanceof Error && err.name === 'AbortError') {
      throw new OptimizerError('Le service d\'optimisation a dépassé le délai imparti.', 'TIMEOUT');
    }
    throw err;
  } finally {
    clearTimeout(timeoutId);
  }
}
```

```typescript

// Pattern : lecture Supabase → filtre coords → sérialise dé-identifié → idempotence → appel solveur

import { createClient } from '@/lib/supabase/server';
import { solve } from '@tap/optimizer-client';
import { SolveRequestSchema } from '@tap/optimizer-client';

export async function POST(req: Request) {
  const idempotencyKey = req.headers.get('Idempotency-Key');
  const { date } = await req.json();

  const supabase = createClient();
  // Lecture des courses du jour (coordinates nullables)
  const { data: rides } = await supabase
    .from('rides')
    .select('id, scheduled_at, urgency, transport_mode, pickup_lat, pickup_lng, dropoff_lat, dropoff_lng, pickup_citycode, dropoff_citycode')
    .gte('scheduled_at', `${date}T00:00:00+04:00`)
    .lt('scheduled_at', `${date}T23:59:59+04:00`)
    .eq('status', 'validee');

  // D-17 : séparer courses avec et sans coordonnées
  const withCoords = rides?.filter(r => r.pickup_lat && r.dropoff_lat) ?? [];
  const withoutCoords = rides?.filter(r => !r.pickup_lat || !r.dropoff_lat) ?? [];

  // D-08 : payload dé-identifié — UNIQUEMENT IDs opaques + géométrie + contraintes
  const payload = SolveRequestSchema.parse({
    contract_version: '1',
    date,
    rides: withCoords.map(r => ({
      id: r.id,                              // UUID opaque — aucun nom patient
      pickup: [r.pickup_lat, r.pickup_lng],
      dropoff: [r.dropoff_lat, r.dropoff_lng],
      scheduled_at: r.scheduled_at,
      urgency: r.urgency,
      transport_mode: r.transport_mode,
    })),
    // vehicles lus depuis la table vehicles…
    correction_factor: 1.3,   // DEC-056 — à lire depuis tariff_grids en production
    avg_speed_kmh: 50,         // D-12 constante initiale
    time_limit_seconds: 3,     // D-05
  });

  // TODO : vérifier idempotency_keys avant d'appeler le solveur
  // Pattern withIdempotency() adapté depuis apps/web/src/lib/api/idempotency.ts

  const response = await solve(payload, {
    baseUrl: process.env.OPTIMIZER_SERVICE_URL!,
    timeoutMs: 7000,  // D-05 : > time_limit_seconds (3s) + marge réseau
  });

  return Response.json({
    ...response,
    rides_exclues: withoutCoords.map(r => ({ id: r.id, pickup_address: '—' })),
  });
}
```

### Anti-Patterns à éviter

- **Ne jamais inclure `patient_id`, `patient.nom`, NIR ou toute PII dans le payload solveur** — violation RGPD + D-08. L'`id` de la course est suffisant pour le round-trip.
- **Ne pas utiliser `AddDisjunction` sans penalty élevée** — sans penalty, les courses non desservies ne coûtent rien, le solveur les ignore toutes.
- **Ne pas oublier la contrainte de même véhicule** (`VehicleVar(pickup) == VehicleVar(dropoff)`) — sans elle, pickup et dropoff peuvent être sur des véhicules différents.
- **Ne pas accrocher le timeout HTTP à `time_limit_seconds` sans marge** — le réseau + sérialisation JSON prennent 100-500 ms. `timeoutMs = time_limit_seconds × 1000 + 2000` minimum.
- **Ne pas appeler le solveur depuis un Server Component** — le composant `optimization-shell.client.tsx` déclenche l'appel via `useEffect` ou une action asynchrone dans `use-optimization.client.ts`.
- **Ne pas persister la SolveResponse en base** — la proposition est éphémère (D-18). Seule l'écriture finale (Server Action après validation régulatrice) touche la base.

Cette valeur est un paramètre du payload (`avg_speed_kmh`) — la régulatrice peut l'ajuster depuis un panneau de configuration (hors périmètre V1, mais l'architecture supporte déjà).

## Common Pitfalls

### Pitfall 1 : `AddDisjunction` sans les deux nœuds de la paire

**Ce qui rate :** appeler `AddDisjunction([pickup_idx], penalty)` et `AddDisjunction([delivery_idx], penalty)` séparément. Le solveur peut alors desservir le pickup sans le dropoff.

**Raison :** `AddDisjunction` doit recevoir les deux nœuds d'une paire ensemble : `AddDisjunction([pickup_idx, dropoff_idx], penalty)`. Cela signifie « serve les deux ou ni l'un ni l'autre ».

**Comment éviter :** toujours passer la paire complète à `AddDisjunction`. Tester avec un cas où une course est forcément exclue (fenêtre impossible).

---

### Pitfall 2 : `RoutingIndexManager.NodeToIndex()` retourne -1 pour les nœuds fictifs

**Ce qui rate :** utiliser `NodeToIndex()` sur un nœud hors des bornes (ex. nœud de dépôt si Start/End sont différents du nœud 0) → retourne -1 → crash silencieux.

**Raison :** en configuration Single-Depot (tous les véhicules partent et reviennent au nœud 0), `NodeToIndex(0)` retourne l'index du dépôt. Si on passe des starts/ends différents par véhicule, le mapping change.

**Comment éviter :** garder le dépôt unique au nœud 0 en V1. Tester que `manager.NodeToIndex(0) != -1`.

---

### Pitfall 3 : Timeout HTTP < `time_limit_seconds`

**Ce qui rate :** `time_limit_seconds = 3` et `timeoutMs = 3000` → la requête HTTP expire systématiquement avant que le solveur ait rendu son résultat (sérialisation JSON + réseau ~100-500 ms).

**Comment éviter :** `timeoutMs = time_limit_seconds * 1000 + 2000`. Pour `time_limit_seconds = 3` → `timeoutMs = 5000`.

---

### Pitfall 4 : Contrat zod / pydantic désynchronisé silencieusement

**Ce qui rate :** le schéma Python est mis à jour (ex. ajout d'un champ `tpmr_places_requises`) sans incrémenter `contract_version`. Le client TS parse correctement la vieille réponse (champ absent → `undefined`) mais le comportement est incorrect silencieusement.

**Comment éviter :** (1) `contract_version` dans chaque payload, (2) côté TS : `SolveResponseSchema.safeParse()` avec log d'erreur si `parsed.success === false`, (3) tests pytest vérifient que la réponse est parseable par le schéma TS equivalent (contrat inversé).

---

### Pitfall 5 : Capacité TPMR non distincte de `places_assises`

**Ce qui rate :** grouper une course TPMR avec une course standard dans un véhicule berline sans TPMR. Le solveur ne sait pas faire la différence si la contrainte n'est pas modélisée.

**Comment éviter :** ajouter une dimension capacité TPMR séparée, ou utiliser `SetAllowedVehiclesForIndex` pour restreindre les nœuds TPMR aux véhicules TPMR. En V1 simple : si `transport_mode == 'tpmr'`, restreindre au véhicule TPMR disponible via `routing.SetAllowedVehiclesForIndex([tpmr_vehicle_idx], pickup_idx)`.

---

### Pitfall 6 : PII dans le payload solveur (violation D-08)

**Ce qui rate :** inclure `patient_id`, `patient.nom`, ou une adresse en texte libre dans `SolveRequest`. Le solveur non-HDS reçoit des données de santé indirectes.

**Comment éviter :** le Route Handler ne passe que `ride.id` (UUID opaque), coordonnées numériques, horodatages. Jamais de champs texte liés au patient. Tests pytest vérifient que le payload de test ne contient pas de champs `patient_*`.

### Applicable ASVS Categories

### Menaces spécifiques à cette phase

| Menace | STRIDE | Mitigation |
|---|---|---|
| PII dans le payload solveur | Divulgation d'information | Validation automatique : aucun champ `patient_*` dans `SolveRequestSchema` ; test Vitest « no PII in payload » |
| Injection de coordonnées aberrantes | Tampering | `z.number()` bounds dans `RideNodeSchema` ; pydantic `float` avec bounds sur le service |
| Cold-start du solveur en prod → timeout → régulateur bloqué | DoS partiel | Fallback gracieux dans `optimization-shell.client.tsx` : état erreur sans bloquer le cockpit (D-14, UI-SPEC §13) |
| Dérive silencieuse du contrat | Tampering | `contract_version` dans chaque payload ; `safeParse` côté TS avec log d'erreur |
| SSRF via `OPTIMIZER_SERVICE_URL` | Tampering | `OPTIMIZER_SERVICE_URL` est une env var serveur (non exposée au client) ; valider qu'elle pointe vers Railway en CI |

## State of the Art

| Ancienne approche | Approche actuelle | Changement | Impact |
|---|---|---|---|
| OR-Tools `constraint_solver` (API V1) | OR-Tools `routing` module (API V2 stable depuis v7) | 2018 | L'API `pywrapcp` est stable ; le module `routing` est la surcouche haut niveau recommandée |

## Open Questions

1. **Valeurs exactes de tolérance (D-11)**
   - Ce qu'on sait : la règle est une constante de code.
   - Ce qui est flou : ±30 min pour `programmee` est-il suffisant pour la dialyse réelle de La Réunion (certains centres imposent ±5 min) ?
   - Recommandation : implémenter ±30/60/15 min en V1, ajouter un commentaire `# TODO UAT D-11` ; ajuster lors du premier UAT avec un design partner dialyse.

2. **Facteur de correction routier à utiliser dans le payload solveur**
   - Ce qu'on sait : DEC-056 fixe le facteur, il est stocké dans `tariff_grids.facteur_correction_routier`.
   - Ce qui est flou : faut-il lire la grille tarifaire active pour l'envoyer dans le payload, ou utiliser une constante codée en dur (1.3) dans le Route Handler ?
   - Recommandation : lire `tariff_grids.facteur_correction_routier` de la grille active au moment de la requête (une seule query Supabase supplémentaire dans le Route Handler). Cohérent avec DEC-057.

3. **`idempotency_keys` extension vs table dédiée**
   - Ce qu'on sait : la table actuelle a un check `mutation_type` limité.
   - Ce qui est flou : est-ce plus propre d'ajouter `'optimize_rides'` ou de créer `optimizer_request_cache` ?
   - Recommandation : ALTER TABLE existante — coût minimal, cohérence avec le pattern DEC-045.
