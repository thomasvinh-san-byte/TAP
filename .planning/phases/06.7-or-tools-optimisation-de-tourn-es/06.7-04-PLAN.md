# Plan 06.7-04 — Enrichissement minimal UI écran d'optimisation (Wave 4)

## Contexte

Le walkthrough Wave 3 du 2026-06-01 a confirmé que la chaîne fonctionne mais que l'écran d'optimisation affiche des IDs opaques inutilisables (`Course 6dc5714b`, `Véhicule suggéré 33333333`) et que la modale d'ajustement a un dropdown véhicule vide. La régulatrice ne peut ni comprendre ni agir sur les propositions.

Le code Wave 3 avait anticipé cet enrichissement : la prop `rideLabels?: Record<string, string>` existait déjà dans `excluded-rides-section.tsx`, et `adjust-sheet.client.tsx` itérait sur une variable `availableVehicles`. La plomberie UI était en place — il restait à brancher la source côté Route Handler et à propager les props depuis le shell.

## Périmètre

**Lecture A — minimum vital pour walkthrough utilisable.** Pas de refonte visuelle, pas de polish. La passe UX complète (lecture B — structure Plan actuel, micro-interactions, design system) reste tracée comme dette pour phase UX dédiée (cf. `docs/dette-technique/2026-06-01-phase-06.7-cloture.md` D3).

## Tasks

1. **Étendre `OptimizationProposal`** (`packages/optimizer-client/src/transform.ts`) — ajouter `rideLabels?: Record<string, string>` et `vehicles?: Array<{ id; label }>`. Rétrocompatible (optionnels, fallback gracieux côté UI). `solveResponseToProposal()` non modifiée (reste pure).

2. **Enrichir le Route Handler** (`apps/web/src/app/api/optimizer/route.ts`) — `readRidesForDate()` lit en plus `pickup_city`, `dropoff_city`, `pickup_address`, `dropoff_address`, `patient:patients(prenom, nom)`. `readActiveVehicles()` lit en plus `immatriculation`. Helper `enrichProposal()` ajoute `rideLabels` (format « 14h00 — Saint-Denis → Saint-Pierre (B. L.) ») et `vehicles` (format « AB-123-CD — taxi »). Appliqué sur les 2 chemins de retour (cas vide + cas solveur). **D-08 respectée** : enrichissement côté Route Handler authentifié uniquement ; `ridesToSolveRequest()` continue de filtrer explicitement les champs côté `@tap/optimizer-client` (cf. commentaire ligne 93 de `transform.ts`), donc le solveur (Python ou mock) ne voit toujours que des UUIDs opaques.

3. **Étendre l'état empty** (`_lib/use-optimization.client.ts`) — `OptimizationState` `empty` porte désormais `excludedRides: ExcludedRide[]`. Permet au shell d'afficher un message spécifique quand toutes les courses sont exclues pour `no_coordinates`.

4. **Brancher les props** sur 5 composants UI : `optimization-shell.client.tsx` extrait `vehicles` et `rideLabels` de `state.proposal`. `comparative-view.tsx` propage `rideLabels` + calcule `vehicleLabel` par groupement. `proposed-group-card.tsx` consomme `rideLabels` (liste rides) + `vehicleLabel` (suggestion véhicule). `adjust-sheet.client.tsx` consomme `rideLabels` (checkboxes courses). `excluded-rides-section.tsx` reçoit `rideLabels` (déjà câblé en Wave 3, juste alimenté).

5. **Message d'erreur spécifique** dans `optimization-shell.client.tsx` — quand `state.status === 'empty'` ET toutes les `excludedRides` ont `reason === 'no_coordinates'`, afficher « Aucune course exploitable : les N courses de la journée n'ont pas de coordonnées géographiques. L'optimisation nécessite des adresses géocodées. » au lieu du message générique.
