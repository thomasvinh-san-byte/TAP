# Plan 06.11-02 — Wave 2 : Passe UX écran optimisation

## Goal

Enrichir l'écran `/cockpit/optimisation` (5 composants Wave 4 Phase 06.7) avec 5 patterns issus de Solvice OnRoute (« suggest functionality »), RoadWarrior (list view enrichie), étude académique tule2236 (couleurs cluster), et UX standard (loader + bouton).

## Items couverts

### B2 — Modal d'ajustement « le solveur propose, vous décidez »

**Source** : Solvice OnRoute « suggest functionality to propose multiple options for a single empty assignment » + collaborative dispatching pattern.

**Périmètre V1** : sur un groupement proposé, la régulatrice peut :
- Changer le véhicule suggéré (parmi les véhicules compatibles selon `type_permis ↔ vehicle.type` — règle déjà en place Phase 04.5).
- Retirer une course du groupement (la course retourne dans « non groupées »).
- Fusionner deux groupements (drag-and-drop ou bouton « combiner avec... »).

**Implémentation** :
- Composant `<AdjustGroupingModal grouping={g} availableVehicles={...} onSave={...} />`.
- Server Action `updateGroupingPropose(id, changes)` qui ne modifie PAS l'optimisation côté solveur (pas de ré-optimisation back V1) — juste sauvegarde la proposition ajustée en local state du cockpit.
- L'utilisateur peut ensuite « Accepter » la version ajustée → assignation chauffeurs comme aujourd'hui.

**Hors périmètre V1** :
- Ré-optimisation après ajustement (appel solveur). Mock ne supporte pas, vrai solveur reporté Phase 06.12. → bouton « Re-calculer » (B7) déclenche une nouvelle proposition complète depuis zéro.

**Tests Vitest** : modal s'ouvre/ferme, changement véhicule applique le filtre type_permis, fusion 2 groupements respecte les capacités véhicule.

### B3 — Visuels enrichis (badges urgence, TPMR, icônes véhicule)

**Source** : RoadWarrior list view multi-couleur.

**Implémentation** :
- Composant `<RideBadge type="urgency|tpmr|transport_mode" value={...} />` réutilisable.
- Badges affichés sur chaque course dans les groupements proposés ET dans le plan actuel :
  - Urgence : 🟢 programmée / 🟡 urgente / 🔴 immédiate
  - TPMR : icône fauteuil si `transport_mode = 'tpmr'`
  - Type véhicule : icône taxi/TPMR/VSL/ambulance
- Couleurs alignées avec convention GAR (Wave 1 A3) pour cohérence visuelle globale.

**Tests Vitest** : badges rendus correctement pour les 4 modes transport + 3 urgences + TPMR true/false.

### B9 — Couleurs distinctes par groupement (visualisation cluster)

**Source** : étude académique tule2236 GitHub (`Dynamic-Dispatch-and-Route-Optimization-Application`) — « displaying them on the manager interface with different colors for different groups ».

**Implémentation** :
- Chaque groupement reçoit une couleur dédiée (palette 8-10 couleurs distinctes accessibles WCAG, ex: bleu, violet, vert, orange, rose, cyan, ambre, indigo).
- Couleur appliquée :
  - Bordure gauche du card groupement (4-5 px).
  - Pastille colorée à côté de l'ID groupement.
  - Pastille colorée à côté de chaque course dans la liste « plan actuel » (à droite de l'heure) qui appartient à un groupement.
- Effet visuel : la régulatrice voit immédiatement, dans la liste plan actuel, quelles courses sont groupées ensemble et lesquelles restent isolées.

**Tests Vitest** : assignation déterministe couleur ↔ groupement (modulo palette).

### B7 — Bouton « Re-calculer » explicite

**Source** : UX standard.

**Implémentation** :
- Bouton secondaire « ↻ Re-calculer » en haut de l'écran optimisation, à côté du sélecteur de date.
- Au clic : déclenche un nouvel appel au Route Handler `/api/optimizer` (qui appelle mock ou vrai solveur selon env var).
- Tooltip explicatif : « Recalcule à partir des courses actuelles. Annule les ajustements en cours. »
- Confirmation modal si des ajustements B2 sont en cours et non sauvegardés.

**Tests Vitest** : clic déclenche fetch correct, confirmation s'affiche si dirty state.

### B6 — Skeleton loader pendant solving

**Source** : UX standard.

**Implémentation** :
- Composant `<OptimisationSkeleton />` qui mime la structure réelle (2 colonnes, cards groupements grisés).
- Affiché pendant le fetch initial ET pendant un « Re-calculer ».
- Note future : ce composant deviendra **critique** quand vrai solveur réactivé Phase 06.12 (cold start + solving ~5-15 s).

**Tests Vitest** : skeleton affiché tant que loading=true, vraies données affichées dès loading=false.
