# Plan 06.11-03 — Wave 3 : Finition démo

## Goal

Polir les empty states de tous les écrans applicatifs avec un appel à l'action systématique (pattern Doctolib/Stripe), et actualiser le showcase de captures (existant Phase 03) avec tous les écrans livrés Phase 04 à 06.

## Items couverts

### C1 — Empty states audit transverse

**Source** : UX classique Doctolib (déjà adopté Phase 03.1 smart defaults) + Stripe.

**Périmètre** : auditer tous les écrans applicatifs et vérifier que chaque cas « rien à afficher » présente :
- Une icône ou illustration sobre.
- Un titre court et descriptif (« Aucun patient enregistré »).
- Un texte explicatif d'une phrase (« Créez votre première fiche patient pour commencer. »).
- Un bouton primaire « + Nouveau patient » qui mène directement à l'action.

**Écrans à auditer (liste indicative — à confirmer en début de wave)** :

| Écran | Cas empty | Action proposée |
|---|---|---|
| `/patients` | Aucun patient | + Nouveau patient |
| `/courses` | Aucune course aujourd'hui | + Nouvelle course |
| `/courses/caisse` | Aucune course à encaisser | (info seule) |
| `/cockpit` | Aucune course en cours | (info seule) |
| `/cockpit/optimisation` | Aucune course exploitable | + Créer course OU lien vers `/courses` |
| `/admin/chauffeurs` | Aucun chauffeur | + Inviter chauffeur |
| `/admin/vehicules` | Aucun véhicule | + Ajouter véhicule |
| `/admin/tarifs` | Aucune grille | (info seule + lien doc) |
| `/admin/sms-templates` | Aucun template | + Nouveau template |

| `/admin/legal/breaches` | Aucun incident | (info seule, bonne nouvelle) |
| `/admin/legal/requests` | Aucune demande | (info seule) |

**Composant centralisé** : `<EmptyState icon={...} title={...} description={...} action={...} />` dans `apps/web/src/components/empty-state.tsx` si pas déjà existant. Si déjà existant (vérifier `grep -r "EmptyState" apps/web/src/`), réutiliser.

**Tests Vitest** : composant `EmptyState` rendu correctement avec et sans action.

### C7 — Showcase mis à jour Phase 04-06

**Source** : convention interne TAP — `showcase/` existait pour Phase 03 (mentionnée en ROADMAP Phase 0.7 + Phase 04.5 « livraison 10 captures showcase Phase 03 »).

**Périmètre** : capturer les écrans clés Phase 04 à 06 et les organiser dans `showcase/` avec une page index lisible.

**Écrans cibles** (15-20 captures, à valider en début de wave) :
- Phase 04 : invitation chauffeur magic link, AuthShell, DemoCredentials.
- Phase 04.5 : modal assignation filtré type_permis, audit logs.
- Phase 04.7 : page caisse Stripe-style, PricingBreakdown.
- Phase 04.9 : PWA chauffeur (templates pages chauffeur, ConnectionStatus 4 cas).
- Phase 05 : cockpit Realtime, modal récurrence cascade, UI admin SMS, workflow no-show.
- Phase 05.5 : page grille tarif active, simulateur live, recalcul rétroactif.
- Phase 06 : facturation CGSS PDF récapitulatif mensuel.
- Phase 06.6 : pages RGPD pré-remplies (registre, DPA, DPIA).
- Phase 06.7 : écran `/cockpit/optimisation` Wave 4.
- Phase 06.8 : tableau de bord dirigeant (idéalement avec les enrichissements Wave 1 de cette phase).

**Implémentation** :
- Lire la structure existante `showcase/` pour respecter la convention.
- Capturer via Playwright (déjà installé en dépendance dev) — script `scripts/capture-showcase.ts` qui prend des screenshots automatisés.
- Page index `showcase/index.html` ou `showcase/README.md` qui liste les captures par phase avec titre + description courte.

**Hors périmètre** :
- Captures animées (vidéos).
- Versions multi-résolutions (desktop + mobile).
- Versions multi-thèmes (clair / sombre).

**Tests** : aucun test unitaire. Validation visuelle dirigeant lors du walkthrough.
