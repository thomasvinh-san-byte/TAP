# Phase 10.0 — CONTEXT

> Prototype géoloc / terrain. Capture événementielle aux pointages,
> pas de suivi temps réel continu. Données fictives en pré-HDS.

## Principe directeur (RETEX devs réels)

**Capture ÉVÉNEMENTIELLE aux pointages, PAS de suivi temps réel continu.**

Raison : le continu est techniquement impossible à garantir en PWA — la capture s'arrête dès que le chauffeur ouvre Waze/Maps ou éteint l'écran. Ce n'est pas un arbitrage de ressources, c'est une barrière dure. L'événementiel est le pattern qui marche ET le plus sobre.

**Honnêteté produit (non négociable)** : le cockpit affiche la DERNIÈRE POSITION CONNUE + son âge (« vu il y a X min »), JAMAIS un faux « live ». Le mode démo utilise des positions STATIQUES fictives — pas de simulation animée. **On ne vend pas du faux.**

## Cadre : fictif, réversible, zéro dette RGPD

Aucune vraie position persistée en prod (DEC-075). Le proto valide architecture (capture → Realtime → carte) + UI/UX sur données démo. La capture réelle au pointage est CÂBLÉE derrière un flag `GEOLOC_ENABLED` qui n'écrit qu'en démo tant que HDS n'est pas fait.

### D-02 — Table `driver_positions`

Migration `supabase/migrations/20260605000001_driver_positions.sql` :
- `id`, `organization_id`, `driver_id`, `ride_id` nullable, `lat`/`lng numeric(10,7)`, `accuracy`, `captured_at`, `source check ('event','foreground','demo')`.
- Index `(driver_id, captured_at desc)` pour lecture cockpit.

- Fonction `purge_driver_positions()` rétention 90j — câblée, **schedule pg_cron NON activé** tant que HDS n'est pas en place (la planification se fera dans la migration de bascule HDS).

### D-03 — Capture événementielle au pointage (câblée, flag)

`apps/web/src/lib/geoloc/capture-current-position.client.ts` :
- `enableHighAccuracy: true`, `timeout: 8s`, `maximumAge: 5s`.
- Filtrage `POSITION_MAX_ACCURACY_M` (100 m) côté client ET serveur.
- Refus permission / timeout / accuracy mauvaise → renvoie `{}` (pointage non bloqué).

Schéma zod partagé `@tap/shared/driver-position` : `lat`/`lng`/`accuracy` tous OPTIONNELS. Merged dans `start`/`end`/`no-show` payload schemas via `.merge(driverPositionInputSchema)`.

3 Route Handlers `api/driver/rides/[rideId]/{start,end,no-show}` : appellent `recordDriverPosition()` après la mutation métier — non bloquant. `ride-actions.client.tsx` capture la position AVANT le POST, l'ajoute au body et au payload enqueue (offline-first).

Flag applicatif `GEOLOC_ENABLED=true` : tant que pré-HDS, l'INSERT en table de positions réelles ne se fait QUE si explicitement activé (preview démo). En production sans HDS, le flag reste OFF → seul le seed démo persiste.

### D-04 — Capture premier-plan opportuniste (NON LIVRÉ V1 — différé phase suivante)

`watchPosition`/`clearWatch` au mount/blur — laissé en backlog. Le socle (event capture aux pointages) couvre 80 % du besoin cockpit. La capture premier-plan est un bonus qui demande des garde-fous batterie/permission supplémentaires : reportée à une itération ultérieure.

### D-05 — Cockpit : panneau carte + marqueurs + honnêteté temporelle

`use-driver-positions.ts` calqué sur `use-cockpit-rides.ts`, canal Realtime `cockpit:driver_positions`. Garde une `Map<driverId, position>` = dernière connue par chauffeur.

`DriverPositionsPanel` (panneau cockpit) :
- Carte avec marqueurs (tone `primary` < 5 min, `muted` ≥ 5 min).
- Label « vu il y a X min » obligatoire — calculé via `formatPositionAge()`.
- Liste textuelle accompagnante (a11y clavier + lecteur d'écran).
- Badge « DÉMO » visible si au moins une position est `source='demo'`.

Aucune position inventée : un chauffeur sans position connue n'apparaît pas sur la carte.

### D-06 — Mode démo positions STATIQUES

`supabase/seed.demo.sql` étendu : 3 positions fictives sur les 3 chauffeurs démo, coordonnées 974 réelles (Saint-Denis, Saint-Pierre, Saint-Benoît), horodatages variés (2 min, 15 min, 80 min) pour illustrer le rendu « vu il y a X min ». **Aucune animation, aucun simulateur.** `source='demo'` non purgé par rétention 90j.

## RGPD (câblé, prend effet post-HDS)

- **Banner consentement** `GeolocConsentBanner` posé en tête de `/conduite`. Information préalable : capture aux pointages, service uniquement, 90 j max, refus permission NON bloquant. Dismiss persistant via `localStorage`.
- **Indicateur capture** : le délai du pointage (état `pending`) couvre l'acquisition GPS — pas d'indicateur dédié V1.
- **Capture service uniquement** : pas de `watchPosition` automatique (cf. D-04 différé).
- **Rétention 90 j** : fonction câblée, schedule pg_cron à activer en Phase 09 (HDS).
