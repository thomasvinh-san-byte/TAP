# Plan 06.10-02 — Wave 2 : Pipeline geocoding au moment création course (D2)

## Goal

Persister automatiquement `pickup_lat/lng/citycode` + `dropoff_lat/lng/citycode` à la création d'une course via UI, en réutilisant les coordonnées déjà disponibles dans le `onChange` de l'autocomplete BAN/Géoplateforme. Élimine le besoin du seed ad hoc `seed-courses-pour-optimiseur.sql` et débloque la validation de l'optimiseur sur des données réelles.

## Pré-requis

- Wave 1 terminée (Vercel `/py/` OK ou bascule Render OK) ; ou exécution parallèle si audit Wave 2 révèle un cas A simple.
- Pas de modification du schéma `rides` (colonnes `pickup_lat`, `pickup_lng`, `pickup_citycode`, `dropoff_lat`, `dropoff_lng`, `dropoff_citycode` existent déjà depuis migration Phase 04.7).

## Tasks préparatoires (audit — à faire avant tout effort)

### T1 — Auditer `AddressPickerField`

- Localiser le composant : probablement `apps/web/src/components/forms/AddressPickerField.tsx` ou équivalent.
- Inspecter sa signature : que retourne le `onChange` ou `onSelect` ?
  - **Cas A** : `{address, lat, lng, citycode}` complet → effort 4 lignes dans `createRide`.
  - **Cas B** : `{address}` seul, mais le composant tient les coords en state interne (consultables via une ref ou un callback supplémentaire) → effort 15-30 min pour étendre l'événement.
  - **Cas C** : `AddressPickerField` n'utilise pas l'autocomplete (saisie libre uniquement) → effort 2-4 h pour brancher Géoplateforme.

### T2 — Auditer `createRide` Server Action

- Localiser : probablement `apps/web/src/app/(app)/courses/_lib/actions.ts` ou équivalent.
- Inspecter le payload extrait du `FormData` : les coordonnées sont-elles déjà reçues mais non persistées, ou pas reçues du tout ?

### T3 — Tracer le cas dans le PLAN

- Avant d'écrire le moindre code, tracer dans ce PLAN le cas trouvé (A, B, ou C) en commit séparé. Permet d'engager l'effort en connaissance de cause.

## Tasks selon cas (à exécuter après audit T1+T2+T3)

### Cas A — Le plus probable (4 lignes de code)

- T4-A : modifier `createRide` Server Action pour extraire `pickup_lat`, `pickup_lng`, `pickup_citycode`, `dropoff_lat`, `dropoff_lng`, `dropoff_citycode` du `FormData` ou du body de la requête, et les passer à l'INSERT Supabase.
- T5-A : ajouter un test Vitest qui vérifie qu'une course créée avec adresse géocodée a bien ses coordonnées en base après `createRide`.
- Effort : 15 min.

### Cas B — Refactor moyen (15-30 min)

- T4-B : étendre le `onChange` ou `onSelect` d'`AddressPickerField` pour inclure les coords issues de la réponse BAN/Géoplateforme.
- T5-B : adapter le formulaire parent (probablement `RideExpressModal` ou équivalent) pour passer ces nouvelles données dans le `FormData`.
- T6-B : appliquer T4-A et T5-A (extraction côté Server Action + test).
- Effort : 30-45 min.

### Cas C — Refactor lourd (2-4 h)

- T4-C : refactor `AddressPickerField` pour utiliser l'autocomplete Géoplateforme (`https://data.geopf.fr/geocodage/search`) au lieu de la saisie libre. Vérifier explicitement que c'est le bon endpoint (l'ancien `api-adresse.data.gouv.fr` était scheduled pour désactivation janvier 2026 selon l'enquête).
- T5-C : appliquer le pattern « autocomplete retourne `{address, lat, lng, citycode}` dans `onChange` » (alignement avec cas A).
- T6-C : appliquer T4-A et T5-A (extraction côté Server Action + test).
- Effort : 2-4 h.

## Tasks complémentaires (tous cas)

### T7 — Mise à jour du seed démo

- Modifier `supabase/seeds/seed.sql` (ou équivalent) pour que les courses seedées aient leurs coordonnées peuplées.
- Source : utiliser les mêmes adresses Saint-Denis / Saint-Pierre déjà présentes dans le seed (cf. enquête : ~6 adresses connues), géocodées manuellement une fois via curl Géoplateforme et inscrites en dur dans le seed.
- **Élimine définitivement le besoin** du seed ad hoc `seed-courses-pour-optimiseur.sql` utilisé lors du walkthrough Wave 3.

### T8 — Vérification globale

- Recharger `/cockpit` : compteur de courses du jour correct.
- Créer une nouvelle course via UI : vérifier en base que ses coordonnées sont peuplées.
- Lancer `/cockpit/optimisation` avec `OPTIMIZER_USE_MOCK=true` (ou `false` si Wave 1 OK) : vérifier que les courses créées via UI ne sont plus dans `excludedRides` avec `reason='no_coordinates'`.

## Critères de succès Wave 2

- 100 % des courses créées via UI (`RideExpressModal` ou équivalent) après merge ont `pickup_lat`, `pickup_lng`, `pickup_citycode`, `dropoff_lat`, `dropoff_lng`, `dropoff_citycode` non null en base.
- Le mock optimizer (ou le vrai solveur post-Wave 1) reçoit les courses du jour sans exclusion `no_coordinates`.
- Seed démo mis à jour (courses seedées géocodées).
- `pnpm --filter @tap/web typecheck` vert.
- Tests Vitest existants verts + 1 nouveau test vérifie la persistance coords.

## Garde-fous

- **Pas de changement de schéma `rides`** (colonnes lat/lng/citycode existent déjà depuis migration Phase 04.7).
- **Pas de migration de courses historiques sans coords** dans cette wave (script séparé hors Phase 06.10 si nécessaire).
- **Respecter le rate-limit BAN/Géoplateforme** : 50 req/s/IP. Pour TAP en bêta on est très loin (la régulatrice saisit 10-20 courses/jour).
- **Préférer l'endpoint Géoplateforme** `data.geopf.fr/geocodage/search` (l'ancien BAN `api-adresse.data.gouv.fr` était scheduled pour désactivation janvier 2026 selon enquête open-source 2026-06-01).
- **Pas d'appel HTTP au persist** (pattern 2 de l'enquête : geocoding au moment de la saisie UI, pas du persist).
- **NFR-001** : aucun nom propre dans les logs ou commits.
