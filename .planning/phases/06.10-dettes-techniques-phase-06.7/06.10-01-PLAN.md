# Plan 06.10-01 — Wave 1 : Hébergement Python solveur (D1)

## Goal

Faire fonctionner `/api/solver/health` sur preview Vercel en moins de 4 h en déplaçant physiquement le code Python hors de `/api/` Next.js, conformément au pattern non encore essayé (issue Vercel #6598, template `vercel/examples/nextjs-flask-starter`). Critère d'abandon ferme à 4 h. Bascule Render Starter Docker en Wave 1bis si abandon.

## Pré-requis

- Phase 06.7 close (validation walkthrough Wave 4 OK).
- ADR-009 acté (pattern container long-running pour algorithmes coûteux).
- Accès Vercel dashboard pour consulter logs Functions (le diagnostic à distance est épuisé sans cet accès — les 5 PR précédentes ont échoué faute de logs).

## Tasks Wave 1 (tentative Vercel `/py/`)

### T1 — Déplacer physiquement le code Python

- Source actuelle : `apps/web/api/solver/` (1 fichier `index.py` ~40 lignes + `solver.py`, `models.py`, `haversine.py`, `_extract.py`, `requirements.txt`).
- Cible : `apps/web/py/solver/` (ou équivalent à la racine du projet Vercel, hors de `apps/web/src/app/api/` et hors de `apps/web/api/` qui est conflictuel avec Next.js).
- Action : `git mv apps/web/api/solver apps/web/py/solver` puis vérifier que le builder Vercel `@vercel/python` reconnaît bien le nouveau chemin.
- Code Python lui-même : **aucune modification** (les imports relatifs entre `solver.py` et `models.py` ne changent pas, la structure interne est préservée).

### T2 — Adapter `vercel.json`

- État actuel : `vercel.json` racine pointe vers `apps/web/api/solver/index.py` (configuration héritée de Wave 1 Phase 06.7).
- Action : adapter pour pointer vers `apps/web/py/solver/index.py` (legacy `builds`/`routes` ou nouvelle config `functions`, à valider via doc Vercel). Vérifier que la config respecte la convention Vercel pour les fonctions Python hors `/api/`.

### T3 — Adapter `next.config.mjs` rewrites

- État actuel : `next.config.mjs` redirige `/api/solver/:path*` vers `127.0.0.1:8000` en dev (pattern Phase 06.7).
- Action : ajouter ou adapter le rewrite pour que `/api/solver/:path*` côté Next.js soit redirigé vers `/py/solver/:path*` côté Vercel Python en preview/production. Préserver le comportement dev local (proxy vers FastAPI sur port 8000).

### T4 — Retirer le middleware exclude

- État actuel : `middleware.ts` exclut `/api/solver/*` via PR #196 (devenu nécessaire après bascule hybride PR #195).
- Action : retirer cette exclusion (le path Python n'est plus dans `/api/` Next.js, donc le conflit middleware/Python n'existe plus).
- Vérifier que les autres exclusions middleware (statiques, public) restent intactes.

### T5 — Redéployer et tester

- Push branch, attendre déploiement preview Vercel.
- Tester `curl https://<preview>/api/solver/health` : attendu HTTP 200 + body `{"status":"ok"}`.
- Si OK : bascule `OPTIMIZER_USE_MOCK=false` sur preview uniquement, recharger `/cockpit/optimisation`, valider walkthrough complet (cartes affichées, dropdown véhicule rempli, résultat OR-Tools cohérent).
- Si KO : consulter logs Functions Vercel dashboard, capturer l'erreur exacte, l'inscrire dans le SUMMARY pour Wave 1bis.

## Critères de succès Wave 1

- `/api/solver/health` retourne `{"status":"ok"}` HTTP 200 sur preview Vercel.
- `OPTIMIZER_USE_MOCK=false` produit une vraie réponse OR-Tools sur preview (validation manuelle walkthrough).
- `pnpm --filter @tap/web typecheck` vert.
- Tests Vitest et pytest existants verts (régression côté contrat zod + code Python).
- Production reste avec `OPTIMIZER_USE_MOCK=true` jusqu'à validation qualité OR-Tools complète (décision dirigeant Q2).

## Critères d'abandon Wave 1

**Critère ferme** : 4 h écoulées sans `/api/solver/health` à 200 → bascule sur Wave 1bis (Render). Pas d'acharnement.

**Tracking obligatoire** : inscrire dans le PLAN à chaque palier de 1 h la durée écoulée + le symptôme observé (404, 500, timeout, etc.). Permet audit a posteriori.

**Conditions concrètes** :

- Palier 1 h : si T1+T2+T3+T4 pas terminées, pause + ré-évaluation.
- Palier 2 h : si déploiement vert mais `/api/solver/health` ne répond pas, lire logs Vercel et tracer l'erreur exacte.
- Palier 3 h : si logs Vercel inaccessibles ou erreur non comprise après 2 h d'analyse, préparer mentalement la bascule.
- Palier 4 h : si toujours 404 ou erreur non résolue → STOP, switch Wave 1bis.

## Wave 1bis (conditionnel, si abandon Wave 1)

### Goal

Faire fonctionner le solveur OR-Tools sur un container Render Starter long-running (~7 $/mois), aligné avec le pattern communautaire VRP (cf. ADR-009).

### Tasks Wave 1bis

- **T1bis** : créer un compte Render et un service Starter ($7/mois) avec le `Dockerfile` historique de `services/optimizer/` (commit pré-bascule hybride #195 — récupérable via `git show`).
- **T2bis** : exposer URL publique Render (format `https://<service>.onrender.com`).
- **T3bis** : ajouter env var `OPTIMIZER_BASE_URL=https://<service>.onrender.com` sur Vercel apps/web (preview + production).
- **T4bis** : adapter `apps/web/src/app/api/optimizer/route.ts` pour utiliser `OPTIMIZER_BASE_URL` au lieu du chemin Vercel interne. Réintroduire le `solve()` HTTP client de `@tap/optimizer-client` (déjà câblé, conditionné sur `OPTIMIZER_USE_MOCK`).
- **T5bis** : retirer ou commenter la config Vercel Python racine (`vercel.json` + `apps/web/py/`) — ces fichiers deviennent dead code après bascule. Garder dans l'historique Git.
- **T6bis** : tester `curl https://<preview>/api/solver/health` (preview Vercel relayé vers Render). Walkthrough complet `OPTIMIZER_USE_MOCK=false` sur preview.
- **T7bis** : amender ADR-008 pour acter la bascule Vercel → Render. DEC-079 sera rééexaminée à ce moment.

### Critères de succès Wave 1bis

- Render service répond `200` sur `/health`.
- Vercel preview avec `OPTIMIZER_USE_MOCK=false` produit une vraie réponse OR-Tools relayée depuis Render.
- ADR-008 amendée + DEC-079 mise à jour.
- Coût mensuel récurrent connu et accepté (~$7/mois, à ajouter au budget infra).

## Garde-fous

- **Code Python intact** : `solver.py`, `models.py`, `haversine.py`, `_extract.py` ne sont pas modifiés. Seul le chemin physique change.
- **Contrat zod intact** : `CONTRACT_VERSION='1'` reste source de vérité. Pas de modification de `packages/optimizer-client/src/contract.ts`.
- **`OPTIMIZER_USE_MOCK=true` reste actif en production** pendant et après Wave 1. Preview seulement bascule pour tester.
- **Pas de migration BDD** dans cette wave.
- **Doctrines D-08, D-19, NFR-001** respectées (cf. CONTEXT).
- **Pas d'acharnement** : critère d'abandon ferme à 4 h. Wave 1bis est légitime sans hésitation per ADR-009.

## Tentative 2 — config legacy `builds`/`routes` (2026-06-01)

Après échec de la Tentative 1 (config `functions` avec chemin `py/solver/index.py` → erreur build Vercel « Function pattern doesn't match » — cf. `docs/dette-technique/2026-06-01-enquete-post-echec-wave1.md`), tentative finale Vercel avec config legacy `builds`/`routes`.

**Différence avec Tentative 1** : la config legacy accepte explicitement des chemins arbitraires (`@vercel/python` sur `py/solver/index.py` + `@vercel/next` sur `package.json`). **Critère d'abandon ferme : 2 h** après push. Si `/api/solver/health` n'est pas à 200 dans ce délai, **bascule TypeScript/WASM** (Phase 06.11 à discuss) — pas Render (exclu par directive dirigeant).
