## Summary

Phase de **conformité légale** : registre des traitements (art. 30), DPA Supabase (art. 28), DPIA santé (art. 35), portail patient pour les droits art. 15-21, tracker violation 72h (art. 33), pages légales statiques + bandeau cookies CNIL-conforme. **Blocker légal absolu** avant qu'un design partner n'introduise des données patient réelles.

Stack figé : Next.js 14 + Supabase + Tailwind + shadcn/ui. Une seule **nouvelle dépendance majeure justifiée** : `@react-pdf/renderer@4.5.1` pour l'export PDF du registre (autorisé par CONTEXT.md D-17). Le rendu Markdown des pages légales utilisera `next-mdx-remote@6.0.0` (déjà compatible Server Components). Le tracker 72h utilisera **pg_cron + pg_net** (extensions Supabase natives) plutôt qu'une Edge Function dédiée — pas de nouvelle dépendance.

**Primary recommendation :** Suivre le plan de tables/RLS verrouillé en CONTEXT.md (D-05 à D-09) et reproduire fidèlement le pattern audit trigger de la migration 003 patients (filtre colonnes sensibles + `to_jsonb(old) - 'col'` style). Pour la signature JWT du portail patient, utiliser `jose@6.2.3` (déjà standard Next.js 14, pas de dep nouvelle si déjà transitive). Pour l'effacement art. 17, **anonymiser sans détruire** (NIR → hash SHA-256, identité → NULL, courses conservées 5 ans).

### Spécificités France 2026 à respecter

1. **CNIL dark patterns enforcement (déc. 2024 + 2025)** : la CNIL met en demeure les éditeurs avec bandeaux cookies asymétriques. Les boutons « Accepter » et « Refuser » doivent être **équivalents en taille, couleur, lisibilité**. Cette règle est appliquée et sanctionnée. [VERIFIED: cnil.fr Dark Patterns formal notice]
2. **Données de santé = catégorie particulière (art. 9)** : DPIA obligatoire, hébergement HDS exigé en production commerciale (placeholder ADR-003 V1.5).
3. **Délai 30 jours art. 12** : prolongeable une seule fois 60 jours si justifié (complexité + nombre demandes).
4. **Conservation données CGSS** : 5 ans minimum (Code sécurité sociale L114-19) — bloque l'effacement art. 17 → anonymisation. [ASSUMED — durée à confirmer juridiquement]
5. **NIR = donnée à risque** : décret 2019-341 encadre son traitement. Notre stockage chiffré applicatif AES-256-GCM (Phase 1) est conforme.
6. **Cross-domain cookie consent** : la CNIL doit publier guidelines en 2026. Pas de prise en compte V1 (mono-domaine app.tap.re). [VERIFIED: cnil.fr roadmap 2026]

## Critical Implementation Decisions

### 1. JWT signature pour portail patient

**Recommandation : `jose` lib, HS256, secret 32 bytes via env.**

| Question | Réponse | Justification |
|----------|---------|---------------|
| Algorithme | **HS256** | Sym suffit (un seul issuer = nous). ES256 utile uniquement si validation par tiers externe. Pas notre cas. |
| Lib | **`jose@6.2.3`** | [VERIFIED: npm registry, publié 2025+]. Standard Next.js 14, supporte Edge runtime. Préférée à `jsonwebtoken` (Node-only) et `@panva/jose` (renommé jose). |
| Secret | `APP_LEGAL_TOKEN_SECRET` (32 bytes random base64) | Distinct de `APP_NIR_ENCRYPTION_KEY` et `APP_NIR_SEARCH_KEY`. Stocké env Vercel/Supabase. |
| Expiry | **30 jours** (D-10) | Aligné délai légal art. 12. Le `request_token_expires_at` en DB est source de vérité ; JWT `exp` est miroir. |
| Rotation | Manuelle V1, pas de rotation automatique | Token validity 30j → rotation env tous les 90j sans casser les liens en cours (versioning du secret : `APP_LEGAL_TOKEN_SECRET_V1`, `_V2` + claim `kid`). V1 = pas de rotation. ADR placeholder. |
| Claims | `{ sub: request_id, org: organization_id, type: request_type, iat, exp }` | Pas de PII dans le token (ni email, ni patient_id). Le token désigne une `patient_data_request`, le serveur résout. |

**Snippet (≤ 15 lignes) — Server Action de vérification :**

```ts
// apps/web/src/app/(public)/legal/request/[token]/_lib/verify-token.ts
import { jwtVerify } from 'jose';

const secret = new TextEncoder().encode(process.env.APP_LEGAL_TOKEN_SECRET!);

export async function verifyRequestToken(token: string) {
  const { payload } = await jwtVerify(token, secret, {
    algorithms: ['HS256'],
  });
  // payload: { sub: requestId, org, type, iat, exp }
  return payload as { sub: string; org: string; type: string };
}
```

**Rate limiting (D-20) :** 5 tentatives / heure par token via table `legal_request_attempts(token_hash, attempted_at)` + index sur `(token_hash, attempted_at)`. Compteur en Server Action avant chaque déchiffrement.

**Recommandation : `@react-pdf/renderer@4.5.1`, runtime Node.**

### 4. Bandeau cookies CNIL-conforme 2026

**Recommandation : 3 boutons strictement équivalents + persistance 6 mois max + audit log.**

Règles à respecter [VERIFIED: cnil.fr Dark Patterns formal notice + cookieyes blog 2024-2026] :

1. **Symétrie boutons** : « Tout accepter », « Tout refuser », « Personnaliser » → **même taille (≥ 44 px hauteur), même couleur de fond, même police, même padding**. Pas de bouton « accepter » vert et « refuser » gris.
2. **Pas de pré-coché** sauf cookies strictement nécessaires (session/auth Supabase).
3. **Granularité par finalité** : techniques (forcés), analytics (Sentry only V1), marketing (vide V1 — case présente mais désactivée + tooltip « non utilisé V1 »).
4. **Réversible** : lien permanent « Gérer mes cookies » en footer toutes pages (relance le bandeau).
5. **Durée consentement** : **6 mois** (recommandation CNIL), puis re-prompt. Stocké `localStorage.cookieConsent = { version, choices, expires_at }`.
6. **Pas de scroll = consent** (banni explicitement par CNIL).
7. **Audit log** : action `cookie.consent.set` avec `metadata = { choices, user_agent_hash }`. User auth ou anon (organization_id NULL si anon). [DEROGATION audit_logs : table actuelle exige `organization_id NOT NULL` en RLS — CONTEXT.md ne tranche pas. Planner doit décider : table dédiée `public_audit_log` ou rendre `organization_id` nullable côté policy. **Recommandation : table `cookie_consent_log` séparée, pas de `organization_id`, RLS = service_role insert only.**]

**Anti-patterns interdits (CLAUDE.md alignment) :**
- ❌ Modal pleine page au-dessus du contenu
- ❌ Bouton « Refuser » dans un menu déroulant
- ❌ Texte gris pâle illisible sur fond blanc
- ❌ Lien « Refuser » au lieu d'un bouton

### 5. Trigger 72h breach : `pg_cron` vs Edge Function scheduled

**Recommandation : `pg_cron` + `pg_net` (extensions Supabase natives).**

[VERIFIED: supabase.com/docs/guides/cron — pg_cron + pg_net officiellement supportés ; max 8 jobs concurrents, 10 min par job]

| Critère | pg_cron | Edge Function scheduled |
|---------|---------|------------------------|
| Persistance config | DB (versionnable migration) | Supabase config | 
| Performance | Local au DB, < 10 ms | HTTP appel | 
| Coût | Inclus | Inclus quota Edge |
| Test local | `pg_cron` activable Supabase local | Edge runtime local plus complexe |

**Décision** : `pg_cron` exécute toutes les heures une fonction PL/pgSQL qui :

1. Sélectionne les `data_breach_incident` avec `cnil_notification_required = true` et `cnil_notification_at IS NULL` et `detected_at + interval '72 hours' < now() + interval '6 hours'` (alerte 6h avant deadline).
2. Insère une ligne dans `audit_logs` action `breach.deadline_warning` avec `entity_id = breach.id`.
3. (V1.5) déclenche une notif email/SMS au DPO via `pg_net.http_post`.

**Migration extrait :**

```sql
-- Cron horaire : alerte breaches < 6h restantes ou dépassées
select cron.schedule(
  'breach-72h-watchdog',
  '0 * * * *',  -- chaque heure
  $$ select public.check_breach_deadlines(); $$
);
```

**Exposition Cockpit régulateur** : compteur temps réel via Supabase Realtime sur `data_breach_incident` (J-2, 52h restantes) — calcul côté client (pas de re-render serveur). Code couleur : vert > 24h, orange 6-24h, rouge < 6h.

### 6. Anonymisation art. 17 : que conserver, que hasher

**Recommandation : suppression identifiants + hash NIR + conservation courses + audit.**

Tableau des champs `patients` (cf. `20260507000001_patients.sql`) :

| Champ | Action effacement | Justification |
|-------|------------------|---------------|
| `id` | **Conservé** | Référence intégrité courses/billings |
| `organization_id` | Conservé | Multi-tenant |
| `prenom`, `nom` | **NULL** + `'[anonymisé]'` ou hash court | Identité directe |
| `date_naissance` | **Réduit à année** (`1956-01-01`) ou NULL | Identification croisée possible |
| `genre` | Conservé | Statistique non identifiante |
| `telephone`, `telephone_normalized` | **NULL** | Identifiant direct |
| `adresse_*`, `code_postal`, `ville` | **NULL** sauf code_postal (statistique) | Adresse = identifiante santé |
| `contact_urgence_*` | **NULL** | PII tiers |
| `nir_encrypted` | **NULL** | Donnée déchiffrable supprimée |
| `nir_search_hash` | **Remplacé par SHA-256(nir_search_hash + salt)** | Empêche réidentification cross-org tout en gardant unicité tenant |
| `nir_last4` | **NULL** | Pseudonymisation supprimée |
| `consentement_sms*` | NULL | Plus de communication |
| `archive` | **`true`** | Filtré des recherches |
| `archive_at` | `now()` | |
| `archive_reason` | `'rgpd.art17.anonymisation'` | Auditabilité |
| `search_text` | Régénéré (vide) | Colonne générée |

**Conservation tables liées (5 ans CGSS) :**
- `rides`, `ride_executions`, `ride_billings` : conservés avec `patient_id` valide pointant vers le patient anonymisé. Aucune donnée patient identifiante ne fuit (jointure ne ramène que `id` + `genre`).
- `patient_constraint`, `patient_operational_note` : **supprimés** (pas de durée légale, contiennent PII opérationnelle).
- `audit_logs` historiques : **conservés** (durée légale propre 5 ans), mais le champ `metadata.old/new` peut contenir les anciens nom/prenom — **acceptable** car audit_log est append-only et fait partie du registre légal. À documenter dans la DPIA.

**Audit log obligatoire** : action `patient.anonymized` avec metadata `{ original_id, anonymized_at, requested_by_request_id, retention_basis: 'css_l114_19' }`.

**Snippet helper (≤ 15 lignes) :**

```ts
// packages/shared/src/utils/patient-anonymize.ts
export async function anonymizePatient(
  supabase: SupabaseClient<Database>,
  patientId: string,
  requestId: string,
): Promise<void> {
  const salt = process.env.APP_ANONYMIZATION_SALT!;
  const { error } = await supabase.rpc('rgpd_anonymize_patient', {
    p_patient_id: patientId, p_request_id: requestId, p_salt: salt,
  });
  if (error) throw new Error(`Anonymisation échouée : ${error.message}`);
}
// La RPC SQL fait UPDATE + suppression contraintes/notes + INSERT audit_logs
// dans une transaction unique. Verrouillage par advisory lock sur patientId.
```

```sql
declare r record;
begin

    where cnil_notification_required = true and cnil_notification_at is null
      and closed_at is null
      and now() > detected_at + interval '66 hours'  -- 6h avant deadline

    select organization_id, null, 'breach.deadline_warning', 'data_breach_incident', r.id,

    from data_breach_incident where id = r.id;
```

### Anti-Patterns to Avoid

- ❌ **Effacement physique du patient** (DELETE) — viole conservation CGSS 5 ans → use anonymize

- ❌ **NIR clair en réponse art. 15** sans audit log de déchiffrement — viole D-05 Phase 1
- ❌ **Bandeau cookies bloquant** (modal full-page) — anti-pattern CNIL
- ❌ **Bouton « Refuser » plus petit ou caché** — sanctionné CNIL 2024-2025

## Common Pitfalls

### Pitfall 1 : Token JWT contenant des PII

**What goes wrong** : un dev met `patient_id`, `email`, ou `nir_last4` dans les claims pour éviter un round-trip DB.
**Why it happens** : optimisation prématurée, méconnaissance du modèle de menace JWT.
**How to avoid** : claims minimaux `{ sub: requestId, org, type }`. Le serveur résout les autres champs en DB. JWT n'est pas un coffre, c'est un identifiant signé.
**Warning signs** : taille du JWT > 200 bytes, présence de champs métier dans `payload`.

### Pitfall 2 : Audit trigger qui leak le ciphertext NIR ou le token

**What goes wrong** : trigger générique `to_jsonb(NEW)` sans filtrer les colonnes sensibles → ciphertext NIR ou `request_token` dupliqué dans `audit_logs.metadata` à chaque UPDATE.
**Why it happens** : copy-paste sans relecture du pattern Phase 1.
**How to avoid** : reproduire fidèlement le filtre `to_jsonb(old) - 'col1' - 'col2'` de la migration 003. Pour `patient_data_request` : exclure `request_token`, `requester_proof_of_identity_url`, et tout futur champ secret. Test pgTAP : insertion d'une ligne avec token, lecture audit_logs, assert que le token n'apparaît pas en clair.
**Warning signs** : ligne audit_logs > 5 KB, présence de bytea ou JWT-shaped strings dans `metadata`.

### Pitfall 3 : Effacement art. 17 qui casse l'intégrité référentielle

**What goes wrong** : DELETE physique du patient → ON DELETE CASCADE supprime courses → comptabilité CGSS impossible à reconstituer → non-conformité loi.
**Why it happens** : le dev applique RGPD littéralement sans connaître la conservation CGSS L114-19.
**How to avoid** : helper `anonymizePatient` UPDATE only, jamais DELETE. Garde-fou : RLS empêche DELETE pour rôle régulateur (D-19 implicite — pas de policy DELETE sur patients en migration 003).
**Warning signs** : présence de `DELETE FROM patients` dans le code, suppression cascade activée sur `rides`.

### Pitfall 4 : Bandeau cookies non-conforme à l'audit CNIL 2025

**What goes wrong** : design « propre » avec bouton primary « Accepter » et lien gris « Refuser » → mise en demeure CNIL en cas de plainte.
**Why it happens** : pression UX/marketing, méconnaissance des sanctions concrètes 2024-2025.
**How to avoid** : équivalence stricte des 3 boutons (taille, couleur, padding). Test visuel obligatoire dans la PR. Snapshot Playwright comparé à un design figé.
**Warning signs** : différence > 10% en surface entre boutons, bouton « Refuser » dans un menu, pré-coché analytics.

### Pitfall 5 : pg_cron silencieusement non installé en Supabase local

**What goes wrong** : `pg_cron` est une extension privilégiée. En Supabase local (`supabase start`), elle est dispo mais doit être activée via `create extension pg_cron`. Sur Supabase prod, il faut l'activer via Dashboard ou migration.
**Why it happens** : dev oublie l'activation, watchdog 72h ne tourne jamais en prod.
**How to avoid** : migration explicite `create extension if not exists pg_cron with schema cron;` + test pgTAP qui assert `select count(*) from cron.job where jobname = 'breach-72h-watchdog'` ≥ 1.
**Warning signs** : aucun audit_log `breach.deadline_warning` malgré breaches en `data_breach_incident`.

### Pitfall 6 : Rate limit table qui grandit sans purge

**What goes wrong** : `legal_request_attempts` accumule des lignes ad vitam, table devient lente.
**Why it happens** : pas de TTL côté Postgres natif.
**How to avoid** : pg_cron quotidien `delete from legal_request_attempts where attempted_at < now() - interval '7 days'`.
**Warning signs** : table > 100k lignes, requêtes rate-limit > 50ms.

### Verify request token (rate-limited)

```ts
// apps/web/src/app/(public)/legal/request/[token]/_lib/rate-limit.ts
export async function checkRateLimit(supabase: SupabaseClient, tokenHash: string) {
  const { count } = await supabase.from('legal_request_attempts')
    .select('*', { count: 'exact', head: true })
    .eq('token_hash', tokenHash)
    .gte('attempted_at', new Date(Date.now() - 3600_000).toISOString());
  if ((count ?? 0) >= 5) throw new Error('Trop de tentatives. Réessayez dans 1 heure.');
  await supabase.from('legal_request_attempts').insert({ token_hash: tokenHash });
}
```

   - Recommandation : V1 = régulatrice initie depuis admin (canal email vérifié). V1.5 = formulaire public + rate limit IP + reCAPTCHA invisible.

3. **CGU acceptance — bloquante ou banner ?**
   - What we know : D-13 dit « banner d'avertissement si v courante > version acceptée ».
   - What's unclear : peut-on continuer à utiliser l'app sans accepter ? RGPD ne l'impose pas (CGU contractuelle), mais CGV oui pour les actes contractuels.
   - Recommandation : V1 = banner non-bloquant pour CGU+confidentialité, modal bloquant pour CGV à la facturation. Décision planner.

4. **Effacement DPIA `audit_logs.metadata` — leak nom/prenom historique acceptable ?**
   - What we know : audit_logs est append-only, contient `metadata.old/new` avec PII anciennes.
   - What's unclear : faut-il un purge_pii_after_anonymize() qui scanne audit_logs ?
   - Recommandation : NON. audit_logs = registre légal, conservation 5 ans légitime. À documenter dans la DPIA explicitement comme « base légale obligation légale ». Décision planner à valider.
