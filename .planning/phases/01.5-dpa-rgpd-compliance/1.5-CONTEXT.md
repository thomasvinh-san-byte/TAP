## Phase Boundary

Le SaaS dispose d'un **cadre RGPD complet** couvrant les obligations légales pour un traitement de données de santé en France :
- Registre des traitements (art. 30 RGPD) accessible et exportable
- DPA Supabase (Data Processing Agreement art. 28) signé et tracé
- DPIA / Analyse d'Impact Protection des Données (santé = obligatoire CNIL)
- Portail patient pour exercer les droits art. 15-20 (accès, rectification, effacement, portabilité)
- DPO contact + procédure violation 72h
- CGU / CGV / Politique de confidentialité publiées et opposables

**Cette phase est un blocker légal absolu avant l'utilisation par un design partner réel** (i.e. avec des données patient réelles, pas de seed).

**Scope inclus**
- Tables : `data_processing_register`, `dpa_record`, `dpia_record`, `data_breach_incident`, `patient_data_request`
- UI admin légère : registre, DPA, DPIA, breach tracker
- Portail patient (lien email → page publique authentifiée par token signé) : 4 droits exerçables
- Procédure violation 72h documentée + tracker DB
- CGU / CGV / Politique de confidentialité publiées sur `/legal/*` (Markdown rendu)
- Bandeau cookies CNIL-conforme (consent par finalité)

**Scope exclus (autres phases)**
- Chiffrement des données : déjà couvert Phase 1 (DEC-007)
- Audit logs : déjà couvert Phase 0+1 (DEC-010)
- Sécurité technique (RLS, AES-256-GCM) : déjà couvert
- Migration HDS production : V1.5 (ADR-003 placeholder)
- Certification HDS formelle : hors scope dev (audit externe)
- Anonymisation pour exports analytics : V2

## Implementation Decisions

### Cadre légal de référence (verrouillé)

- **D-01** : RGPD applicable + Loi Informatique et Libertés (LIL) modifiée + Code de la santé publique (données santé). Référentiels CNIL appliqués : « Sécurité des données personnelles » + « Référentiel relatif aux traitements de données à caractère personnel mis en œuvre dans le cadre de la prise en charge de patients ».
- **D-02** : **Responsable de traitement** = la société de TAP (notre client SaaS). **Sous-traitant** = nous (éditeur du SaaS) ET Supabase (hébergeur). DPA signé avec Supabase obligatoire (art. 28 RGPD). DPA proposé à nos clients via CGV.
- **D-03** : DPO non obligatoire pour PME mais **fortement recommandé** pour traitement données santé. La société peut désigner un DPO mutualisé (cabinet d'avocats CNIL) ou un dirigeant formé. Notre rôle : exposer un champ DPO contact dans la fiche société, NE PAS imposer un fournisseur.
- **D-04** : DPIA / PIA obligatoire pour le traitement (cf. liste CNIL des traitements à risque élevé : « profilage », « surveillance systématique », « données sensibles »). Modèle CNIL fourni (PDF + Word) — on pré-remplit les sections récurrentes (sécurité, mesures techniques, conservation) et on laisse libres les sections métier (finalités spécifiques, contexte client).

### Tables de données (verrouillé)

- **D-05 — `data_processing_register`** :
  ```sql
  create table data_processing_register (
    id uuid primary key default gen_random_uuid(),
    organization_id uuid not null references organizations(id),
    purpose text not null,                -- finalité (CNIL nomenclature)
    legal_basis text not null check (legal_basis in (
      'consentement', 'contrat', 'obligation_legale',
      'mission_interet_public', 'interet_legitime', 'sauvegarde_vie'
    )),
    data_categories text[] not null,      -- ex: ['identite', 'contact', 'sante', 'financier']
    data_subjects text[] not null,        -- ex: ['patient', 'chauffeur', 'medecin_prescripteur']
    recipients text[] not null,           -- ex: ['CGSS', 'cabinet_comptable', 'transporteur_partenaire']
    retention_period_days int not null,   -- ex: 1825 = 5 ans CGSS, 36500 = 100 ans dossier patient
    security_measures text not null,      -- texte libre (chiffrement, RLS, audit, etc.)
    international_transfer boolean not null default false,
    international_transfer_safeguards text,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),
    created_by uuid not null references auth.users(id),
    updated_by uuid not null references auth.users(id)
  );
  ```
  Versioning par lignes : chaque modification crée une nouvelle ligne, l'ancienne est conservée historiquement (pas de UPDATE destructif). Acceptable car volume faible (~10-30 traitements par société).

- **D-06 — `dpa_record`** : trace les DPA signés (Supabase + nos sous-traitants futurs : Twilio/OVH SMS, Stripe, etc.)
  ```sql
  create table dpa_record (
    id uuid primary key default gen_random_uuid(),
    organization_id uuid not null references organizations(id),
    subprocessor_name text not null,           -- 'Supabase', 'Twilio', 'OVH SMS'
    subprocessor_role text not null,           -- 'hebergement', 'sms_provider', 'payment'
    dpa_version text not null,                  -- 'v2025-01-15' ou hash document
    dpa_document_url text,                      -- URL document signé (Supabase fournit le sien)
    signed_at date not null,
    expires_at date,                            -- NULL si évergreen
    notes text,
    created_at timestamptz not null default now(),
    created_by uuid not null references auth.users(id)
  );
  ```

- **D-07 — `dpia_record`** : DPIA versionnée (1 par traitement à risque élevé, généralement 1-3 par société)
  ```sql
  create table dpia_record (
    id uuid primary key default gen_random_uuid(),
    organization_id uuid not null references organizations(id),
    title text not null,                                  -- 'Transport sanitaire patients ALD'
    scope text not null,
    data_flow_diagram text,                               -- markdown ou URL image
    risks_identified jsonb not null default '[]'::jsonb,  -- liste de risques structurée
    mitigations jsonb not null default '[]'::jsonb,
    residual_risk_level text check (residual_risk_level in ('faible', 'moyen', 'eleve')),
    cnil_consultation_required boolean not null default false,
    cnil_consultation_date date,
    reviewed_at date not null,
    next_review_at date not null,
    status text not null check (status in ('brouillon', 'validee', 'archivee')),
    created_at timestamptz not null default now(),
    created_by uuid not null references auth.users(id)
  );
  ```

- **D-08 — `data_breach_incident`** : tracker violation 72h
  ```sql
  create table data_breach_incident (
    id uuid primary key default gen_random_uuid(),
    organization_id uuid not null references organizations(id),
    detected_at timestamptz not null,
    severity text not null check (severity in ('faible', 'moyen', 'eleve', 'critique')),
    nature text not null check (nature in ('confidentialite', 'integrite', 'disponibilite')),
    affected_data_categories text[] not null,
    affected_subjects_count int,
    description text not null,
    immediate_measures text not null,
    cnil_notification_required boolean not null default false,
    cnil_notification_at timestamptz,                       -- doit être <= detected_at + 72h
    cnil_notification_reference text,                        -- numéro ARS-CNIL
    subjects_notification_required boolean not null default false,
    subjects_notified_at timestamptz,
    closed_at timestamptz,
    closed_by uuid references auth.users(id),
    created_at timestamptz not null default now(),
    created_by uuid not null references auth.users(id)
  );
  ```
  Trigger : si `cnil_notification_required = true` et `cnil_notification_at IS NULL` après 72h, déclencher alerte.

- **D-09 — `patient_data_request`** : trace les demandes de droits (art. 15-20)
  ```sql
  create table patient_data_request (
    id uuid primary key default gen_random_uuid(),
    organization_id uuid not null references organizations(id),
    patient_id uuid references patients(id),               -- nullable (demande anonyme possible si NIR fourni)
    request_type text not null check (request_type in (
      'acces',           -- art. 15
      'rectification',   -- art. 16
      'effacement',      -- art. 17
      'limitation',      -- art. 18
      'portabilite',     -- art. 20
      'opposition'       -- art. 21
    )),
    requested_at timestamptz not null default now(),
    deadline_at timestamptz not null,                      -- requested_at + 30 jours (art. 12)
    status text not null check (status in ('recue', 'en_cours', 'satisfaite', 'rejetee', 'partiellement_satisfaite')),
    response text,
    response_at timestamptz,
    response_by uuid references auth.users(id),
    request_token text not null unique,                     -- token URL signé pour le portail
    request_token_expires_at timestamptz not null,
    requester_email text,                                   -- pour notifier
    requester_proof_of_identity_url text,                  -- pièce justificative chiffrée
    created_at timestamptz not null default now()
  );
  ```

### Portail patient (verrouillé)

- **D-10 — Flow** : la régulatrice (ou le patient lui-même via un formulaire publique) crée une `patient_data_request`. Un email avec lien `https://app.tap.re/legal/request/{token}` (token JWT signé valide 30 jours) est envoyé au patient (consent SMS suffit pas — email vérifié obligatoire). Le patient se connecte avec son NIR + nom + date naissance pour valider l'identité, puis :
  - **Accès** : reçoit un PDF récapitulant ses données + un JSON portable (art. 15 + 20)
  - **Rectification** : formulaire de modification → workflow régulateur (validation manuelle) → audit log
  - **Effacement** : workflow avec garde-fous légaux (durée légale CGSS = 5 ans NON effaçable). Soit anonymisation (NIR remplacé par hash unique non réversible), soit refus motivé
  - **Portabilité** : JSON structuré exportable + format ouvert (CSV)
- **D-11 — Délai légal** : 30 jours (art. 12) prolongeable une fois 60 jours si complexité. Indicateur visuel deadline approchant.
- **D-12 — Refus possible** : effacement refusé si conservation légale obligatoire (CGSS), motif documenté, droit de recours CNIL communiqué.

### Pages légales statiques (verrouillé)

- **D-13** : Pages `/legal/cgu`, `/legal/cgv`, `/legal/confidentialite`, `/legal/cookies`, `/legal/dpo` rendues depuis fichiers Markdown versionnés dans `apps/web/src/content/legal/*.md` (typed via Contentlayer ou simple `import`). Versionning : chaque édit = nouveau commit + acceptance horodatée nécessaire en CGU/CGV. Banner d'avertissement si v courante > version acceptée par utilisateur authentifié.
- **D-14 — Bandeau cookies** : 3 boutons (« Tout accepter », « Tout refuser », « Personnaliser ») + persistance en `localStorage.cookieConsent` + entrée `audit_logs` action `cookie.consent.set` (avec choix). Pas de cookie déclenché tant que pas accepté (sauf cookies strictement nécessaires session/auth).

### DPO contact (verrouillé)

- **D-15** : Champ `organizations.dpo_contact_email` + `dpo_contact_phone` + `dpo_external` boolean (cabinet externe vs interne). Affiché dans page `/legal/dpo` avec mention CNIL. Modifiable par dirigeant uniquement (rôle `dirigeant` requis).

### UI admin (verrouillé)

- **D-16 — Pages admin** sous `/admin/legal/*` (rôle `dirigeant` requis) :
  - `/admin/legal/registre` — CRUD `data_processing_register` (table + drawer édition)
  - `/admin/legal/dpa` — Liste `dpa_record` (table simple)
  - `/admin/legal/dpia` — CRUD `dpia_record` (formulaire long Markdown-aware)
  - `/admin/legal/breaches` — CRUD `data_breach_incident` avec compteur 72h en temps réel
  - `/admin/legal/requests` — CRUD `patient_data_request` (consultation + workflow réponse)
  - `/admin/legal/dpo` — Edition `organizations.dpo_*`
- **D-17** : Export PDF du registre via route Server `/api/admin/legal/registre/pdf` utilisant `@react-pdf/renderer` (déjà compatible stack — autorisé par DEC-003 comme dep client). Si `@react-pdf/renderer` absent, justifier en commit ou utiliser fallback HTML + impression navigateur.

### Sécurité (verrouillé — DEC-002, DEC-006, DEC-010)

- **D-18** : RLS forcée sur les 5 nouvelles tables avec organization_id + helpers existants (`current_organization_id`, `current_user_role`, `has_role`).
- **D-19** : Toutes les mutations sur ces tables → audit_logs trigger.
- **D-20** : Le portail patient consume une route Server avec service_role + verification token + rate limiting (max 5 tentatives / heure par token, sinon 429).
- **D-21** : Les pages `/legal/*` publiques sont en SSG (Static Site Generation) — pas de middleware Auth, accessibles sans login.

### Tests (verrouillé)

- **D-22 — Couverture** :
  - pgTAP RLS sur 5 tables (isolation tenant + rôle dirigeant only)
  - Vitest sur le helper `generatePatientDataExport(patientId)` (export complet patient + check zéro NIR clair)
  - E2E Playwright : régulatrice crée breach → 72h timer commence → notification simulée
  - E2E Playwright : patient ouvre lien email → vérifie identité → exerce droit accès → reçoit JSON
- **D-23** : Cible couverture ≥ 80 % (cf. domain package).

### Claude's Discretion

Le user a délégué (« passe en autonomous »). Décisions techniques alignées DEC-001..DEC-016 + RGPD France :

- **Modèle Markdown vs WYSIWYG** pour DPIA et CGU : Markdown choisi (cf. CLAUDE.md anti-pattern « Pas d'emoji UI » + auditabilité git)
- **Token signature pour portail patient** : JWT HS256 avec secret env `APP_LEGAL_TOKEN_SECRET` (32 bytes). Pas de Edge Function dédiée — Server Action suffisante.
- **PDF generation** : `@react-pdf/renderer` est la solution la plus propre. Si jugée trop lourde, fallback HTML + window.print().
- **Notification CNIL violation** : pas d'API CNIL programmable en 2026 — la procédure est manuelle (formulaire web CNIL). Le tracker enregistre simplement le numéro de notification reçu.
- **Anonymisation patient pour effacement art. 17** : remplacement du NIR par hash SHA-256 non réversible + suppression nom/prenom/téléphone/adresse + conservation des courses sans lien identitaire (durée légale CGSS).

## Specific Ideas

### Compteur 72h breach
Bandeau temps réel visible dans `/admin/legal/breaches` : « Notification CNIL : J-2 (52h restantes) ». Code couleur :
- Vert > 24h restantes
- Orange 6-24h
- Rouge < 6h ou dépassé

### CGU versioning
Chaque user authentifié a un champ `profiles.cgu_version_accepted` (ex: `'2026-05-01'`). Si `current > accepted`, banner « Nos CGU ont été mises à jour » avec bouton « Lire et accepter ». Accept = mise à jour `cgu_version_accepted` + audit log.

### Bandeau cookies
3 boutons de taille équivalente (pas dark pattern « Accepter » plus gros). Choix granulaire : techniques (pré-coché et désactivable), analytics (Sentry only), marketing (vide V1).

### Page `/legal/dpo`
Format simple : nom DPO, email, téléphone, adresse postale + procédure « Comment exercer mes droits » avec lien vers `/legal/request/new`.

### Helper patient-data-export
Pure function dans `packages/shared/src/utils/patient-data-export.ts`. Signature :
```ts
export async function generatePatientDataExport(
  supabase: SupabaseClient<Database>,
  patientId: string
): Promise<{
  format_version: '1.0';
  exported_at: string;
  patient: { ... };  // toutes données patient
  rides: RideExport[];      // courses (à venir Phase 2+)
  prescriptions: PrescriptionExport[];  // bons de transport (à venir)
  audit_log: AuditEntry[];   // historique modifications
}>
```
Doit appeler une route serveur pour le déchiffrement NIR (audit log obligatoire).

### Helper patient-anonymize
Remplace identifiants par hash, conserve les courses/billings (durée légale CGSS), produit un audit log « patient.anonymized » avec horodatage et auteur.
