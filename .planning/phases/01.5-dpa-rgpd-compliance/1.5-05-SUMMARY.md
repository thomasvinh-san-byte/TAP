### Task 5.2 — Portail patient (verify token + rate-limit + identity)

**`_lib/rate-limit.ts`** (35 lignes) — `checkRateLimit(token)` calcule
SHA-256 du token, compte les attempts < 1h, throw si ≥ 5. Insère
systématiquement une ligne (`success: false`). `markAttemptSuccess` insère
une ligne séparée après match identity. Service-role uniquement (la table
`legal_request_attempts` est revoke `authenticated, anon`).

**`page.tsx`** (64 lignes) — try/catch :
1. `checkRateLimit(token)` (D-20)
2. `verifyRequestToken(token)` (Plan 03, JWT HS256 strict)
3. Render `<IdentityForm />`

En cas d'erreur (rate-limit, JWT invalide/expiré, claims malformés),
message générique français (« Lien invalide ou expiré ») — aucune stack
trace, aucune info technique exposée (T-1.5-19, CLAUDE.md § 1).

**`actions.ts`** (190 lignes) — 3 Server Actions :

- `verifyIdentityAction(prevState, formData)` :
  - `checkRateLimit` → `verifyRequestToken` → zod parse (NIR + nom + DDN)
  - `loadRequest(claims.sub, withType=true)` → vérifie status `recue|en_cours`
  - `computeNirSearchHash(nir)` HMAC-SHA256 local (clé `APP_NIR_SEARCH_KEY`)
  - RPC `nir_match_patient_for_legal_request(p_request_id, p_nir_search_hash, p_nom, p_date_naissance)` (Plan 02, SECURITY DEFINER)
  - Si match : update `status = 'en_cours'` + `patient_id`, `markAttemptSuccess`, `redirect('/legal/request/{token}/{access|erasure}')`
  - Sinon : « Identité non vérifiée. » (message générique uniforme — pas de leak entre rate-limit, NIR mismatch, nom mismatch)
- `fulfillAccessAction(token)` :
  - `verifyRequestToken` → `loadRequest` → `generatePatientDataExport` (Plan 03, vue `patients_safe`, NIR null)
  - INSERT `audit_logs.action = 'patient.data_request.fulfilled'` (D-19)
  - UPDATE `status = 'satisfaite'` + `response_at`
  - Retourne `{ data }` (consommé par DownloadJsonButton)
- `fulfillErasureAction(token)` :
  - `verifyRequestToken` → `loadRequest` → `anonymizePatient` (Plan 03 → RPC `rgpd_anonymize_patient` UPDATE only)
  - UPDATE `status = 'satisfaite'` + `response_at` + `response = 'Anonymisation effectuée. Les courses sont conservées 5 ans (CSS L114-19).'`

**`identity-form.client.tsx`** (88 lignes) — `useFormState` + `useFormStatus`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] HMAC-SHA256 du NIR computé localement plutôt que via Edge Function `nir.hash`**

- **Found during:** Task 5.2 conception
- **Issue:** Le plan suggérait « hash via Edge Function NIR puis match RPC ». Or l'Edge Function `nir.hash` exige un JWT user (anon-key + `supabase.auth.getUser(jwt)` retourne le user, voir `supabase/functions/nir/_shared/auth.ts:36-83`). Le portail patient est anonyme — pas de session Supabase. Le service-role JWT n'a pas d'utilisateur associé : `getUser` retourne `null` → 401 « Non autorisé ».
- **Fix:** Calcul HMAC-SHA256 localement dans la Server Action via `node:crypto.createHmac('sha256', APP_NIR_SEARCH_KEY)`. La clé est la **même** que celle utilisée par l'Edge Function (`APP_NIR_SEARCH_KEY`, 32 bytes base64) — produit donc un hash strictement identique. Le NIR clair vit uniquement dans la mémoire de l'action Node, jamais persisté, jamais loggé. Garantie cryptographique : `hashNir()` Edge ≡ `computeNirSearchHash()` apps/web.
- **Files modified:** `apps/web/src/app/(public)/legal/request/[token]/actions.ts`
- **Commit:** e367303
- **Risque:** zéro — algorithme + clé + normalisation identiques. Si la clé Edge change, la Server Action doit suivre (déjà le cas pour tous les déploiements coordonnés CI).

**2. [Rule 1 — Bug] Coercion frontmatter Date → string dans loadLegalDoc**

- **Found during:** Task 5.3 `pnpm build`
- **Issue:** `pnpm build` échoue : « Objects are not valid as a React child (found: [object Date]) ». gray-matter parse `version: 2026-05-08` (YAML date littérale sans guillemets) en `Date` JS. Rendu directement dans `<p>Version : {frontmatter.version}</p>` → React refuse.
- **Fix:** Helper `toIsoDate(value)` dans `load-legal.ts` qui détecte `value instanceof Date` et renvoie `.toISOString().slice(0, 10)`. Appliqué à `version` et `effective_at`. Rebuild OK.
- **Files modified:** `apps/web/src/app/(public)/legal/_lib/load-legal.ts`
- **Commit:** bb9bc8e

**3. [Rule 3 — Blocking] Cast manuel `requestRes.data as DataRequestRow | null` dans actions.ts**

- **Found during:** Task 5.2 typecheck
- **Issue:** La chaîne `supabase.from('patient_data_request').select(...).eq(...).single()` retourne `data: never` malgré `Database` correctement typé — limite de profondeur d'inférence TS sur `@supabase/supabase-js` v2.45 (déjà documentée Plan 04).
- **Fix:** Définition d'un type local `DataRequestRow` + cast explicite `as DataRequestRow | null`. Pattern identique à `(admin)/layout.tsx` Plan 04. Aucune perte de safety (le type DB n'est pas utilisé pour l'inférence ici, seulement pour les noms de tables).
- **Files modified:** `apps/web/src/app/(public)/legal/request/[token]/actions.ts`
- **Commit:** e367303

**4. [Rule 3 — Blocking] Trim actions.ts de 235 → 190 lignes**

- **Found during:** Task 5.3 acceptance check (max_lines: 200 plan frontmatter)
- **Issue:** Première écriture à 235 lignes avec 3 répétitions du SELECT + cast `patient_data_request`.
- **Fix:** Helper privé `loadRequest(sb, requestId, withType?)` factorisé en sortie de `verifyIdentityAction`. Économise 40+ lignes sans changer la sémantique. typecheck + build verts.
- **Files modified:** `apps/web/src/app/(public)/legal/request/[token]/actions.ts`
- **Commit:** bb9bc8e
