# Phase 06.9 — CONTEXT

> Montée Next.js 14.2 → 15.5, React 18 conservé, migration async complète.

## Pourquoi 15.5 + async complète

- 15.5 = dernière stable ligne 15 (`typedRoutes` stable, Turbopack-compatible, Node 20 déjà en place).
- Next 15 garde une compat sync TEMPORAIRE des Request APIs ; Next 16 la supprime. On migre à fond maintenant pour ne pas y revenir.
- React 18 conservé (React 19 hors périmètre, ADR-007 inchangée).

## Décisions fermées

### D-01 Cible Next 15.5, React 18 inchangé

`apps/web/package.json` :
- `next: "^14.2.35"` → `"^15.5.0"` (résolu 15.5.19).
- `next-mdx-remote: 6.0.0` → `5.0.0` (6.x demande React 19).
- React, `react-dom`, `@types/react`, `@types/react-dom` : inchangés (`^18.3.x`).

`packages/database/package.json` : peerDep `next` mise à `^15.5.0`.

### D-02 Migration async complète — interdit casts `UnsafeUnwrapped*`

Le codemod `next-async-request-api` du `@next/codemod@canary` a transformé 17 fichiers. Toutes les pages serveur dynamiques (`params`/`searchParams`) ont migré en `Promise<...>` + `await`. `cookies()` et `headers()` aussi.

Le codemod a inséré 2 casts `UnsafeUnwrappedCookies` / `UnsafeUnwrappedHeaders` — RETIRÉS à la main :

- `lib/supabase/server.ts` : `createClient` devient **async**. Tous les 84 sites consommateurs (`const supabase = createClient()`) migrés à `const supabase = await createClient()` via sed. Les 8 sites typés `ReturnType<typeof createClient>` migrés à `Awaited<ReturnType<typeof createClient>>` (helper `nir-client.ts` consommé partout).
- `admin/chauffeurs/actions.ts:resolveOrigin` : devient `async function resolveOrigin(): Promise<string>` avec `await headers()`. Callers `const origin = await resolveOrigin()`.

### D-03 Codemod-first, reprise manuelle minimale

Codemods exécutés :
- `@next/codemod@canary upgrade` : non utilisé (pas de mode dry-run, j'ai édité `package.json` à la main pour pinner les versions choisies).
- `@next/codemod@canary next-async-request-api .` : 17 transformations, 0 error, 0 `@next-codemod-error` marker. Aucune reprise manuelle de marker requis.

Reprise manuelle ciblée :
- 2 casts `UnsafeUnwrapped*` retirés (D-02).
- 8 `ReturnType<typeof createClient>` → `Awaited<...>`.
- 84 appels `createClient()` → `await createClient()` (sed automatisé).
- 1 import dynamique `await import('@/lib/supabase/server')` ajusté.

### D-04 `ban.ts` cache explicite

Le `fetch` BAN dans `lib/geocoding/ban.ts` n'était caché par défaut qu'en Next 14. En Next 15 il ne l'est plus — comportement souhaité pour du géocodage. Rendu EXPLICITE : `fetch(url, { cache: 'no-store' })` + commentaire « géocodage = pas de cache, fraîcheur voulue ».

Audit : aucun autre `fetch` serveur n'attendait un cache implicite (les 6 autres `fetch` sont CLIENT — modales chauffeur, `use-optimization.client`, cookie-banner, `sync-engine` — non concernés par la rupture cache fetch Next 15).

### D-05 Serwist montée + validation SW/offline

`@serwist/next`, `@serwist/precaching`, `serwist` : déjà `^9`, résolus à `9.5.11` (compatibles Next 15). Build SW (`(serwist) Bundling the service worker script with the URL '/sw.js'`) vert. Pas de régression PWA détectée à la compilation. Validation runtime du précache `/conduite` + offline laissée au smoke test cloud.

### D-06 Purge rewrite `/api/solver` mort

`next.config.mjs` : suppression du bloc `async rewrites()` qui pointait vers `/py/solver/index.py` (FastAPI port 8000 en dev). Le microservice Python a été retiré en Phase 06.12 (ADR-010) — plus aucun caller, plus aucune raison de garder ce rewrite.

### D-07 `typedRoutes` activé (stable 15.5)

`next.config.mjs` : `typedRoutes: true` au TOP-LEVEL (a quitté `experimental` en 15.5). Build vert avec routes typées.

### D-08 ESLint au build : conservé désactivé

`eslint.ignoreDuringBuilds: true` maintenu. Next 15 supporte la flat config ESLint 9, mais l'activer au build risquerait de faire échouer Vercel pour des warnings hors périmètre (9 warnings préexistants). Le lint reste assuré par le job CI dédié. Réactivation ciblée laissée à une phase nettoyage CI ultérieure.

## Résolution incident MDX

Le build initial Next 15 cassait sur `/legal/cgu` et `/legal/cgv` avec « A React Element from an older version of React was rendered » — `next-mdx-remote@6.0.0` (peerDep `react: ">=16"` mais bundle interne React 19) incompatible avec React 18 + Next 15 SSG. Résolution :

1. Downgrade à `next-mdx-remote@5.0.0` (toujours React 18 friendly).
2. `_lib/load-legal.ts` (renommé `.tsx`) : passage de `compileMDX` (double-sérialisation problématique sous SSG) à `<MDXRemote>` (rendu direct RSC, recommandé doc Next 15 + next-mdx-remote).
3. Pages `/legal/*` : `export const dynamic = 'force-dynamic'` (5 pages). SSG laissé pour une phase ultérieure quand un fix amont (React 19 + ADR-007) sera décidé. Impact : pages servies à la demande au lieu du build, latence négligeable, contenu identique. À traquer si volume de requêtes /legal devient critique (V2).
