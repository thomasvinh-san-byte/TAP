# Phase 06.15 — Refonte data tables — CONTEXT

## Goal

Uniformiser les 13 data tables de l'application sur un composant
`<DataTable>` sémantique commun, en consommant les tokens livrés
en 06.14 et les primitives existantes (`EmptyState`, `Badge`,
`Skeleton`). Option 3 dirigeant : **uniformiser maintenant** (structure
+ styles + a11y), **enrichir plus tard** (tri généralisé, pagination,
sélection multiple). Aucune fonctionnalité métier nouvelle.

Valeur : cohérence visuelle/sémantique des 13 surfaces de listes
densément consultées par la régulatrice (8 h/jour), conformité RGAA
4.1.2 (cf. DEC-088), et préparation des fonctionnalités tri/pagination
sans dette d'architecture.

## Pourquoi maintenant

Phase 06.14 vient de poser `tokens.json` comme source de vérité unique
(PR #223). Les 13 data tables actuelles réimplémentent chacune leur
structure (8 `<table>`, 4 `divide-y`, 1 mixte), sans composant
partagé : aucun `ui/table` shadcn dans le repo. C'est la **racine
de l'incohérence** visuelle restante après 06.11/06.13/06.14. Refondre
les tables maintenant :

- consomme directement les tokens migrés (validation de la chaîne) ;
- referme la promesse design system avant les phases produits suivantes
  (06.16 settings, 07 mobile) ;
- évite que de futures phases ajoutent encore des structures de tables
  ad-hoc.

## Décisions

### D-01 — Composant `<DataTable>` sémantique

Créer `apps/web/src/components/data-table/`. Structure HTML
`<table>/<thead>/<tbody>/<tr>/<th>/<td>` (pas de `divide-y` sur un
`<div>`). Rendu dense aligné DEC-034 : header `bg-muted/40`,
padding `12`, séparateurs `divide-border`, hover `bg-muted/50`,
densité 64-72 px/ligne.

Rationale : un `<table>` sémantique permet une a11y RGAA propre
(role row/cell implicite, scope th, aria-sort natif, navigation clavier
au lecteur d'écran), un tri colonne natif quand on l'activera, et
une densité maîtrisée. Aucun composant Table partagé n'existait dans
le repo — c'est la racine de l'incohérence. `ui/table` shadcn non
adopté V1 : on construit le minimum nécessaire, pas plus.

### D-02 — Compose les primitives existantes

Le composant consomme :

- `apps/web/src/components/ui/empty-state.tsx` (06.11 Wave 3 C1) —
  rendu de l'état vide via prop `emptyState?: EmptyStateProps`.
- `apps/web/src/components/ui/badge.tsx` — utilisable dans les
  cellules par le consommateur, max 3 badges par ligne (DEC-034).
- `apps/web/src/components/ui/skeleton.tsx` — rendu loading via prop
  `loading?: boolean`, structure miroir de la table (même nombre de
  colonnes, mêmes largeurs relatives).

Couleurs : exclusivement classes Tailwind sémantiques consommant les
tokens 06.14 (`bg-background`, `border-border`, `text-foreground`, etc.).
**Aucun hex en dur** (NFR-001 + DEC 06.14).

Aucune nouvelle dépendance npm — Radix Table non requis, le minimum
sémantique HTML suffit.

### D-03 — API extensible, seul le tri existant implémenté

Interface prévisionnelle :

```ts
interface DataTableColumn<T> {
  key: string;
  header: ReactNode;
  cell: (row: T, index: number) => ReactNode;
  sortable?: boolean; // déclaré, implémenté V1 uniquement pour caisse
  width?: string; // pourcentage ou px
  align?: 'left' | 'right';
}

interface DataTableProps<T> {
  columns: DataTableColumn<T>[];
  rows: T[];
  rowKey: (row: T) => string;
  ariaLabel: string;
  // Tri (DEC-034 — implémenté V1 pour caisse-table)
  sort?: { column: string; dir: 'asc' | 'desc' };
  onSortChange?: (column: string, dir: 'asc' | 'desc') => void;
  // États
  loading?: boolean;
  emptyState?: EmptyStateProps;
  // V2 (déclarés, NON implémentés V1)
  pagination?: { /* future */ };
}
```

V1 — seul le tri accessible existant (`caisse-table.client.tsx` :
`aria-sort` + tri par URL params + deep-link) est généralisé.
Toutes les autres tables passent `sortable: false`. **Pagination :
prop déclarée mais NON implémentée** — à activer en phase ultérieure
si besoin.

Note vérifiée : `drivers-list.client.tsx` n'a pas de tri de colonnes ;
ses `useState` portent des dialogues archive/invitation. Une seule
table a un tri réel à généraliser (`caisse-table`).

### D-04 — Migration, logique métier préservée

Pour chaque table, l'extraction se limite à la **présentation
tabulaire** :

- Définir le tableau `columns` (header, cell renderer).
- Passer `rows` + `rowKey`.
- Conserver dans le composant client appelant : actions, handlers,
  Server Actions, dialogues, Drawers, Sheets, formulaires.

Cas délicats (poids et richesse fonctionnelle) :

- `drivers-list.client.tsx` (~615 lignes) — multiples actions par
  ligne, dialogues archive/invitation. Extraire UNIQUEMENT la
  structure tabulaire ; les handlers `onClick` restent dans le
  composant appelant et sont passés via les `cell` renderers.
- `vehicles-list.client.tsx` (~200 lignes) — pattern similaire.
- `caisse-table.client.tsx` — généralisation du tri (D-03) sans
  toucher au calcul `total`, à la summary, ni au format `eur`.

**DEC-033 préservée** : les clés React de lignes incluent le champ
mutable (`status`, `actif`, etc.) là où c'était déjà le cas. La prop
`rowKey: (row: T) => string` permet à chaque consommateur de
composer la clé selon ses contraintes.

### D-05 — Accessibilité + densité

- `<th scope="col">` sur tous les en-têtes.
- `aria-sort` sur les colonnes triables, valeurs `ascending`,
  `descending`, `none` selon état actif.
- Navigation clavier native (tab parcourt les liens d'action des
  cellules, pas chaque cellule — comme aujourd'hui).
- Focus visible (anneau token `--ring`).
- `prefers-reduced-motion` : pas d'animation sur hover/sort.
- Densité 64-72 px/ligne (DEC-034) — padding cellule `12`, ligne
  `divide-border`.
- Jour + nuit à parité (tokens 06.14, sélecteur `[data-theme='dark']`).
- Couleur jamais seule (NFR-003) — badges et statuts portent texte
  visible à côté de l'icône.
