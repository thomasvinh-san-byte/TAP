# Phase 06.15 — DISCUSSION LOG

## Arbitrage Option 3 (décision dirigeant 2026-06-04)

Trois options évaluées en amont du cadrage :

- **Option 1** — Migration purement esthétique : remplacer les classes Tailwind
  ad-hoc par les tokens 06.14 dans chaque table, sans toucher à la structure.
  Effort minimal (~4-6 h), gain visuel partiel, **conserve l'incohérence
  structurelle** (8 `<table>`, 4 `divide-y`, 1 mixte).

- **Option 2** — Refonte complète avec tri généralisé + pagination sur les 13
  tables, sélection multiple, états de chargement riches. Pattern Carbon /
  Linear / Polaris. Effort élevé (~30-40 h), gain produit fort mais **scope
  dépasse le besoin V1** (régulatrice satisfaite du modèle actuel hors
  cohérence visuelle).

- **Option 3** — Uniformiser MAINTENANT (composant `<DataTable>` sémantique
  commun, structure `<table>`, primitives partagées), enrichir PLUS TARD
  (tri généralisé, pagination, sélection). API conçue extensible mais
  seul l'existant (tri caisse-table) est implémenté V1. Effort modéré
  (~12-16 h), résout l'incohérence sans sur-engager.

**Décision dirigeant** : Option 3. Rationale : la valeur produit V1 est la
cohérence visuelle et l'a11y (DEC-088 WCAG 2.1 AA + RGAA 4.1.2), pas l'ajout
de fonctionnalités. Préparer l'API pour les enrichissements futurs évite
la dette d'architecture. Le `caisse-table` existant a déjà un tri accessible
(URL params + `aria-sort`) — c'est le modèle à généraliser, pas à réinventer.
