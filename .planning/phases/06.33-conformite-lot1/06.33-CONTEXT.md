# Phase 06.33 — CONTEXT

> Premier lot du module **Conformité réglementaire** (CdC §5.21).
> Pose le socle : modèle de données + saisie + statut dérivé. Les
> alertes (cron + cockpit) et le blocage planification sont les lots
> 2 et 3.

## Pourquoi

Aucun suivi d'échéance n'existait. `drivers` a `numero_licence`/
`type_permis` mais 0 date d'échéance ; `vehicles` 0 échéance ; aucune
représentation de la convention CGSS. Risque légal réel.

**À distinguer du `ComplianceCard` existant** (tableau-de-bord) qui
concerne la conformité RGPD documentaire (registre/DPA/DPIA) — sujet
distinct. Ici = conformité réglementaire **MÉTIER** (cartes, CT,
assurance, convention CGSS, etc.).

## Décisions fermées

### D-01 — Table dédiée `compliance_items` (ADR-013)

Table polymorphe plutôt que colonnes éparses :

```sql
compliance_items (
  id, organization_id, entity_type, entity_id, kind,
  label, reference, issued_at, expires_at, document_url,
  archive, archive_at, created_at, updated_at, created_by
)
```

- CHECK `kind` ∈ {8 valeurs} aligné avec `@tap/shared`.
- CHECK `(entity_type, entity_id)` : `'organization' → null` ;
  `'driver'|'vehicle' → required`.
- RLS forcée : `SELECT same_org`, `INSERT/UPDATE dirigeant`. Pas
  de DELETE (archive logique).
- Trigger audit `compliance_items_audit_trigger` (pattern
  vehicles/drivers).
- Index `(organization_id, expires_at)` pour le cron du lot 2.
- Index `(organization_id, entity_type, entity_id)` pour le badge
  des listes.

Migration : `supabase/migrations/20260608000001_compliance_items.sql`.

### D-02 — Validators et libellés FR centralisés (NFR-001)

### D-03 — Saisie dans les écrans existants

`<ComplianceFieldset>` (`apps/web/src/app/(admin)/admin/conformite/_components/compliance-fieldset.client.tsx`) :
- Section « Conformité réglementaire » embarquée dans `driver-form`
  et `vehicle-form` (mode édition uniquement — la création nécessite
  d'abord d'avoir un UUID).
- Slots pré-définis selon l'entité (3 pour driver, 4 pour vehicle,
  1 pour organization).
- Chaque slot : référence + date délivrance + date échéance + badge
  d'état + bouton Save inline.
- Chargement des items existants via `listComplianceItemsForEntityAction`
  (Server Action, RLS Postgres).
- Save via `upsertComplianceItemAction` (DEC-041 row-count check sur
  UPDATE).

### D-04 — Statut dérivé, jamais stocké

`packages/shared/src/utils/compliance-status.ts` :

```ts
complianceStatus(expiresAt, today?) → { status: 'ok'|'soon'|'expired',
                                         daysUntilExpiry: number|null }
```

- `null/undefined → ok` (sans expiration).
- `expires_at < today → expired`.
- `0 ≤ days ≤ 90 → soon` (fenêtre d'alerte alignée 90/60/30/7 j).
- `> 90 days → ok`.

Helper pur, testable Vitest (14 cas verts). Plus `complianceAlertStep`
pour le cron du lot 2 (capture des franchissements exacts 90/60/30/7).

## Garde-fous

- DEC-032 (branche + PR) ✓
- guard-commit (typecheck + format + tests verts) ✓
- ≤ 300 LOC / fichier ✓
- RLS stricte + pgTAP (10 cas, DEC-098) ✓

- WCAG AA : badge icône + texte (pas couleur seule, critère 1.4.1) ✓
- Jour + nuit : tokens sémantiques uniquement (`text-success`, `text-warning`, `text-destructive`)
- Terracotta : moments-clés réservés — la création d'échéance n'est pas
  un moment-clé d'avancement, bouton « Enregistrer » slot reste neutre
- Données : échéances ≠ données de santé patient → pas de blocage HDS
