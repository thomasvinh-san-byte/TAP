## Assumptions à valider dirigeant

### A-01 — Pricing stub : random vs Haversine ?

**Question** : `computeCgssShortTrip` doit-il retourner un tarif vraiment fictif (random dans une plage) ou une approximation réaliste basée sur la distance Haversine pickup→dropoff (quand les coordonnées sont disponibles) ?

**Options :**

- **(a) Random pur** dans plage [10 € - 80 €] selon urgence/mode transport. Simple, ne dépend pas du géocoding, mais incohérent visuellement (deux courses identiques peuvent avoir des tarifs très différents = perte de crédibilité démo).
- **(b) Haversine + fallback random** : si `pickup_lat/lng` ET `dropoff_lat/lng` sont remplis, calculer la distance Haversine et appliquer `forfait + km × 2.10 € + majo nuit + supp TPMR`. Sinon, fallback random dans la plage. Cohérent visuellement, préfigure le vrai calcul Phase 05.5.
- **(c) Haversine strict** : exiger les coordonnées, lever erreur si manquantes. Bloquant tant que Tronc 3 (géocoding) pas livré sur les courses existantes. Trop strict V1.5.

**Recommandation :** **(b) Haversine + fallback random** — réaliste visuellement, dégrade proprement si coords absentes (les courses créées avant Tronc 3 ou les patients hors BAN). Préfigure le vrai algo Phase 05.5 sans le complexifier (pas de tables de prix kilométriques par tranche, pas de jours fériés 974). Constantes à harmoniser plus tard avec les vraies grilles CGSS.

**Impact si (a)** : -30 min de dev (pas de Haversine), mais risque de friction UAT (« pourquoi le même trajet coûte 35 € la première fois et 62 € la deuxième ? »).

**Impact si (c)** : bloque la démo tant que toutes les courses ne sont pas géocodées — inacceptable V1.5.

### A-02 — `OverrideTarifModal` : dirigeant only ou dirigeant + régulateur ?

**Question** : qui peut forcer manuellement le tarif d'une course ?

**Options :**

- **(a) Dirigeant only** : le tarif est sensible (impact comptable). Le régulateur signale, le dirigeant décide.
- **(b) Dirigeant + régulateur** : la régulatrice gère 8 h/jour les courses ; faire valider chaque override par le dirigeant = friction inacceptable. Trace `audit_logs` permet contrôle a posteriori.
- **(c) Régulateur en mode urgence (asymétrique)** : régulateur peut override jusqu'à ±20 %, dirigeant any value. Complexité supplémentaire pour bénéfice incertain.

**Recommandation :** **(b) Dirigeant + régulateur** avec trace `audit_logs` exhaustive (ancien tarif + nouveau + raison + acteur + timestamp). Cohérent DEC-029 esprit pragmatique (l'urgence prime, l'audit informe). Le dirigeant peut consulter `/admin/audit-logs` (Phase 04.9) et challenger les overrides régulateur a posteriori.

**Mitigation des abus** : raison textarea **obligatoire** ≥ 200 chars (vraie justification, pas un « ok » jeté). Trigger Postgres `audit_logs` automatique. Pas de bouton « override silencieux ».

### A-03 — Caisse : exclure le chauffeur en V1.5 ?

**Question** : le chauffeur a-t-il une vue caisse ou non ?

**Options :**

- **(a) Exclure chauffeur V1.5** : sa vue = `end-ride-modal` sur ses propres courses (au moment de la clôture). Pas de page récap dédiée. Cohérent vue régulateur Stripe Balance.
- **(b) Vue chauffeur simple** : ajouter `/conduite/mes-encaissements` qui montre uniquement ses propres courses du jour. ~30 min de dev supplémentaire.
- **(c) Vue chauffeur via filtre paramétré** : régulateur partage l'URL `/courses/caisse?driver_id=X` au chauffeur. Mais RLS doit alors autoriser le chauffeur à voir SES courses → couplage complexe.

**Recommandation :** **(a) Exclure chauffeur V1.5**. Le chauffeur sait ce qu'il a encaissé (il vient juste de saisir le tarif lors de la clôture). Une vue dédiée `/conduite/mes-encaissements` est une feature « nice to have » mais pas un blocker démo design partner régulatrice. À reporter Phase 04.9 (PWA) si le chauffeur en exprime le besoin.

**Risque** : un chauffeur curieux essaie d'accéder à `/courses/caisse` → RLS bloque (il n'a pas le rôle régulateur/dirigeant). UI affiche une 403 « Accès réservé au régulateur. ».

### A-04 — Backfill géocoding : Server Action one-shot vs script manuel ?

**Question** : comment déclencher le re-géocodage des courses existantes (créées avant Tronc 3) ?

**Options :**

- **(a) Server Action one-shot** déclenchée depuis une page admin `/admin/maintenance` (dirigeant only) avec bouton « Re-géocoder N courses sans coordonnées ». Toast progressbar pendant le run.
- **(b) Script Node `supabase/scripts/backfill-geocoding.ts`** lancé manuellement par le dirigeant ou un développeur. Évite l'ajout d'UI mais viole DEC-032 esprit (les opérations BDD doivent passer par CD ou Server Action tracée).
- **(c) Cron quotidien automatique** qui re-géocode les rides sans coords. Risque rate-limit BAN si volume soudain élevé.

**Recommandation :** **(a) Server Action one-shot** depuis `/admin/maintenance` (page minimaliste, ~15 min). Conforme DEC-032 (tout passe par Server Actions ou CD). Trace `audit_logs` chaque appel. Dirigeant garde la main sur le déclenchement. À utiliser une fois post-déploiement, puis la persistance auto T3.2 prend le relais.

**Si (b) retenu malgré tout** : le script doit être documenté dans `supabase/scripts/README.md` et son exécution loggée manuellement dans `STATE.md`.

### DEC-042 — Algo pricing stub Phase 04.5 (Haversine + fallback random)

`computeCgssShortTrip` :
- Si `pickup_lat/lng` ET `dropoff_lat/lng` fournis : calcul Haversine (formule sphérique terre, rayon 6371 km), tarif = `4.20 + dist_km × 2.10`
- Sinon : `random(min, max)` dans une plage cohérente avec `transport_mode` et `urgency`
- Toujours appliquer : majo nuit (+20 % entre 20 h et 7 h), supplément TPMR (+5 €), arrondi à 0.05 € le plus proche
- Total clamp final ∈ [10 €, 80 €]
- Badge UI « DEMO » obligatoire pour rappeler que ce n'est pas le calcul CGSS final

**Justification** : visuellement crédible, préfigure Phase 05.5, dégrade proprement.

### DEC-044 — Géocoding persistance threadé BAN + POI

Quand l'utilisateur sélectionne une adresse dans `AddressOrPOIPicker` :
- **POI** : récupère `latitude/longitude` de `pois_metier`, propage `(lat, lng, citycode=postcode)` au parent via `onSelect`
- **BAN** : récupère `f.geometry.coordinates[1] / [0]` + `f.properties.citycode` (déjà extrait dans le legacy `address-picker-field.client.tsx`), propage au parent
- **Saisie libre** : pas de coords (acceptable, fallback random pricing T1.2 pour ces courses)

`createRideAction` + `editRideAction` reçoivent les 6 colonnes optionnelles dans leur input Zod, persistent en BDD. Pas de Edge Function, pas de re-géocodage temps réel.
