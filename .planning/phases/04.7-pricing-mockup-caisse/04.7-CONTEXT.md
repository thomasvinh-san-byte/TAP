## Goal de la phase

Livrer la **chaîne pricing UI complète** (sans le calcul réel CGSS, reporté Phase 05.5) + une **page caisse régulateur** type Stripe Balance pour visualiser et exporter les paiements + la **migration géocoding** (lat/lng/citycode) pour préparer le calcul réel Phase 05.5.

La régulatrice doit pouvoir, post-Phase 04.7, fermer une course avec un tarif lisible et cohérent (même si fictif), réviser ce tarif si besoin avec justification, et consulter sa caisse du jour avec export Excel propre. Le tout sans toucher au code Edge Function NIR (différé Phase 06) ni à l'intégration tarif réel CGSS.

## Dépendances et risques

**Dépendances :**
- Phase 04.5 livrée (✅ #71..#87 mergées)
- `AddressOrPOIPicker` (PR #84) — fournit la base à étendre Tronc 3
- Migration `pois_metier` (PR #84) — fournit `latitude/longitude` pour pré-remplissage POI

**Risques identifiés :**

- **R1 — Compat Vitest packages/pricing** : nouveau workspace, risque de mauvais alignement vitest 2.x avec setup pnpm monorepo. Mitigation : copier la config de `packages/shared/vitest.config.ts`.
- **R2 — Encoding CSV Excel FR** : `utf-8-sig` + `;` est le combo connu mais à tester sur Excel macOS et Excel Windows. Mitigation : test E2E qui ouvre le fichier downloadé et vérifie le contenu (sans Excel mais avec parser CSV node).
- **R3 — Backfill géocoding lent** : 100+ courses existantes × 1 req BAN/seconde = 100 s. Acceptable one-shot. Mitigation : toast progressbar + bouton « stopper », résultats partiels OK.
- **R4 — pricing stub trop simpliste** : si le tarif retourné est incohérent (ex : 80 € pour 2 km), la démo perd de la crédibilité. Mitigation : Haversine + table prix km réaliste 974 (~2.10 €/km observé sur grilles publiques) — voir A-01.
