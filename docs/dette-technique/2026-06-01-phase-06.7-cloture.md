# Dettes ouvertes à la clôture Phase 06.7 (2026-06-01)

Document consolidé pour les sessions futures. La Phase 06.7 OR-Tools est
fonctionnellement close avec mock (cf. SUMMARY 06.7-03 et ROADMAP), mais
quatre dettes assumées restent à reprendre.

## D1 — Hébergement Python solveur OR-Tools

- **État** : `OPTIMIZER_USE_MOCK=true` sur Vercel `apps/web` (Preview +
  Production). Le mock (`apps/web/src/app/api/optimizer/_mock-solver.ts`)
  retourne une réponse conforme au contrat zod sans appel au service Python.
- **Code Python** : `apps/web/api/solver/` (intact depuis la bascule
  hybride PR #195, 11/11 pytest verts dans cette localisation).
- **DEC-079 reste LOCKED en intention** (Vercel Python serverless, voie
  hybride single-projet, repli Clever Cloud documenté). Les six critères
  de monitoring documentés deviennent caducs tant que le service Python
  n'est pas en ligne.
- **Bloquant** : malgré 5 PR de fix consécutives (#196 middleware exclude,
  #197 router FastAPI sans double-prefix, #198 `vercel.json` au Root
  Directory, #199 rewrite Next.js, plus le refactor initial #195), le
  `curl /api/solver/health` renvoie un 404 persistant. Diagnostic à
  distance épuisé sans accès direct aux logs Functions du dashboard
  Vercel.
- **À reprendre** : quand la validation qualité OR-Tools deviendra
  prioritaire — pas avant. Réactivation = retirer `OPTIMIZER_USE_MOCK` et
  débloquer le 404 avec accès aux logs Functions (ou changer d'hébergeur).

## D2 — Pipeline geocoding au moment création course

- **État** : toutes les courses arrivent en base avec `pickup_lat=NULL`
  et `dropoff_lat=NULL`. La migration Phase 04.7 a créé les colonnes
  (`pickup_lat`, `pickup_lng`, `pickup_citycode`, idem dropoff) mais
  aucun appel automatique au géocodeur BAN gouv.fr ou aux POI métier
  n'est branché à la création de course.
- **Conséquence** : l'optimiseur exclut systématiquement ces courses
  (`packages/optimizer-client/src/transform.ts` filtre les courses sans
  coordonnées avant d'envoyer le payload au solveur). Sur les 25 courses
  préexistantes du seed démo, 0 étaient géocodées au moment de la
  validation Wave 3.
- **DEC-044** documente l'intention (threading du `lat/lng/citycode`
  depuis l'`AddressOrPOIPicker.onSelect`) mais le pipeline n'est pas
  branché côté Server Action `createRideAction`.
- **À reprendre** : Phase 04.7 (compléter le threading déjà documenté)
  ou plus tôt selon priorité. **Bloque la validation métier OR-Tools
  réelle** : sans géocodage automatique, on ne peut pas mesurer la
  qualité d'optimisation sur un volume représentatif.

## D3 — Passe UX écran optimisation Wave 3

- **État** : cartes de groupement affichent des IDs opaques
  (`Course 6dc5714b`) au lieu de patient + trajet (ville pickup → ville
  dropoff) + horaire. Véhicule affiché en ID technique (`33333333`) au
  lieu d'immatriculation lisible. « Plan actuel » à gauche : liste
  numérotée sans hiérarchie visuelle.
- **Message d'erreur trompeur** : « Aucune course compatible » s'affiche
  quand toutes les courses sont exclues pour absence de coordonnées —
  message à reformuler en « X courses exclues car sans coordonnées
  géographiques ».
- **Cause structurelle** : la transformation
  `solveResponseToProposal` (`packages/optimizer-client/src/transform.ts`)
  ne ré-enrichit pas la réponse solveur avec les infos d'affichage. La
  dé-identification D-08 est correcte côté solveur (le solveur ne reçoit
  jamais de nom patient), mais le Route Handler ou la transformation
  finale doit ré-enrichir avant de retourner au front depuis la base.
- **À reprendre** : passe UX dédiée Wave 3+ (peut entrer dans la
  prochaine itération cockpit ou être traitée en hotfix UX selon la
  proximité produit).

## D4 — Audit casts `as TYPE[]` (lot 3 audit D+A)

- **État** : 2 TODO commentés ajoutés sur les casts cockpit emblématiques

- **À reprendre** : moment calme, post-clôture de phase. Pas urgent.
